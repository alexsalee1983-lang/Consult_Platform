# 安全扫描

CI 的 `security` 任务在每次推送、每个 PR 和每周一 09:00（北京时间）运行；镜像扫描在 `compose` 任务里对整套已构建镜像运行。发现问题即失败，不能合并。

| 扫描 | 工具 | 范围 | 失败条件 |
|---|---|---|---|
| Python 依赖漏洞 | pip-audit 2.7.3 | `backend/requirements-dev.txt`（含 `requirements.txt` 及其传递依赖） | 任何已知漏洞 |
| 前端依赖漏洞 | npm audit | `frontend/package-lock.json` | 任何已知漏洞 |
| 密钥泄露 | gitleaks 8.30.1（官方发布包，校验 SHA-256） | 全部提交历史 | 任何疑似密钥 |
| Python 代码静态检查 | bandit 1.9.4 | `backend/app` | 中危及以上 |
| 镜像漏洞 | trivy 0.76.2（官方发布包，校验 SHA-256） | `docker compose config --images` 列出的全部镜像（不含只用于测试的模拟模型） | 有修复版本的高危、严重漏洞（`--ignore-unfixed`） |

暂无修复版本的漏洞不让 CI 失败，但每周扫描结果要看，修复版本发布后会自动开始报错。

## 本地运行

```bash
# backend 目录，虚拟环境中
pip install pip-audit==2.7.3 && pip-audit -r requirements-dev.txt
# frontend 目录
npm audit
# 仓库根目录（需先安装 gitleaks）
gitleaks git --redact --verbose .
# 仓库根目录
pip install bandit==1.9.4 && bandit -q -r backend/app -ll
# 有 Docker 的机器（测试机），先 docker compose build
for img in $(docker compose --profile monitoring config --images | sort -u); do trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed --ignorefile .trivyignore.yaml "$img"; done
```

## 扫描失败怎么办

**依赖漏洞**：升级到修复版本，在 PR 里写明漏洞编号和升级前后的版本。升级会引入新的传递依赖时，先确认它不联网调用外部服务（数据保护红线第 2 条）。确实无法升级时问负责人，不要自行加忽略。

**疑似密钥**：

1. 真密钥：立即通知负责人，**先作废这把密钥**，再从代码中删除。提交历史里的密钥删不干净，只能作废。
2. 误报（如机密级检测规则的测试样例）：把 gitleaks 输出的 `Fingerprint` 加进仓库根目录的 `.gitleaksignore`，写一行注释说明为什么是误报。只按指纹忽略单处，不按目录或规则整体放行。**注释里不要写出被忽略的值本身**，否则这一行又会被扫出来。
   唯一的例外写在根目录 `.gitleaks.toml`：知识条目文件（`knowledge/**/*.md`）元数据头里的 `key: 条目标识` 一行会被默认规则误判为密钥，这里同时按路径和整行格式放行（两个条件都满足才放行），其他位置、其他写法照常扫描。新增此类例外须负责人同意。

测试样例尽量用明显虚构、不像真实格式的值，避免触发误报。

**代码静态检查（bandit）**：确认是误报的，在该行加 `# nosec Bxxx  理由`（只针对这一条规则，不写不带编号的 `nosec`），PR 里说明。

**镜像漏洞（trivy）**：优先升级基础镜像或系统包（Dockerfile 里固定版本的镜像改到修复版本）；确实不影响本平台（例如漏洞在未使用的组件里）且一时无法升级的，写进根目录 `.trivyignore.yaml`：每条写 `statement`（理由和影响评估）、`paths`（只对相应文件生效）和 `expired_at`（复查日期，到期自动失效、扫描重新报出），PR 里说明。
