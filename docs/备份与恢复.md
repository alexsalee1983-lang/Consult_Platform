# 备份与恢复（M5 ④）

依据：架构设计第六节“备份”（每日全量，异地或离线副本；RPO 24 小时、RTO 4 小时；每季度演练；备份保留期不超过合同约定的最短保留期，项目销毁时记录备份过期日期）；等保三级技术控制自查 8.1.4.3 c、8.1.4.9。

## 1. 备份什么

| 对象 | 方式 | 说明 |
|---|---|---|
| PostgreSQL（含审计表） | `pg_dump -Fc`，gpg 对称加密（AES-256） | 审计表只追加的触发器随库一起备份和还原 |
| 对象存储（MinIO 数据卷） | 暂停 MinIO 几秒打包数据卷，再 gpg 加密 | 对象本身已服务端加密（`MINIO_KMS_SECRET_KEY`），备份里是双层密文 |
| 审计链头 | 备份前先 `verify-audit`，链头写进 `manifest.json`，并追加到备份根目录的 `audit-heads.log` | 链不完整时不备份；链头留在库外，防止审计记录末尾被删后链仍自洽 |
| 不备份 | Redis（只有会话，恢复后重新登录）、向量和重排模型（镜像里自带） | |

`.env` 不进备份。恢复需要和备份时一致的 `MINIO_KMS_SECRET_KEY`（否则对象读不出）、`TOTP_KEYS`（否则动态码种子解不开）和数据库口令：部署时把 `.env` 和备份口令按公司密钥管理要求另行离线保管，**不要和备份文件放在一起**。

## 2. 每日备份

```bash
# 部署机，仓库根目录。备份口令文件只放部署机：
sudo install -d -m 700 /etc/consult-platform
head -c 48 /dev/urandom | base64 | sudo tee /etc/consult-platform/backup.pass >/dev/null
sudo chmod 600 /etc/consult-platform/backup.pass

BACKUP_PASSPHRASE_FILE=/etc/consult-platform/backup.pass bash scripts/backup.sh /srv/backups/consult-platform
```

- 每次一个子目录（UTC 时间戳）：`db.dump.gpg`、`objects.tar.gpg`、`manifest.json`（迁移版本、链头、文件大小和 sha256，不含业务内容和密钥）。
- 完成后写审计 `backup.create`（时间戳、链头编号、字节数）。
- 超过 `BACKUP_KEEP_DAYS`（`.env`，默认 30）天的子目录自动删除。
- 定时：部署机 crontab（以能执行 docker 的运维账号），每天 02:00：
  `0 2 * * * cd /srv/consult-platform && BACKUP_PASSPHRASE_FILE=/etc/consult-platform/backup.pass bash scripts/backup.sh /srv/backups/consult-platform >> /var/log/consult-backup.log 2>&1`
- 异地或离线副本：把备份根目录同步到公司备份系统（文件已加密，可直接推送），公司备份系统的保留期也不超过 `BACKUP_KEEP_DAYS`。

## 3. 备份保留期与客户删除承诺

项目资料删除（M4 ②）只删除在线数据；此前的备份里仍有副本，随备份轮换清除。删除记录写明“备份中的副本最迟清除日”= 删除完成日 + `BACKUP_KEEP_DAYS`（`backups_purged_by`），与《客户数据告知模板与合同条款》法务审核事项 4 “备份在下一轮覆盖周期内清除”对应。改 `BACKUP_KEEP_DAYS` 时同步公司备份系统的保留期，不要超过合同约定的最短保留期。

不从备份里单独删除某个项目：备份整体加密、整体过期。恢复备份后，恢复点之后已删除的项目会重新出现，**恢复后要立即重新执行这段时间内已确认的删除**（`python -m app.cli deletion-report --all` 对照恢复前的删除记录）。

## 4. 恢复

```bash
BACKUP_PASSPHRASE_FILE=/etc/consult-platform/backup.pass bash scripts/restore.sh /srv/backups/consult-platform/20270110T020000Z
```

1. 核对清单里各文件的 sha256，解密到临时目录（口令不对在这一步失败，不影响运行中的服务）。
2. 要求输入备份目录名确认（非交互用 `RESTORE_CONFIRM=<目录名>`）。
3. 停 backend、worker、frontend；删库重建并 `pg_restore`；停 MinIO，清空数据卷后解包；启动（后端自动升级迁移）。
4. `verify-audit --expect-head <备份时的链头>`：链完整且备份时的链头仍在链上，写审计 `backup.restore`。
5. 运行 `bash scripts/smoke_test.sh`；按第 3 节补做恢复点之后已确认的删除；通知所有人重新登录。

## 5. 恢复演练

- CI 每次都跑一遍：备份 → 新建项目 → 错误口令恢复被拒且服务不受影响 → 正确口令恢复 → 新建的项目消失、对象数一致、只有恢复这一条备份审计 → 冒烟通过。
- 测试机和生产每季度演练一次，记录：备份时间戳、备份大小、恢复用时（脚本输出）、`verify-audit` 结果、冒烟结果、问题。RTO 4 小时以内为通过。演练记录写进测试 PR 评论或运维记录，不附备份文件、口令。
