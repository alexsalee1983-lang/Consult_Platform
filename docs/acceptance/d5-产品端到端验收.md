# 二期 D 线 ⑤：四个新产品端到端验收（测试环境）

对象：IRE、DSM、ISO、NSG。素材在 `knowledge/virtual-clients/<产品>/`（全部虚构，只用虚拟代号）。
前提：四个产品及其模块的配置已是 `status: ready`（公开方法版 v0，待专家复核，#204、#205）；不需要临时改状态，只确认 main 上的配置是 ready。

## 一、准备（只在测试环境，不提交）

1. 确认测试环境检出的是最新 main，`products/{ire,dsm,iso,nsg}.yaml` 和它们挂的 `modules/*.yaml` 的 `status` 都是 `ready`，然后 `docker compose up -d --build backend worker`。
2. 用模拟模型（`--profile mock-llm`）或测试环境已接的外部模型（`LLM_EXTERNAL=true`，只处理虚拟数据）。
3. 知识库里至少有依据原文和公开知识（测试环境已有的即可）。

## 二、每个产品执行一遍

以 IRE 为例，其余三个把代号和目录换掉。项目代号用测试库里没用过的虚拟代号（如 MFG-C1、BANK-A1、GRID-B1、MFG-C2）。

1. 立项：`python -m app.cli create-project --code MFG-C1 --tier standard --manager <项目经理> --product IRE --industry 制造`；
   检查 D1～D8 都建好、各交付件大纲与 `products/ire.yaml` 的 `outline` 一致（依赖 #196）。
2. 录入素材（顾问账号，网页或接口）：
   - `notes-*.md` → `POST /api/projects/{code}/notes`，`kind=interview`，`interviewee_role` 取文件头的受访者角色；
   - `obs-*.md` → 同上，`kind=observation`；
   - `doc-*.txt` → `POST /api/projects/{code}/documents` 上传；
   - 全部 201，编号 I-xx / O-xx / D-xx 连续；没有被机密级检测拦下。
3. 发起交付链：`POST /api/projects/{code}/runs` → 202；等运行结束或停在确认卡。
   - 每一步的 Agent 与 `chain` 一致；有确认卡的，顾问处理后自动继续。
4. 检查产出：
   - D3 按产品评估域分章、每条带证据编号；IRE 有事件时间线；
   - 差距分析只用“差距分析、符合性初判、整改建议”，没有测评、认证、成熟度等级结论；DSM 不出成熟度分数；
   - 依据引用能在依据库里找到，找不到的标【依据待核实】；
   - D4 / D5 / D6 / D7 / D8（按产品 chain 写的那几份）有正文，章节和大纲一致。
5. 质量评审：对 D4 发起评审，结论能出；平台规则阻断（资质边界用语、来源核对不上）为 0。
   D3 / D4 / D5 / D7 门禁通过后仍是“起草中”（L2，#192 已合并）。
6. 导出 D4 Word，页眉为草稿、脚注带来源。
7. 留痕：审计里没有素材正文；`docker compose logs backend worker` 里搜素材里的独特短语（如“生产计划系统”“营销名单”“调度支持系统”“工控”）为 0。

## 三、回报

PR 评论按《测试交接规范》写：首行写环境；每个产品一张表（立项、录入、运行、产出、评审、导出、留痕各一行，结论 + 关键编号）；产出质量问题写题目和章节，不贴长段正文。
测完把 `products/`、`modules/` 的临时改动还原（`git checkout -- products modules`）。
