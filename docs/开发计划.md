# 安全咨询 Agent 平台 · 代码开发计划

> 本文件与 claude.ai 上的《安全咨询 Agent 平台 · 代码开发计划》同步，2026-11-07 版。以仓库中的这份为开发依据，计划调整时两边一起改。

## 一、目标与范围

**目标：2027 年 1 月 15 日交付第一个可用版本。** 顾问能在平台上用知识库和 Agent 组，按标准档完成一个 SOC 运营体系设计项目的主要交付件；严格档的摘要卡流程能跑通；平台满足等保第三级的主要技术控制，可以进入定级备案和测评。

里程碑沿用《安全咨询 Agent 平台架构设计》第九节的 M1～M5，每个里程碑是一个两周冲刺，研发线性推进。

**一期包含**：平台底座（登录与权限、项目区与知识区隔离、审计、模型网关）；知识服务（投料、解析、去标识、审批发布、检索）；标准档交付链（纪要与资料上传、交付侧 Agent、确认卡、交付件审阅与 Word 导出）；严格档与删除管理；安全加固。

**一期不包含**：售前角色；出海合规认证、云安全方向；与客户系统的任何对接（平台不接入客户生产网络）；在客户现场运行大模型；GPU 采购；移动端界面。

**与 Agent 两周冲刺（11-09～11-20）的关系**：Agent 冲刺用虚拟客户打磨 Agent 的 md 和黄金样例；代码 S1 同期提供“Agent 运行时”，让这些 md 能直接在平台上试跑。

## 二、当前进度：M0 已完成

M0 可运行骨架（PR #1）：机密级拦截、模型网关（未配置模型时为演示模式）、审计日志（不记原文）、项目 / 交付件 / 待确认接口、暗色版 3 屏界面、PostgreSQL + pgvector、Redis、Nginx、Docker Compose、CI（后端测试、前端构建、整套启动后冒烟测试 7/7 通过）。

与架构设计的偏差：MinIO 社区版官方镜像已于 2026 年 9 月下架，M0 暂未引入对象存储，S2 前定替代方案。

| S3 12-07～12-18 | M3 标准档交付链 | 用虚拟客户在一天内从纪要生成 D4 现状评估初稿；确认卡闭环；Word 导出套用公司模板 |

## 四、各里程碑任务分解

### S1 · M1 平台底座

| 模块 | 内容 | 主要数据表 / 接口 |
|---|---|---|
| 数据库迁移 | 引入 Alembic，把 M0 的自动建表改为版本化迁移脚本 | `alembic/versions` |
| 登录 | 对接公司 SSO（方式待定）；过渡期本地账号 + TOTP 双因素。服务端会话存 Redis，HttpOnly Cookie，30 分钟无操作超时，连续失败锁定 | `users` `sessions`；`/api/auth/login` `/logout` `/me` |
| 角色与三权分立 | 顾问、项目负责人、知识专家、知识管理员、系统管理员、安全审计员。系统管理员看不到业务数据，审计员只读审计 | `roles` `user_roles` |
| 项目隔离 | 项目接口按成员过滤；非成员访问返回 404 | `project_members` |
| Agent 工具授权 | 知识侧 Agent 不能读项目区，交付侧 Agent 不能写知识库；在工具调用层强制检查 | `agent_tool_grants` |
| 审计加固 | 只追加；每条记录含上一条的哈希，篡改可检出；审计员查询界面 | `/api/audit/verify` |
| 模型网关加固 | 用量计量（按人、项目、模型）、超时重试、流式输出、模型可用性检查、假名化开关（默认关） | `llm_usage` |
| Agent 运行时 | 读取 `01_公共规范.md` + 各 Agent md 组装系统提示，注入项目卡；对话存入项目区；对话页可切换 Agent | `agents` `conversations` `messages` |
| 界面 | 登录页、用户与角色管理、审计查询、对话页 Agent 切换 | — |

### S2 · M2 知识服务

| 模块 | 内容 | 主要数据表 / 接口 |
|---|---|---|
| 对象存储 | 按选型结果接入；项目区与知识区分桶、服务端加密 | — |
| 中文分词 | 自建 PostgreSQL 镜像（pgvector + zhparser），建全文索引 | `deploy/postgres/Dockerfile` |
| 后台任务 | Redis 队列 + 独立 worker 容器，处理解析、向量化、删除 | `worker` 服务 |
| 投料与解析 | 上传 Word / PDF / Markdown / 文本；扫描件用 CPU OCR；切分；入口先过机密级拦截 | `uploads` `/api/kb/intake` |
| 去标识 | 知识只收做法：客户名、人名、系统名替换，生成审查报告 | `deid_reports` |
| 知识条目 | 按公共规范第 7 节的元数据字段建模；版本、来源、复审日期 | `kb_items` `kb_versions` `kb_chunks` |
| 向量化 | 优先用公司模型平台的 embedding 接口；没有则在 CPU 上跑小型中文向量模型 | `kb_chunks.embedding` |
| 审批流程 | 草稿 → 待审 → 双人审核 → 已发布 → 待复审 → 下线；冲突提示、版本差异、发布影响 | `kb_reviews` |
| 检索 | 全文 + 向量混合检索（RRF 融合），按服务产品 / 阶段 / 类型过滤，返回 doc_id；作为 Agent 工具 `kb.search` | `/api/kb/search` |
| 界面 | 投料箱、审批队列、知识地图与健康 | — |
| 评测与入库 | 依据查询评测集（问题 → 期望条目）；业界知识批量导入脚本 | `scripts/kb_eval.py` |

### S3 · M3 标准档交付链

| 模块 | 内容 | 主要数据表 / 接口 |
|---|---|---|
| 项目区资料 | 客户资料上传、访谈纪要录入（只写角色）；证据编号 I- / D- / O- | `documents` `evidences` |
| Agent 编排 | LangGraph 流程：咨询师 Agent 协调调研访谈、依据与差距分析、方案设计、报告 Agent；工具 `kb.search` `project.evidence` `confirm.create` | `agent_runs` |
| 确认卡 | Agent 遇到方案取舍、来源冲突、证据不足时暂停并生成卡片，顾问处理后继续 | `confirmations` 扩展 |
| 交付件 | 按章节存储与版本化；来源标注；质量评审 Agent 门禁（阻断 / 重要 / 建议）；签署流程 | `deliverable_sections` `section_versions` `sign_offs` |
| Word 导出 | python-docx 套用公司模板，草稿页眉标记、证据脚注 | `/api/deliverables/{id}/export` |
| 界面 | 交付件审阅页；项目驾驶舱接真实数据 | — |

### S4 · M4 删除与严格档

| 模块 | 内容 | 主要数据表 / 接口 |
|---|---|---|
| 删除管理 | 验收日 + 6 个月到期；提前 30 天提醒；项目负责人人工确认；删除文件、索引、向量、对话；生成可交给客户的删除记录；客户要求时提前删除 | `retention_schedules` `deletion_records` |
| 单文档升级 | 标为“仅现场使用”后拒绝上传和引用 | `documents.local_only` |
| 客户同意记录 | 严格档摘要卡须关联客户书面同意记录才能上传 | `consents` |
| 摘要卡 | 调研访谈 Agent 生成空白摘要卡；上传时规则检查（不得含真名、原话、IP、系统名）；Agent 用占位符起草 | `summary_cards` |
| 现场工具 | 可离线运行的单文件网页：填卡、规则自检、占位符回填（对照表只留现场）、导出加密包 | `field-tool/` |

## 五、代码结构与技术约定

```
backend/app/
  core/        配置、数据库、安全（会话、权限依赖）、审计
  api/         接口层，按领域分文件：auth、projects、kb、deliverables、audit
  models/      数据表
  services/    业务逻辑：guard、gateway、kb、retention
  agents/      Agent 运行时、工具、LangGraph 流程
  workers/     后台任务
backend/alembic/   数据库迁移
agents/            Agent md（从 Agent 组同步，版本随代码管理）
frontend/src/      pages、components、api
field-tool/        严格档现场工具（单文件网页）
deploy/            自建镜像、生产 Compose、运维脚本
scripts/           冒烟测试、知识库评测、批量导入
```

技术约定见仓库根目录 `CLAUDE.md`。

## 六、测试、CI 与验收

| 层次 | 覆盖什么 | 在哪里跑 |
|---|---|---|
| 单元测试 | 机密级规则、网关路由、去标识、删除到期计算等纯逻辑 | 本地 + CI |
| 接口测试 | 每个接口的正常与异常路径；S2 起改用真实 PostgreSQL（pgvector + zhparser）服务容器 | CI |
| 权限矩阵测试 | 角色 × 接口的允许 / 拒绝表逐格断言；Agent × 工具授权同理；每次改权限都要跑 | CI |
| 冒烟测试 | `scripts/smoke_test.sh`，每个里程碑追加对应项目 | CI + 测试机 |
| Agent 评测 | 黄金样例对照、依据查询准确率、“不编造条款号”红线用例；需要真实模型，只在测试机跑 | 测试机 |
| 安全扫描 | 依赖漏洞、镜像漏洞、密钥泄露；S5 补渗透测试 | CI（S1 起） |

合并条件：CI 全绿 → 测试助手在测试机上按 `docs/测试交接规范.md` 测试通过并在 PR 留评论 → 负责人合并。

## 七、开发与部署流程

1. 每个里程碑一个分支（`feat/m1-...`），里程碑内按模块拆成小 PR，一个 PR 只做一件事。
2. 开发助手：写代码和测试 → 推送 → CI 修到全绿 → PR 里写清楚改了什么、怎么测。
3. 测试助手：在测试机上拉分支、启动、测试，结果写成 PR 评论。
4. 负责人合并到 main；每个里程碑验收后打标签 `v0.1`、`v0.2`……，一期可用版本为 `v1.0`。
5. S1 起数据库变更只通过迁移脚本；重大变更前先备份。
6. 测试机只用虚拟客户数据。
7. 每个冲刺第一周周五交付一次可测版本，结束时做里程碑验收。

## 八、待决定与风险

| 待决定 | 选项 | 最晚决定 | 影响 |
|---|---|---|---|
| 公司 SSO 对接方式 | **已定（11-08）：一期用本地账号 + 动态码，不对接 SSO** | — | S1 登录 |
| 公司模型平台接口 | 是否 OpenAI 兼容；推理 / 标准 / 轻量模型名；有无 embedding 接口；并发与上下文长度。**就绪前开发测试可用外部模型（11-08 决策，限虚拟数据）** | 11-18 | S1 网关、S2 向量化 |
| 对象存储 | **已定（11-08）：MinIO，源码自建镜像，代码只用 S3 协议（可更换）** | — | S2 投料 |
| 公司 Word 模板 | 封面、页眉页脚、样式模板文件 | 12-07 | S3 导出 |
| 现场工具形态 | 单文件离线网页（推荐）/ 桌面小程序 | 12-18 | S4 严格档 |

| 风险 | 应对 |
|---|---|
| 单线研发，任一冲刺延期顺延到后面 | S4 留余量；S3 验收是硬关口，延期时先砍非核心界面 |
| CPU 服务器上 OCR 和向量化慢 | 优先用公司模型平台的 embedding；解析走后台队列；OCR 可选 |
| zhparser 需自建数据库镜像 | 构建脚本进仓库，CI 每次构建；备选 pg_jieba |
| 开源组件供应变化（如 MinIO 镜像下架） | 依赖固定版本；关键镜像同步到公司内部镜像仓库 |
| Agent 输出质量不稳定 | 质量门禁 + 人工签署；Agent 评测集随 Agent 冲刺一起建 |
