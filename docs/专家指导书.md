# 人工专家指导书（v1.0）

本书写给平台上**必须由人来做**的环节：顾问、项目经理、项目负责人、知识专家和知识管理员。平台的原则是：Agent 主笔，人负责投料、拍板、审核和署名。平台不会替人做下面这些决定。

读者不需要懂代码。页面名称以“我的项目”“项目驾驶舱”“交付件审阅”“知识审批队列”“知识地图与健康”为准。

---

## 一、先记住的四条

1. **不收机密级内容。** 口令、密钥、可利用的漏洞细节、完整网络拓扑与 IP 规划、业务数据和个人信息样本，两档项目都不收。上传时平台会拦截。被拦截后请删掉这些内容再传，**不要换个写法绕过**。
2. **只写客户代号。** 平台里写 BANK-A 这类代号，不写客户真实名称。访谈纪要只写受访者角色（如“SOC 负责人”），不写姓名。
3. **不出结论性用语。** 不写“通过等保测评”“符合密评要求”“可获得认证”。统一用“差距分析、符合性初判、整改建议”。质量评审会把测评、认证结论用语判为阻断。
4. **你署名就是你负责。** Agent 写的是初稿。签署前，项目经理要对内容负责。

## 二、角色与账号

| 角色 | 做什么 | 关键约束 |
|---|---|---|
| 交付顾问（consultant） | 上传证据、处理确认卡、审改交付件、提交签署 | 只看得到自己参与的项目 |
| 项目经理（项目成员角色 manager） | 调整成员、签署或退回、驳回评审意见、登记验收和客户书面文件 | 每个项目由立项时指定 |
| 项目负责人（project_lead） | 确认删除申请 | 不能确认自己发起的申请 |
| 知识专家（knowledge_expert） | 投料、写条目、内容审核 | 不能审自己写的版本 |
| 知识管理员（knowledge_admin） | 去标识确认、合规审核 | 不能确认自己上传的资料 |

**两人原则**：以下三件事必须由两个人完成，一个账号持有全部角色也不行：

- 去标识确认：上传者以外的人确认
- 知识发布审核：作者以外的人审核
- 删除确认：发起人以外的人确认

人手少时，可以让两个账号都持有上面四个业务角色，日常用一个账号，碰到这三件事时换另一个账号。系统管理员和安全审计员不能兼任业务角色，也看不到业务数据。

## 三、交付侧：一个项目从立项到删除

### 1. 立项（运维用命令行，一期没有网页立项）

立项时必须定档：

- **标准档**：客户资料可以进入平台。
- **严格档**：资料不出客户现场，平台只收客户书面同意后的去标识摘要卡。

定档依据是合同和客户的数据要求（见 `客户数据告知模板与合同条款.md`）。拿不准时按严格档立项。

### 2. 上传证据（顾问）

- 进入平台的是三类证据：客户资料（编号 D-xx）、访谈纪要（I-xx）、现场观察（O-xx）。编号一经分配就不变，也不复用。
- **访谈纪要**：
  - 写受访者角色，不写人名。
  - 记事实和原话要点，不记口令、IP、系统账号。
  - 矛盾、拿不到证据的地方要如实记下，Agent 会据此发“证据不足”卡。
- **仅现场使用**：客户书面通知某份资料只能留在现场时，项目经理在资料上标“仅现场使用”。
  - 要填文号，不写客户名。
  - 标记**不可撤销**。平台会立即删除这份资料的原件和解析结果，以后交付件里不能再引用它。

### 3. 运行交付链和处理确认卡（顾问）

- 在项目驾驶舱发起交付链（标准档 SOC 依次跑第 3 步事实清单、第 4 步差距分析、第 7 步现状评估报告初稿）。同一项目同时只能有一次运行。
- Agent 遇到以下情况会发**确认卡**并停下来等人：方案取舍、来源冲突、证据不足、范围确认。
  - 处理方式：选一个选项，或者写意见。处理后不能改，请想清楚再点。
  - 卡都处理完后，交付链自动继续，你的处理结果会交给后续步骤，同一问题本次运行不会再问。
  - “证据不足”卡的正确处理方法是**补上证据**，不是让 Agent 自己推测。
- 推荐理由不成立时，不要照着推荐选，写明你的意见即可。

### 4. 审改交付件（顾问）

逐章阅读 Agent 初稿，重点看：

- **来源标注**：每条结论后面要有 `[I-01]` `[D-12]` `[O-05]`（严格档为 `[S-02]`）、依据条目或 `[推断]`。
  - 平台把核对不上的编号列为“来源核对不上”，这一条在质量评审里判为阻断。
  - 整章只有推断的，判为重要问题。
- **【依据待核实】**：知识库里没有依据时，Agent 会标这个记号。请对照标准或法规原文核实，再改成正式引用。核实后的依据可以投料进知识库（见第四节）。
- **锋利度**：Agent 容易写出放之四海而皆准的通用话。请检查结论是否针对本客户，写得通用的地方用客户的事实改写。你的每一次改写，都是一次知识投喂。
- 每次保存都会新建一个版本，旧版本保留，可以放心改。

### 5. 质量评审与签署

1. 顾问或项目经理发起**质量评审**。评审由平台规则和质量评审 Agent 一起完成，结论为：通过、修改后通过、不通过。
2. **项目经理可以驳回 Agent 提出的阻断**，但必须写理由，至少 10 个字。理由要具体，例如“该条依据已核对原文第 8.1.3 条，Agent 误判”，不要写“无问题”。平台规则判出的阻断（缺正文、机密级内容、结论用语、来源核对不上）**不能驳回**，只能改正文。
3. 门禁通过后，项目成员提交签署，项目经理签署或退回。退回必须写理由。
4. **签署后只读，一期不能撤销。** 签署前请确认已经通读全文。
5. 导出 Word：未签署的每页页眉标“草稿”。**不要把草稿发给客户。**

### 6. 严格档项目额外要做的

1. 项目经理登记客户书面同意，填文号和签署日期，不写客户名。没有有效同意，就不能上传摘要卡，也不能运行交付链。
2. 在客户现场用**现场工具**（`field-tool/field-tool.html`，离线网页）整理摘要卡：
   - 机构、人员、系统一律用占位符：【客户】【人员1】【系统A】。
   - 不写真名、职务加姓、IP、域名、产品名和版本号，不引用原话。
   - 占位符与真名的对照表只存在加密工作文件里，**只留在现场，不带回来**。
3. 摘要卡要经客户审阅，审阅日期写在卡上。上传时任何一张卡不过检查，整批都会被拒收。
4. 客户书面撤回同意时，项目经理登记撤回。平台会清空摘要卡，以及据摘要卡写成的未签署内容。已签署的交付件保留。

### 7. 验收与删除

- **验收**：项目经理登记验收日和保留月数（默认 6 个月，按合同约定调整），平台算出到期日。
- **到期删除**：平台每小时扫描一次，自动发起到期项目的删除申请，由**项目负责人确认**。
  - 确认时必须选经验回流情况：已回流（填投料编号）、无可回流、客户不同意回流。
  - 回流要在确认前做完：把可复用的做法去标识后投料进知识库。
- **客户要求提前删除**：
  - 项目经理凭客户书面要求发起，填文号，要在 10 个工作日内完成。
  - 由另一位项目负责人确认。
- 删除完成后，删除记录（编号、日期、计数、确认人、回流情况）可以直接交给客户。

## 四、知识侧：怎么把经验变成知识

知识库只收**去标识后的做法**，不收客户原文。原则是：人只投“原料”、做审批，把原料加工成知识条目的工作交给 Agent。

### 1. 投料（知识专家、顾问）

- **投什么**：
  - 公开资料，如标准、法规、行业报告。
  - 公司方法论和模板。
  - 签字终稿里“最好的 20%”：报告、方案、制度、访谈提纲、汇报材料。
- **投之前确认**：这份资料对应客户的保密协议是否允许脱敏复用。不允许的不投。
- **投时填三项**：来源、能否复用、好在哪（一句话）。“好在哪”最有价值，请认真写。
- **不收的文件**：扫描件、加密文件、超大文件，以及含机密级内容的文件。同一文件重复投料会被拒绝。
- 批量入库由运维用 `kb-import` 命令完成，条目文件格式见 `knowledge/` 下的示范。

### 2. 去标识确认（知识管理员，不能是上传者）

去标识分三道：规则词库先替换，脱敏审查 Agent 复查漏网名称，最后由知识管理员**逐项确认**。

确认前请检查以下三点：

1. 机构名、人名、系统名、地名都已替换成占位符。
2. 没有可以反推出客户的组合信息，如“某省唯一一家……”“2025 年某次重大事件”。
3. 留下的是做法和判断规则，不是客户的具体数据。

**确认后，原件和未去标识的解析结果会被删除，不能恢复。** 有疑问就退回，不要先确认再说。

### 3. 发布审核（两人原则）

| 审核 | 谁来审 | 看什么 |
|---|---|---|
| 内容审核 | 知识专家（作者以外） | 做法是否正确、是否可复用；适用条件写清楚了没有；与已有条目是重复、补充、冲突还是替代 |
| 合规审核 | 知识管理员（作者以外） | 去标识是否彻底；来源和复用授权是否清楚；有没有结论性用语 |

- 一个人同时持有两个角色，可以审两项，但都不能审自己写的版本。
- **公开资料单人审核**（开关 `KB_SINGLE_REVIEWER_PUBLIC` 打开时）：作者本人可以审核发布，条目带“单人审核”标记。之后要由作者以外的知识专家**复审确认**，标记才会清除。请定期清理这类标记。
- **冲突的条目**：两条并存，各自写明来源和适用条件，不要直接删掉旧条目。被替代的旧条目标“已替代”，历史版本保留。

### 4. 依据库（L4）要特别小心

- 法规条款、标准条号必须**对照原文**核对：标准号、版本年份、条款号、原文表述。
- 法规标准废止或换版时，旧条目标“已废止”或下线，新版本另建条目。
- 依据条目默认每 6 个月复审一次，其他条目每 12 个月一次。“知识地图与健康”页会列出到期待复审的条目。

### 5. 评测

运维用 `kb-eval` 跑一组固定问题，看检索结果对不对。专家负责维护这组问题：每个领域选 10～20 个顾问真会问的问题，每个问题标出应该命中的条目。检索不到或命中错误时，分两种情况处理：

- 缺内容：补库。
- 有内容但检索不到：改条目的标题、关键词和元数据。

## 五、二期需要专家投入的地方

二期把交付链做成可配置的服务产品（SOC 之后接 ISO 27001 认证准备、等保整改等，见 `二期开发计划.md`）。每增加一个产品，都要专家提供或审定以下内容：

1. **交付件清单**：D1～Dn 各叫什么、属于哪个阶段、哪些交给客户。
2. **评估基线**：能力域、对照的框架和标准。
3. **每一步的任务说明**：Agent 每一步要做什么、不做什么。专家写成大白话即可，开发负责转成配置。
4. **质量门禁**：哪些章节必须有、哪些用语禁止使用、哪些控制项必须覆盖（如 ISO 27001 附录 A 全部控制项）。
5. **黄金样例评审**：按下表评审 Agent 为虚拟客户产出的整套交付件。

| 问题 | 怎么答 |
|---|---|
| 公司的做法和样例不同的地方有哪些？ | 至少列 3 处；如果没有，说明原因 |
| 缺了什么公司一定会做的内容？ | 逐条列出 |
| 哪里写错了，或在客户面前站不住？ | 写清楚所在章节和原因 |
| 换成其他行业（电力、制造）要改哪些地方？ | 逐条列出 |
| 结论 | 采纳 / 修改后采纳 / 推倒重写 |

样例里引用的法规条款一律先标【依据待核实】，专家对照原文确认后才能进入依据库。样例只用虚拟客户，不用真实客户信息。

## 六、出了问题找谁

| 情况 | 找谁 |
|---|---|
| 账号锁定、忘记口令、换手机后动态口令失效 | 系统管理员 |
| 被机密级检测误拦截 | 先自查有没有口令、IP 等内容；确属误拦截，告诉系统管理员是哪一类，**不要转发原文** |
| Agent 输出明显错误、反复犯同一个错 | 记下项目代号、交付件、章节和版本号，交给项目负责人 |
| 客户提出删除、撤回同意、仅现场使用 | 项目经理按第三节操作，书面文件存档在平台以外 |
| 怀疑有客户信息泄露 | 立即报项目负责人和安全审计员 |
