# SOC 咨询 Agent 组开发项目方案

Nov 7, 2026 · @YufenXu

## 一、项目目标与验收

**目标**：到 2026 年 11 月 20 日（2 周），完成 Agent 组开发和业界知识底座入库。Agent 组要能以“Agent 主笔、顾问审核署名”的方式，为一个虚拟客户输出完整的 SOC 运营体系设计交付件（D1～D8）。公司最佳实践和专家输入放到第二阶段，持续迭代进入知识库。

**“独立输出”的定义**：Agent 完成全部起草、检索、检查；人只负责三件事——提供事实（访谈与资料）、做取舍判断、审核签字。对客交付物仍须顾问署名，这是资质边界和保密要求，不会因为 Agent 能力提升而改变。

**验收方式：虚拟客户端到端演示。** 两周内拿不到公司历史项目数据，也来不及组织专家盲评。所以改为用第七节的虚拟城商行作为客户，从“接到需求”一路跑到 D8，全程留痕，由一位资深顾问抽查。历史项目回放和专家盲评放到第二阶段，作为“与公司实践对齐”的验收。

**验收标准（待你确认数值）**

| 指标 | 目标 | 怎么量 |
| --- | --- | --- |
| 交付件覆盖 | D1～D8 全部产出 | 对照第三节清单 |
| 链路无断点 | 7 步全部跑通，交接信息完整 | 运行记录 |
| 阻断问题 | 0 项（依据错误、保密残留、资质用语） | 质量评审 Agent + 顾问抽查 |
| 依据可追溯 | 每条依据都有依据库 ID，待核实项单独列出 | 与依据库比对 |
| 顾问抽查 | 资深顾问抽查 D4、D5、D6，结论为“改一改能交给客户” | 抽查记录 |

## 二、关键判断与调整

11 月 7 日调整：工期压缩到 2 周；先整理业界知识；专业判断交给 Agent 综合做出；公司实践和专家输入后置。调整后的判断如下。

1. **知识库建设 Agent 仍是第一步，但工作内容变了。** 两周内它主要整理业界公开知识（法规标准、SOC 能力框架、运营方法），而不是盘点公司资料。公司资料的盘点、脱敏、入库放到第二阶段。
2. **专业判断交给 Agent 综合做出：采纳，加三条护栏。** Agent 综合法规标准、业界框架和已入库的公司实践来判断。护栏一：每个结论标注来源类型（法规标准 / 业界框架 / 公司实践 / 模型推断）。护栏二：法规条款只能引用依据库。护栏三：对客交付物仍由顾问审核署名。公司实践入库后，作为来源之一参与判断，不再自动压过其他来源；来源之间冲突时，Agent 要把分歧列出来，由顾问决定。
3. **黄金样例由 Agent 链路自己产出。** 验收时 Agent 组为虚拟客户产出的 D1～D8，经顾问抽查修订后，就是第一版黄金样例。专家评审放到第二阶段。
4. **运行在白名单大模型：采纳。** 两周内只处理公开知识和虚拟客户，不涉及真实客户资料，所以法务确认不再阻塞这一阶段。但第二阶段导入公司资料前，必须拿到书面确认。
5. **新增方案设计 Agent：保留这条建议。** SOC 设计方案是最核心的专业判断，需要专门的 Agent，不能由报告 Agent 顺带完成。

## 三、SOC 交付件包定义

“一套完整的 SOC 咨询交付件”定为以下 8 类，这也是回放验收的清单。

| # | 交付件 | 项目阶段 | 主笔 Agent | 质量门禁重点 |
| --- | --- | --- | --- | --- |
| D1 | 项目启动包：范围确认单、WBS、启动会材料 | 启动 | 项目交付管理 | 不包含项与资质边界写清 |
| D2 | 调研包：资料清单、6 类角色访谈提纲 | 调研 | 调研访谈 | 每个问题可追溯到评估项 |
| D3 | 事实清单：访谈纪要整理，带证据编号 | 调研 | 调研访谈 | 事实与判断分开，敏感表态剔除 |
| D4 | SOC 现状评估与差距分析报告 | 分析 | 依据与差距分析 → 报告与汇报 | 每条差距有证据、依据和业务影响 |
| D5 | SOC 运营体系设计方案：组织与人员、运营流程、告警分级、平台与数据源、度量指标 | 设计 | **方案设计（新增）** → 报告与汇报 | 与客户人力和现有工具匹配 |
| D6 | 制度文件包：安全事件分级与响应管理办法、安全监测与告警处置规程、值班管理规程，及配套表单 | 设计 | 制度起草 | 可落地，四件套齐全 |
| D7 | 实施路线图：短期 / 中期 / 长期，含资源与依赖 | 设计 | 方案设计 → 报告与汇报 | 建议四要素齐全 |
| D8 | 高层汇报材料 | 汇报 | 报告与汇报 | 结论先行，预判挑战 |

范围仍按决策记录：聚焦本地数据中心和网络环境，不含云安全运营。

## 四、人与 Agent 的分工

**原则：Agent 负责起草、检索、检查、整理；人负责获取事实、做取舍、对外沟通、签字和审批知识入库。** 凡是需要见客户、承担责任或判断“公司到底怎么做”的事，都在人这边。

**项目角色**

| 角色 | 由谁担任 | 每月投入 | 职责 |
| --- | --- | --- | --- |
| 项目负责人 | 你 | 待定 | 目标、范围、验收；协调专家和法务 |
| 知识库专人 | 已指定 | 约 10 人天 | 操作知识库建设和脱敏审查 Agent；平台配置；维护评测集 |
| SOC 专家负责人 | **待定** | 第二阶段起 5～8 人天 | 提供最佳实践；评审黄金样例；审批入库；盲评验收 |
| 回放顾问 | **待定**（两周内担任抽查顾问） | 3～5 人天 | 按真实流程驱动 Agent 链路，扮演“审核署名”的顾问 |
| 法务 / 保密 | 法务部门 | 按需 | 三项合规确认（见第十节） |
| 平台管理员 | IT | 按需 | 内部智能体平台、知识集合、权限 |

## 五、SOC 交付链：端到端流程

每一步都是“人给输入和取舍 → Agent 起草 → 质量评审 → 进入下一步”。只有第 3 步“访谈客户”完全由人完成，Agent 只做之后的纪要整理。

下表是每一步的输入契约。**带 \* 的输入缺失时，Agent 必须先问，不得猜测或自行补全。**

| 步骤 | Agent | 必需输入 | 输出 | 人工动作 | 交给 |
| --- | --- | --- | --- | --- | --- |
| 1 启动 | 项目交付管理 | 合同范围\*、客户画像\*、WBS 模板、项目卡模板 | D1 启动包、项目卡 | 填项目卡；确认范围和不包含项 | 全部交付 Agent |
| 2 调研准备 | 调研访谈 | 项目卡\*、SOC 能力评估框架\*、访谈提纲模板 | D2 资料清单、6 类角色访谈提纲（内部版 + 客户版） | 确认对象和排期；把客户版发给客户 | 顾问 |
| 3 调研执行 | 调研访谈 | 访谈转写稿或笔记\*、客户提供的资料\* | D3 事实清单（证据编号 I-xx-xx / D-xx）、待补证据、矛盾点 | **访谈客户、收集资料**；补证 | 依据与差距分析 |

| 6 制度起草 | 制度起草 | 目标运营模型\*、客户实际部门\*、已有制度清单\*、制度母版 | D6 制度包 + 四件套 + 落地风险提示 | 确认部门名称和执行可行性 | 质量评审 |
| 7 成稿 | 报告与汇报 | 差距分析表\*、目标运营模型\*、读者和用途\* | D4、D5、D7、D8 成稿 | 确认结论；审核署名 | 客户 |
| 每步之后 | 质量评审与异议应答 | 当步产出\*、项目卡\*、质量检查清单 | 评审意见（阻断 / 重要 / 建议）、挑战预判 | 处理阻断项 | 回到当步 Agent 或下一步 |

## 六、知识底座：SOC 链路需要什么

两周内的知识底座全部来自业界公开知识，由知识库建设 Agent 整理、顾问抽查后发布。第 1 周周五（11 月 13 日）必须可用，否则第 2 周的交付链没有东西可检索。

| 层级 | 内容 | 两周内数量 | 业界来源 | 谁用 |
| --- | --- | --- | --- | --- |
| L1 | 写作规范、质量检查清单、术语表、项目卡模板 | 各 1 份 | 《01\_公共规范》 | 全部交付 Agent |
| L2 | SOC 服务说明、WBS 与排期模板 | 各 1 份 | 业界咨询实践整理 | 项目交付管理 |
| L2 | 资料清单、6 类角色访谈提纲 | 7 份 | 业界咨询实践整理 | 调研访谈 |
| L2 | SOC 能力评估框架（评估项 + 成熟度分级） | 1 份 | 参考 SOC-CMM、NIST CSF 2.0 的检测与响应职能、等保 2.0 安全管理中心要求，自行整理 | 依据与差距分析 |
| L2 | SOC 设计方法：组织与人员、运营流程、告警分级、平台与数据源、度量指标 | 5 份 | 参考 NIST SP 800-61 事件响应指南、MITRE ATT&CK 覆盖度方法、业界人力测算方法 | 方案设计 |
| L2 | 制度母版：3 份办法 / 规程 + 配套表单 | 3 套 | 按业界实践起草，不等内部制度授权 | 制度起草 |
| L4 | SOC 相关依据：监测预警、事件处置、等保 2.0 安全管理中心、银行业监管要求 | 30～50 条 | 法规标准公开文本，以“要点转述 + 出处”入库 | 依据与差距分析、制度起草 |
| L5 | SOC 高频客户异议与应答 | 30 条 | Agent 起草，顾问抽查 | 质量评审 |

**标准原文的版权**：国家推荐性标准和 ISO 标准的原文受版权保护。知识库里以“要点转述 + 条款出处”为主；需要收录原文的，只在公司已购买的授权范围内使用。

**第二阶段（公司实践接入）需要专家提供的材料**

- [ ] 近 3 年做过的 SOC 项目清单（项目、行业、规模、是否签字终稿），用于选回放项目和挑最佳实践
- [ ] 每个项目“最好的 20%”：终稿报告、设计方案、制度、访谈提纲、汇报材料
- [ ] 公司自己的 SOC 方法论材料（如有）：评估框架、人力测算方法、告警分级标准
- [ ] 每个文件对应客户的保密协议是否允许脱敏复用
- [ ] 准备作为制度母版的公司内部制度，以及法务授权编号

## 七、黄金样例计划

两周方案里不再单独起草一套黄金样例，而是让 Agent 链路为虚拟客户产出 D1～D8，经顾问抽查修订后，作为第一版黄金样例。8 份交付件共用同一个虚拟客户，数字、部门和结论前后一致，本身就是一个“标准项目”的示范。

**虚拟客户（建议，待你确认）**：某城市商业银行，员工约 3000 人，本地两地三中心，信息科技部约 150 人，安全团队 12 人，现有 SOC 6 人、白天值守、无 7×24，已部署 SIEM 但告警量大、误报高；适用等保 2.0 第三级和银行业监管要求。选银行是因为它是你们的主要客户，监管要求也最完整。

| 交付件 | 产出方式 | 完成日期 |
| --- | --- | --- |
| D1～D3 启动包、调研包、事实清单 | 交付链第 1～3 步；访谈纪要来自模拟访谈 | 2026-11-17 |
| D4、D5 现状评估与设计方案 | 交付链第 4～5 步 | 2026-11-18 |
| D6、D7 制度包与路线图 | 交付链第 6～7 步 | 2026-11-19 |
| D8 高层汇报 + 全套顾问抽查 | 交付链收尾 | 2026-11-20 |

**模拟访谈是关键。** 虚拟客户没有真人可以访谈，所以由一个独立的会话扮演 CISO、SOC 负责人等 6 个角色，生成访谈纪要。纪要里要刻意埋入矛盾点、证据不足项和不配合的回答，用来检验调研和差距分析 Agent 能不能识别出来。

**专家评审表（第二阶段对齐公司实践时使用）**

1. 公司的做法与这份样例不同的地方有哪些？（至少列 3 处，没有就说明为什么）
2. 缺了什么公司一定会做的内容？
3. 哪里写错了，或者在银行客户面前站不住？
4. 行业差异：换成电力或制造客户，哪些地方要改？
5. 结论：采纳 / 修改后采纳 / 推倒重写

**约束**：样例中引用的法规条款一律标【依据待核实】，由专家对照原文确认后才能进入 L4。样例不使用任何真实客户的信息。

## 九、项目治理

两周按冲刺来管：每天站会，每天跑评测，每个问题都归到具体原因。

- **每日站会（15 分钟）**：项目负责人、知识库专人、抽查顾问参加。只看三样：昨天完成了什么、评测分数变化、阻塞问题。
- **评测集**：第 1 天建立，SOC 方向 30 道题，覆盖依据查询、差距判定、制度条款、异议应答。每次改 md、换语料都全量跑一遍；改动后分数下降的，回退。
- **问题清单分四类**，因为每类找不同的人修：

| 问题类型 | 典型表现 | 谁修 |
| --- | --- | --- |
| md 问题 | 流程漏步、输出格式不稳定、越权回答 | 知识库专人改 md |
| 语料问题 | 检索不到、检索到过期或错误内容 | 知识库专人 + SOC 专家补库 |
| 模型问题 | 推理错误、长文本遗漏、编造条款 | 换模型、拆分任务或加规则约束 |
| 流程问题 | 交接时输入缺失、人工环节卡住 | 项目负责人调整流程 |

- **变更控制**：《01\_公共规范》和各 Agent md 放进版本库，改动须写变更说明，评测通过后才发布到平台。公共规范的修改须项目负责人批准。

## 十、风险与待决策事项

两周方案的最大风险是“看起来对、但很通用”：没有专家把关，Agent 综合判断容易产出放之四海而皆准的方案，在客户面前缺少锋利度。顾问抽查要专门盯这一点。

| 风险 | 后果 | 应对 | 截止 |
| --- | --- | --- | --- |
| 产出通用、缺少针对性 | 顾问抽查认为“交不出去” | 虚拟客户设定足够具体；评审维度加一条“换个客户是否同样成立” | 持续 |
| 依据条款编造或过期 | 在客户面前失去专业信誉 | 依据只从 L4 引用；30～50 条依据由一位顾问对照原文核对 | 2026-11-13 |
| 内部平台能力不足 | 链路靠人工复制交接，两周跑不完 | 第 1 天确认平台能力；不支持互调则用交接卡 | 2026-11-09 |
| 抽查顾问没有时间 | 无法验收 | 第 1 天指定一位资深顾问，第 2 周预留 2 天 | 2026-11-09 |
| 标准原文版权 | 合规风险 | 以要点转述入库；原文只在已购授权范围内使用 | 2026-11-13 |
| 第二阶段导入真实资料未获授权 | 公司实践无法接入 | 本周提交法务三问，不阻塞两周冲刺 | 2026-11-13 提交 |

**法务三问**

1. 未脱敏的客户资料能否发送到公司白名单大模型处理？
2. 主要客户（尤其银行）的合同，是否限制使用第三方云服务或 AI 处理客户资料？
3. 公司内部制度改造成咨询母版并对外使用，需要什么授权？

## 十一、最终形态：Agent 工作台与人机协作

最终形态是一个“咨询项目工作台”：顾问按项目开展工作，Agent 在后台按交付链分工，人在关键节点确认。两周内不做定制界面，直接用内部智能体平台验证链路；工作台界面建议在第二阶段立项。

**要不要做界面**

- **两周内：不做。** 内部平台的对话界面加上交接卡，足够验证 Agent 链路能不能跑通。
- **第二阶段：做。** 对话界面装不下咨询项目的结构：项目卡、阶段、交付件版本、证据编号、评审意见、待确认事项。这些散落在聊天记录里，顾问要来回翻找，又回到了“反复沟通”的老问题。

**工作台大概的样子**

【图示（见 claude.ai 原文档）： 咨询项目工作台 · 线框示意】

顶部是项目和阶段进度；左栏是 D1～D8 及其状态；中间像文档一样可以直接改，每段结论旁边挂着依据、证据和来源类型；右栏上半部分和 Agent 对话，下半部分是等顾问拍板的确认卡。

**人和 Agent 的四种互动方式**

1. **对话**：顾问在右侧面板说“准备 BANK-A 的访谈”，咨询师 Agent 分派给调研访谈 Agent。
2. **流程推进**：一个阶段的交付件签字后，系统自动触发下一步的 Agent，产出进入“待确认”。
3. **批注**：顾问直接在交付件上批注“这里太通用，结合银行业监管要求”，对应的 Agent 按批注修改，生成新版本。
4. **确认卡**：Agent 遇到需要判断的事（方案取舍、来源冲突、证据不足），不自己拍板，而是推给顾问一张确认卡，附上建议和理由。这是“专业判断交给 Agent 综合做出”和“顾问负责签字”之间的连接点。

**从接到客户需求到最终输出**

【图示（见 claude.ai 原文档）： 从接到需求到验收 · 客户 / 顾问 / Agent / 门禁四条泳道】

人在整个项目里只做三类事：见客户（访谈、汇报、评审会）、做取舍（范围、基线、方案）、签字。起草、整理、检索和检查都由 Agent 完成，每份交付物出门前都要过质量评审。图中的周数是一个 12 周项目的示意，实际项目在 3～6 个月之间。

## 十二、知识库运营：界面与人机协作

第十一节的工作台面向交付顾问。知识库需要另一个界面——**知识运营台**，面向知识库专人和专家。核心原则是：**人只投“原料”和做审批，把原料加工成知识条目的活全部交给 Agent。** 专家的时间是整件事最稀缺的资源，每次投喂要按分钟算，而不是按天算。

**谁在哪个界面做什么**

| 角色 | 在哪里 | 做什么 |
| --- | --- | --- |
| 知识库专人 | 知识运营台（全部视图） | 盯流水线、处理退回、看知识地图和健康看板 |
| 专家 | 知识运营台（审批队列、萃取对话、我的贡献） | 投料、接受萃取、审批自己领域的条目 |
| 交付顾问 | 不进运营台，在工作台里完成 | 顺手投料、反馈“有错 / 过时”、确认改稿是否入库 |
| 知识库建设 Agent | 后台 | 加工、萃取提问、冲突检测、结项沉淀、订阅更新 |
| 脱敏审查 Agent | 后台 | 入库门禁 |

**人怎么“喂”：六个入口**

| 入口 | 谁喂 | 什么时候 | 人要做的 | Agent 做的 |
| --- | --- | --- | --- | --- |
| 投料箱 | 专家、顾问 | 随时 | 拖入文件，填 3 项：来源、能否复用、好在哪（一句话） | 识别类型、拆分、模板化、补元数据、送脱敏 |
| 萃取对话 | 专家 | 每次 20～30 分钟，可以用语音 | 回答 Agent 的提问 | 按主题追问判断规则和反例，整理成条目 |
| 交付中修改 | 顾问 | 在工作台改稿时 | 点一下“要不要入库”的确认卡 | 捕捉顾问对 Agent 草稿的实质修改，判断是否通用 |
| 使用反馈 | 顾问 | 用到某条知识时 | 点“有用 / 有错 / 过时”，可附一句话 | 生成纠错工单，定位受影响的条目 |
| 结项沉淀 | 项目经理 | 项目结项时（流程强制） | 上传终稿 | 输出结项沉淀单：样例候选、新异议、踩坑 |
| 外部订阅 | 无需人工 | 法规标准发布或废止时 | 确认影响分析 | 比对依据库，列出受影响条目，发起复审 |

六个入口里，**“萃取对话”和“交付中修改”最重要**。前者拿到的是专家脑子里的判断规则，这些东西从来不在文件里；后者不增加任何额外工作，顾问每一次把 Agent 的通用写法改得更对，就是一次投喂。公司实践也在迭代，这两个入口正好能跟上它。

**知识怎么流转**

【图示（见 claude.ai 原文档）： 知识流转 · 6 个入口、加工流水线、使用回流】

**冲突怎么处理**（与“专业判断交给 Agent 综合做出”一致）

- Agent 不自动覆盖。新内容与已有条目比对后归为四类：**重复**（合并，保留更好的版本）、**补充**（追加）、**冲突**（并存，各自标注来源和适用条件，推确认卡给专家）、**替代**（旧条目标“已替代”，保留历史）。
- 很多“冲突”其实是适用条件不同，比如大行和城商行、有无 7×24 值班。所以条目元数据里要增加一个字段：**适用条件**。
- 交付时 Agent 检索到并存的条目，按客户画像匹配适用条件；匹配不上时，把两种做法都列给顾问选。

**知识运营台长什么样**

【图示（见 claude.ai 原文档）： 知识运营台 · 审批队列线框】

审批队列是最重要的视图，设计上参照代码评审：专家看到的是“这次改了什么”和“Agent 的审查意见”，点采纳、修改或退回即可，不用读全文。其他三个视图：

- **投料箱**：每份原料的流水线状态（已接收 → 加工中 → 脱敏中 → 待审批 → 已发布 / 退回）。
- **知识地图**：服务产品 × 交付阶段的覆盖矩阵，标出空白和“顾问问过但答不上”的问题。
- **健康看板**：到期复审、低命中、被反馈有错、依据变更影响。

**让专家愿意喂**：每条知识署贡献者的名字，“我的贡献”里显示被多少份交付物引用过。这个数字可以直接用于绩效，比“请大家积极贡献”管用得多。

**分阶段实现**

- **两周内**：不做界面。投料用一个共享文件夹，加上在平台上和知识库建设 Agent 对话；审批用一张审批表（条目、来源、冲突、结论）；萃取对话用知识库建设 Agent 的模式 C 直接跑。
- **第二阶段**：知识运营台和顾问工作台做成同一个应用的两个模式（交付 / 知识），共用确认卡和条目卡。“交付中修改”这个入口只有在工作台上线后才能实现。
- **需要同步修改的文件**：知识库建设 Agent 的 md 要增加三个模式（萃取对话、修改捕捉、外部订阅）和冲突检测规则；《01\_公共规范》的元数据要增加“来源类型”和“适用条件”两个字段。
