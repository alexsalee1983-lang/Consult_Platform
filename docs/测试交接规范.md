# 测试交接规范

测试助手（测试机上的 Claude Code）收到“测试 PR #N”或“测试”时，按本规范执行，并把结果写成该 PR 的评论。

测试机（2026-11-18 起，决策记录同日）：高配电脑，同时跑四套测试环境（A、B 起，C、D 为 2026-11-18 追加），四个 PR 可以并行测；再加要先报资源、经负责人同意。

| 环境 | 目录 | 端口 | 默认测 |
|---|---|---|---|
| A | `~/consult-platform` | 8180 / 8181 / 8182 | 开发线 1 的 PR |
| B | `~/cp-test-b` | 8280 / 8281 / 8282 | 开发线 2 的 PR |
| C | `~/cp-test-c` | 8380 / 8381 / 8382 | 开发线 1 的第二路（如知识区、向量评测类 PR） |
| D | `~/cp-test-d` | 8480 / 8481 / 8482 | 开发线 2 的第二路 |

派单时写明用哪套，PR 评论首行写明在哪套测的；各套的数据库和数据卷独立，一套里的数据不影响另一套。冒烟测试带上地址：`bash scripts/smoke_test.sh http://localhost:<WEB_PORT>`。
原 Ubuntu 测试机改为专家试用机，只跟 main，不再测 PR。

## 0. 任务从哪来（PR 标签，2026-11-11 起）

开发助手和测试助手不直接通信，负责人也不再转贴说明和结果：**GitHub 的 PR 就是信箱，PR 标签表示轮到谁**。

| 标签 | 意思 | 谁接手 |
|---|---|---|
| `待测试` | 开发助手已写好测试说明 | 测试助手 |
| `测试未通过` | 测试评论里有要修的问题 | 开发助手 |
| `测试通过` | 可以合并 | 负责人（只有负责人决定合并） |
| `攒批评测` | md/评测题类 PR，CI 绿后挂起，等批次统一评测 | 统筹（凑批） |

- 自动调度（2026-11-23 起，负责人同意）：测试机用 `scripts/pr_test_runner.py`（cron 每 15 分钟）按 `待测试` 标签领单，每个 PR 在空闲环境起一个一次性 `claude -p` 会话，测完写评论、换标签即结束；群会话只收一行结论，不在群会话里跑测试。派单只靠打标签，不再 @ 测试助手。
- 测试助手收到“测试”：`gh pr list --label 待测试` 找任务。测试说明以 PR 描述“怎么测”为准；PR 上有标题为“复核说明”的评论时，以**最新一条**复核说明为准（只测里面列的项）。
- 测完发评论后换标签：`gh pr edit <N> --remove-label 待测试 --add-label 测试通过`（或 `测试未通过`）。
- 叠加的 PR（一个 PR 的目标分支是另一个 PR 的分支）：复核说明会写明在哪个分支上一次测完几个 PR；每个 PR 仍各发一条评论、各换标签。
- 开发助手收到“看测试结果”：`gh pr list --label 测试未通过` 和 `--label 测试通过`；修完推送后发“复核说明”评论，标签改回 `待测试`。

## 1. 准备

```bash
cd ~/consult-platform            # 环境 A；B、C、D 为 ~/cp-test-b、~/cp-test-c、~/cp-test-d
git fetch origin
git checkout <PR 的分支> && git pull
cat .env >/dev/null || cp .env.example .env   # 首次才需要
```

- 从 M1 登录功能起，测试机 `.env` 必须有：`APP_ENV=test`、`COOKIE_SECURE=false`（测试机用 http 访问）、测试账号 `TEST_ACCOUNT_USERNAME / TEST_ACCOUNT_PASSWORD / TEST_ACCOUNT_TOTP_SECRET`（自己生成，见 `.env.example`）。冒烟测试用这个账号登录；在浏览器里登录时，把 TOTP 密钥加进手机认证器，或用 `python3 -c "import base64,hmac,hashlib,struct,time,sys;..."` 现算（`scripts/smoke_test.sh` 里有现成函数）。
- 开测前核对环境干净（2026-11-22 起）：`git rev-parse --short HEAD` 与 PR 的 HEAD 一致，`git status --porcelain` 为空；不一致或有本地改动先 `git stash` 或重新检出，结论里写明“环境干净”。带本地改动测出的结论无效。
- 读 PR 描述中的“怎么测”。
- PR 涉及数据库迁移时，先备份：`docker compose exec postgres pg_dump -U consult consult > ~/backup_$(date +%F_%H%M).sql`

## 2. 执行

1. `docker compose up -d --build`，等 `docker compose ps` 中 backend 显示 healthy（最多 5 分钟）。不要只重建 backend：worker 用同一份后端代码，后台任务处理器（解析、评审、删除等）在 worker 里，只重建单个服务时写 `docker compose up -d --build backend worker`。测试机端口被其他服务占用时，在 `.env` 设 `WEB_PORT`、`BACKEND_DEBUG_PORT`（例如 18080、18000），PR 描述里的 `8080`、`127.0.0.1:8000` 换成对应端口；冒烟测试带上地址：`bash scripts/smoke_test.sh http://localhost:<WEB_PORT>`。
2. `bash scripts/smoke_test.sh`，记录通过 / 失败项数。
3. 按 PR 描述“怎么测”逐项执行，每项记录结果。
   - **控制耗时（#44 测试用了近 2 小时，2026-11-12 定）**：涉及大模型的测试项，PR 描述会标明“需真实模型”还是“模拟模型即可”。签署、退回、权限、只读、状态流转这类流程项用模拟模型（`--profile mock-llm`）或 PR 附的现成素材测，真实模型只跑 PR 指定的那一两次，确认输出能解析。
   - PR 附了测试素材（已知能通过、已知会失败的正文等）就直接粘贴使用，不要自己另写。
   - 不要为了让 Agent 满意反复改内容：同一项试两次还达不到预期，记下现象（结论、计数、Agent 的主要意见）报告出来，接着测下一项；需要的话由开发助手补素材。
4. 本 PR 对应的里程碑验收项（见 `docs/开发计划.md` 第三节），能测的逐条测。
5. 数据保护检查（每次都做）：
   - 发一条含 IP 和口令的对话，应被拦截（返回 422）。
   - 查 `/api/audit`，确认日志里没有刚才发送的原文。
   - 从 M1 起：用非项目成员账号访问项目，应返回 404。测试账号是 BANK-A 项目经理、MFG-C 成员，故意不在 GRID-B，冒烟测试已覆盖；另可用 `python -m app.cli` 建一个不在任何项目里的顾问账号手工验证。
   - 从 M1 审计哈希链起：`docker compose exec backend python -m app.cli verify-audit` 结果为“完整”。
   - 从 M1 起：系统管理员、安全审计员账号看不到任何项目（接口 403，页面显示“没有业务数据访问权限”）。

## 3. 回报格式（PR 评论）

~~~markdown
## 测试结果：通过 / 不通过

- 测试机：<主机名>，提交：<git rev-parse --short HEAD>，环境干净：是 / 否
- 冒烟测试：通过 X 项，失败 Y 项
- 数据保护检查：通过 / 不通过

| # | 测试项 | 结果 | 说明 |
|---|---|---|---|
| 1 | …… | 通过 / 失败 | …… |

### 失败详情（如有）
- 复现步骤：……
- 相关日志（最多 50 行，**不得包含任何真实客户信息或密钥**）：
  ```
  docker compose logs --no-color backend | tail -50
  ```
~~~

发评论：`gh pr comment <N> --body-file result.md`，然后按第 0 节换标签。

## 4. 注意

- 开发助手写 PR“怎么测”时：涉及大模型的项注明“需真实模型 / 模拟模型即可”；需要特定模型结果才能往下走的（例如评审阻断为 0 才能测签署），在 PR 里附上已知能通过的测试素材，或给出不依赖模型结果的走法。

- 测试机只用虚拟客户数据；接入公司模型后，测试对话里也不得出现真实客户信息。
- 不要修改代码、不要推送；发现问题只回报，由开发助手修复。
- `.env` 中的模型密钥只留在测试机，不出现在评论和日志里。
- 开测前确认 SecAssess 靶场的 `boot-start.sh` 没在运行（它会停启本平台的容器，网页 502）；测试中出现 502，等全部服务 healthy 后重测，期间结果作废。
- 测试结束保持服务运行，便于负责人在浏览器里查看；需要清空数据时先问负责人（`docker compose down -v` 会删除所有数据）。

## 5. CI 和测试机怎么分工（2026-11-20 起）

测试机只有一台，是最容易卡住的一环，所以只让它做 CI 做不了的事。
- **CI 能覆盖的不派测试机**：ruff、pytest（SQLite 和 PostgreSQL）、前端构建、镜像漏洞扫描都由 CI 跑。只改这些就能验证的 PR（纯文档、纯单元测试能覆盖的逻辑、评测题格式），CI 绿即可，不打 `待测试`。
- **真模型评测按多轮判定**（2026-11-22 起）：每题至少跑 3 轮，按多数判定通过与否，结论写出每题各轮结果；红线题一轮失败即不通过。
- **真模型回归不进 CI**（三期 C8）：CI 只跑评测门（`agent-eval-lint`：格式、红线、资质用语）和模拟模型逐题跑通（`tests/test_eval_gate.py`），不连任何真模型。真模型 agent-eval 由测试机攒批跑：改 md、换模型的 PR 攒到一批，一批跑一次 3 轮，不重复跑。命令（后端容器里，`<用户>` 为测试账号）：

  ```bash
  for i in 1 2 3; do
    docker compose exec -T backend python -m app.cli agent-eval /srv/knowledge/eval/agents --as <用户> --out /tmp/ae-r$i.json || true
  done
  docker compose exec -T backend python -m app.cli agent-eval-majority /tmp/ae-r1.json /tmp/ae-r2.json /tmp/ae-r3.json
  ```

  `agent-eval-majority` 每题一行“题号 各轮结果 结论”，红线题（或任一轮出现资质边界用语、编造条款号）一轮失败即不通过，全部通过时退出码 0；把这段输出贴进 PR 评论，作为合并条件。评测集随镜像打进 `/srv/knowledge/eval/agents`（backend/Dockerfile）。
- **测试机只做四类事**：Docker 整套运行和冒烟；真实模型的端到端和评测（agent-eval、kb-eval、D1～D8）；浏览器界面；部署、迁移和备份恢复这类运维操作。
- **“怎么测”写成能一键执行的命令**：开发助手把测试机上要跑的步骤写成一段可以直接复制执行的 shell，或放进 `scripts/` 的脚本。每一步都打印“通过 / 不通过”和关键数字，测试助手执行后把输出贴进评论。确实需要人看的（界面、模型输出质量），单独列成“人工核对项”，写明看什么、怎样算通过。
- PR 描述的“怎么测”里，测试机要执行的命令放在标注“测试机命令”的 bash 代码块（块前一行含“测试机命令”），`scripts/pr_test.sh` 自动执行。
- PR 描述写明 `测试机：需要 / 不需要`，不需要的写一句理由，例如“只改文档”或“单元测试已覆盖，见 tests/xxx”。
- **免测 PR 直接合并**（决策记录 2026-11-20）：标为“测试机：不需要”的 PR，CI 全绿后由统筹会话（飞书群会话）直接合并，不打 `待测试`、不等负责人；负责人事后抽查。
- **2026-11-25 起的新划分**（决策记录 2026-11-25，负责人原话：“能不交给测试机的尽量不交”“ci要做好质量把关”）：
  - **必测（派测试机）只剩**：数据库迁移；docker compose、部署脚本改动；真实模型评测；加密与安全机制；里程碑端到端验收。
  - **其余一律 CI 全绿 + 本机验证 + 统筹自审即合并**（含前端界面、纯后端逻辑、权限与数据保护代码的非加密部分、依赖升级），PR 描述写“测试机：不需要”及所属类别，不打 `待测试`。
  - 拿不准按必测。
- **CI 质量门**（四期 质量）：后端 ruff、PostgreSQL 与 SQLite pytest、迁移漂移与往返、红线 2 静态检查（`tests/test_redline_static.py`）、**PR 改动行覆盖率 ≥80%**（diff-cover，全量报告在 artifact `backend-coverage`）；前端 `npm run lint`（ESLint 推荐规则、React Hooks、禁止硬编码颜色）、`npm test`（node --test + Vitest 组件测试，样板 `frontend/src/pages/pages.test.jsx`）、构建；compose 整套冒烟与**浏览器端到端冒烟**（登录 → 我的项目 → BANK-A 驾驶舱、无 console error，失败截图与 trace 在 artifact `e2e-trace`）；安全扫描。改了页面的 PR 照样板补组件测试，改了后端代码的 PR 补测试到改动行覆盖率达标。
- **md 类 PR 攒批评测**（决策记录 2026-11-23）：只改 `agents/*.md`、评测题、内容配置草稿且不改代码的 PR，开发助手打标签 `攒批评测`，不打 `待测试`。
- 统筹凑够一批（或每 2 天）建候选分支 `batch/md-YYYYMMDD` 合入这些 PR，对候选分支打 `待测试`，派测试机一次跑 agent-eval / md 评测。
- 批次评测的多轮判定规则不变，红线题一轮失败即不通过。
- **评测只跑改动涉及的角色**（负责人 2026-11-26 同意）：派测时统筹在指令和 PR 评论里写明涉及的 Agent，测试机每轮都加 `--agent <角色>`（每个角色各跑一次），不再全量跑 93 题；只有换模型、改 `agents/01_公共规范.md` 或网关、运行时代码时才全量跑。
- 红线题三轮、其余题一轮的分档要等 `agent-eval` 支持按题型筛题后才执行（现在 `agent-eval-majority` 遇到轮数不齐的题判不通过）；在那之前按角色筛题跑 3 轮。
- 批次通过且负责人同意 md 后逐个合并原 PR，不通过的 PR 从批次里剔除并退回开发助手。
- 免测不等于免审批：`agents/*.md` 的修改、数据保护红线和资质边界的改动，仍须负责人本人同意后才能合并。

## 6. 会话与通信（2026-11-23 起，负责人同意）

起因：测试机群会话把测试输出堆进对话，上下文反复超限、回复发不出（飞书 99992354）、自动通知的 @ 不生效，测试停摆；统筹侧也出现过合并脚本重复启动、两条合并链抢同一工作树。

1. **领单与会话**：测试机由 `scripts/pr_test_runner.py`（cron 每 15 分钟）按 `待测试` 标签领单，每单一个一次性会话（OpenClaw 用 `RUNNER_AGENT_CMD`），测完写评论、换标签即结束。群会话不跑测试。
   - 2026-11-24 起（负责人 token 优化）：调度脚本先自己跑 `pr_test.sh`；全部通过且“怎么测”无人工核对、真实模型、浏览器类项、无复核说明时，脚本直接贴“测试通过”并换标签，不起模型会话；环境问题未测只贴 summary；有失败或需判断才起会话，只给 summary、“怎么测”段、复核说明和失败日志末 50 行。“人工核对项：无”“模拟模型即可”这类写法不触发会话。
2. **输出**：命令输出落 `~/pr-runner/logs/<单>/`，会话里只看摘要；PR 评论里的日志最多 50 行。
3. **群会话**：只放一行结论和答疑；超过约 60k token 归档重开（OpenClaw：`sessions delete` 并归档）。
4. **通知**：每条通知直接发群新消息，并真 @ 统筹（CC connect Claude）；at 元素用英文直引号，不能把 `<at ...>` 当文字写进 post。改发送方式后先发自测，统筹回一行确认。
5. **防重复**：调度脚本自带锁和每环境一单；手工补跑前先看 `~/pr-runner/state.json`，不要在同一环境另起会话。
6. **环境隔离**：每单 `COMPOSE_PROJECT_NAME=cp<环境>-pr<号>` 新库，库版本比分支新属环境问题；旧项目数据卷不删，清理须负责人决定。
7. **本机适配**：WSL、Windows 互操作等差异用配置项（如 `RUNNER_SETSID=0`）解决；需要改脚本的提 PR，不在本机改。
8. **评测预算**（负责人 2026-11-26 同意）：真模型评测只能由调度脚本 `scripts/pr_test_runner.py` 领单执行，受每单 token 预算和调用次数上限约束，超限自动停并回报；不在群会话或手工会话里直接跑评测。
   - 评测命令放后台跑，结束只报一次结论；不轮询日志、不中途报进度，等待用后台任务通知。
   - 平台或网关回放的旧事件、已结束单的通知不回复。
   - 派评测的指令必须写明“后台跑、结束只报一次、不轮询、旧事件不回”和要跑的角色。
9. **自检**：每次改动调度或通知后，回报写明实际配置、试跑领到的单与环境、日志路径、会话是否独立于群会话。

## 7. 交测前自查（2026-11-25 起，负责人同意）

起因：复盘最近 150 个 PR 里 14 单测试未通过，一半以上是评测题与 md 不一致、“怎么测”不准，不是代码问题。
- 改 md、评测题、知识条目的 PR，交测试机（或进攒批）前，开发线先在本机跑 `agent-eval-lint` 和模拟模型逐题跑通（`pytest tests/test_eval_gate.py`），把输出贴进 PR；lint 不过不交测。
- 评测题里的资质判定一律用公共判定函数（工作项 F6），不写裸词正则；否定句（“不构成测评结论”）必须放行。
- 评测集的 key 必须与条目、md 对得上；控制项编号（如 `SOC.ORG.01`）不得被当成网址或禁词。
- “怎么测”里的每条命令，开发线在本机或 CI 里实际跑过，贴出命令和结果；本机跑不了的明写“未验证，交测试机”。描述与实际结果不一致按测试未通过处理。
- 测试机上的 pytest 一律在容器里跑，不用宿主机 venv（工作项 G7）。
- CI 因外部原因变红（漏洞扫描出新 CVE、下载依赖网络抖动）不算 PR 本身不通过：先 rerun，仍红的在 PR 评论写明外部原因，等升级 PR 合并后 rebase；分层规则见工作项 G8。
- PR 模板见 `.github/pull_request_template.md`。
