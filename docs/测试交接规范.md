# 测试交接规范

测试助手（Ubuntu 测试机上的 Claude Code）收到“测试 PR #N”时，按本规范执行，并把结果写成该 PR 的评论。

## 1. 准备

```bash
cd ~/Consult_Platform            # 测试机上的仓库目录
git fetch origin
git checkout <PR 的分支> && git pull
cat .env >/dev/null || cp .env.example .env   # 首次才需要
```

- 从 M1 登录功能起，测试机 `.env` 必须有：`APP_ENV=test`、`COOKIE_SECURE=false`（测试机用 http 访问）、测试账号 `TEST_ACCOUNT_USERNAME / TEST_ACCOUNT_PASSWORD / TEST_ACCOUNT_TOTP_SECRET`（自己生成，见 `.env.example`）。冒烟测试用这个账号登录；在浏览器里登录时，把 TOTP 密钥加进手机认证器，或用 `python3 -c "import base64,hmac,hashlib,struct,time,sys;..."` 现算（`scripts/smoke_test.sh` 里有现成函数）。
- 读 PR 描述中的“怎么测”。
- PR 涉及数据库迁移时，先备份：`docker compose exec postgres pg_dump -U consult consult > ~/backup_$(date +%F_%H%M).sql`

## 2. 执行

1. `docker compose up -d --build`，等 `docker compose ps` 中 backend 显示 healthy（最多 5 分钟）。
2. `bash scripts/smoke_test.sh`，记录通过 / 失败项数。
3. 按 PR 描述“怎么测”逐项执行，每项记录结果。
4. 本 PR 对应的里程碑验收项（见 `docs/开发计划.md` 第三节），能测的逐条测。
5. 数据保护检查（每次都做）：
   - 发一条含 IP 和口令的对话，应被拦截（返回 422）。
   - 查 `/api/audit`，确认日志里没有刚才发送的原文。
   - 从 M1 起：用非项目成员账号访问项目，应返回 404。测试账号是 BANK-A 项目经理、MFG-C 成员，故意不在 GRID-B，冒烟测试已覆盖；另可用 `python -m app.cli` 建一个不在任何项目里的顾问账号手工验证。
   - 从 M1 审计哈希链起：`docker compose exec backend python -m app.cli verify-audit` 结果为“完整”。
   - 从 M1 起：系统管理员、安全审计员账号看不到任何项目（接口 403，页面显示“没有业务数据访问权限”）。

## 3. 回报格式（PR 评论）

~~~markdown
## 测试结果：通过 / 不通过

- 测试机：<主机名>，提交：<git rev-parse --short HEAD>
- 冒烟测试：通过 X 项，失败 Y 项
- 数据保护检查：通过 / 不通过

| # | 测试项 | 结果 | 说明 |
|---|---|---|---|
| 1 | …… | 通过 / 失败 | …… |

### 失败详情（如有）
- 复现步骤：……
- 相关日志（最多 50 行，**不得包含任何真实客户信息或密钥**）：
  ```
  docker compose logs --no-color backend | tail -50
  ```
~~~

发评论：`gh pr comment <N> --body-file result.md`

## 4. 注意

- 测试机只用虚拟客户数据；接入公司模型后，测试对话里也不得出现真实客户信息。
- 不要修改代码、不要推送；发现问题只回报，由开发助手修复。
- `.env` 中的模型密钥只留在测试机，不出现在评论和日志里。
- 测试结束保持服务运行，便于负责人在浏览器里查看；需要清空数据时先问负责人（`docker compose down -v` 会删除所有数据）。
