# M5 端到端验收清单（S5 ⑧）

对应开发计划第三节 M5 验收标准：**第三级技术控制自查表全部有结论；渗透测试高危问题清零；10 人同时在线压测通过；备份可恢复。** 另加 ⑧ 本身：照《部署手册》能从零部署出生产模式的平台，《运维手册》的常用操作可执行。
全部通过后打标签 `v1.0`。由测试助手在测试机执行，结果按 `docs/测试交接规范.md` 写成 PR 评论。

## 规矩

- 只用虚拟客户：**BANK-V**（标准档）、**GRID-V**（严格档）。不编写、不粘贴任何真实客户信息。
- **只通过页面、接口、`app.cli` 和手册里写的脚本操作，不直接改业务数据。** 手册写得不对、做不下去的地方，记录下来；能按常识绕过的写明怎么绕的。
- 口令、密钥、动态码、`.env` 内容一律不写进 PR 评论、截图和日志。
- 全新部署用单独的 compose 项目名 `cpv1` 和单独的目录、端口，**不动测试机现有的平台和数据**。验收结束后只删除 `cpv1` 自己的容器和数据卷。
- 测试机内存不够同时跑两套时，先 `docker compose stop`（现有平台，数据卷保留），验收完再 `docker compose start`。

## 0. 前置

1. main 已合并 #81（监控）、#78（压测复测）、#82（分库）、#84（部署手册）。
2. 现有平台（测试机原目录）：`git checkout main && git pull && docker compose up -d --build`，按部署手册第三节补 `APP_POSTGRES_PASSWORD` 和 `app-init.sh`；冒烟通过。**这一步同时验收“从 v0.x 升级到 v1.0”。**

## 1. 照部署手册从零部署（生产模式）

```bash
git clone <仓库> /srv/cpv1 && cd /srv/cpv1 && git checkout main
alias dc='docker compose -p cpv1'
```

1. 按部署手册 2.2 写 `.env`：`APP_ENV=prod`、`COOKIE_SECURE=true`，`WEB_PORT=18080`、`WEB_TLS_PORT=18443`，三个数据库口令、MinIO 三项、`TOTP_KEYS` 自己生成；**不配 `TEST_ACCOUNT_*`**；`LLM_BASE_URL=http://mock-llm:8000/v1`（模拟模型，不是外部模型）；`BOOTSTRAP_ADMIN_*` 填首个管理员。证书用 `bash scripts/gen_test_cert.sh` 生成到 `deploy/tls`（只限测试）。复制生产覆盖文件。
2. `dc --profile mock-llm up -d --build`，`dc ps` 全部 healthy。
3. 启动检查各做一次反例（每次改完 `dc up -d backend` 看拒绝启动和日志原因，再改回）：配了 `TEST_ACCOUNT_USERNAME`；`COOKIE_SECURE=false`；`LLM_EXTERNAL=true`；后端连库账号改成超级用户（在 override 里给 backend 设 `DATABASE_URL` 为 `consult` 账号）。前端：拿走证书后 `dc up -d frontend` 拒绝启动。
4. 首个管理员：用 `BOOTSTRAP_ADMIN_*` 登录网页、绑定动态码、改口令；然后从 `.env` 删掉这三项，`dc up -d backend`，仍能登录。
5. 审计员：`dc exec backend python -m app.cli create-user …` + `grant-role --role security_auditor`（口令交互输入）。
6. 管理员在“用户与角色”页建业务账号：顾问 V1、项目经理 V2、项目负责人 V3、知识专家 V4、知识管理员 V5。
7. 立项：`create-project --code BANK-V --tier standard --manager V2`、`create-project --code GRID-V --tier strict --manager V2`，`add-member` 加 V1。
8. 部署手册第七节上线前检查清单的 1～5、10 项逐项核对（6～9、11～13 属部署方或负责人，写“不适用测试机”）。
9. 安全响应：`curl -I http://<测试机>:18080` 301 到 HTTPS；HTTPS 响应带 HSTS、CSP；`curl http://127.0.0.1:8000`（cpv1 没有映射）不通；`/docs` 生产不开放。

## 2. 业务主线回归（生产模式，模拟模型）

1. V1 在 BANK-V 上传 1 份资料、写 1 份访谈纪要（`docs/验收/M3素材/` 里的虚拟材料），发起交付链运行，处理确认卡，到 D4 初稿；质量评审 → 提交签署 → V2 签署 → 导出 Word。
2. V4 投料 1 份公开资料 → 去标识（V5 确认）→ 审核发布（两人原则）→ V1 在对话里检索得到。
3. GRID-V：V2 登记同意，V1 用现场工具做 2 张摘要卡上传，交付链起草出占位符版本。
4. 机密级拦截：在对话里发一段含 `P@ssw0rd2026` 和 `10.1.2.0/24` 的文字，被拦截，审计只记类别。
5. 权限：V1 退出 BANK-V 后访问其项目接口 404；审计员看不到业务数据；管理员看不到业务数据。

## 3. 备份可恢复（M5 验收标准 4）

按 `docs/备份与恢复.md` 在 cpv1 上（`docker compose` 命令换成 `dc`，脚本需要时在 `/srv/cpv1` 下执行并设 `COMPOSE_PROJECT_NAME=cpv1`）：

1. 备份 → 再立一个项目 BANK-W → 恢复 → BANK-W 消失、BANK-V 的交付件和导出仍在、知识条目可检索。
2. 恢复后 `verify-audit` 完整，链头与备份清单的 `audit_head` 一致或在其后。
3. 恢复后数据库账号核对（#84 第 1、2 项）仍成立；冒烟（匿名部分）和第 2 节第 1 项的导出可用。

## 4. 监控与告警

按 `docs/监控.md` 在 cpv1 启用监控：Grafana 面板有数据；制造一次告警（例如连续登录失败触发锁定、或停掉 worker），告警出现、恢复后消除。监控端口不对外映射。

## 5. 运维手册操作

在 cpv1 上各执行一次并记录结果：`list-users`、`unlock`（先输错口令锁定 V1）、`reset-totp`、`jobs`、`selfcheck`、`verify-audit`、`usage-report --days 1`、`retention-report --all`、`deletion-report --all`、`vacuumdb -U consult --all --analyze`、`totp-rekey`（按运维手册第九节加新密钥再轮换，V1 仍能登录）、改 `APP_POSTGRES_PASSWORD`（运维手册 6.1，改后后端正常）。

删除：V2 登记 BANK-V 验收（验收日今天、保留 0 个月）→ `deletion-scan` 发起到期删除 → V3 确认（回流选“无可回流”）→ 删除完成，BANK-V 所有接口 404，删除记录可查，之后 `vacuumdb`。
