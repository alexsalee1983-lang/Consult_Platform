# M3 端到端验收清单（S3 ⑧）

对应开发计划第三节 M3 验收标准：**用虚拟客户在一天内从纪要生成 D4 现状评估初稿；确认卡闭环；Word 导出套用公司模板。**
通过后打标签 `v0.3`（决策记录 2026-11-10）。由测试助手在测试机执行，结果按 `docs/测试交接规范.md` 写成 PR 评论。

## 规矩

- 只用虚拟客户 **MFG-C** 和本目录 `M3素材/` 里的虚拟材料，不编写、不粘贴任何真实客户信息。
- **只通过页面或接口操作，不直接改数据库。** 遇到做不下去的地方，记录下来并停下，不要绕过。
- 模型：测试机当前接外部模型（`LLM_EXTERNAL=true`，只处理虚拟数据，决策记录 2026-11-08）。外部模型不可用时可以换模拟模型重跑流程，但第 3 节 D4 的内容检查必须用真实模型的结果。
- 截图和日志里不出现密钥；回报里不贴整段正文，只摘短句说明问题。

## 0. 前置

1. `git checkout main && git pull && docker compose up -d --build`（要包含 #49 add-member），`bash scripts/smoke_test.sh` 通过，健康检查各项 ok。
2. 账号：
   - **A**：`.env` 里的测试账号（TEST_ACCOUNT_*），启动时自动成为 MFG-C 的项目成员。
   - **B**：MFG-C 的项目经理。用 `python -m app.cli add-member --project MFG-C --username qa-ui --role manager` 指定 qa-ui。签署只能由项目经理做。
3. 确认 MFG-C 的 D3、D4 未签署，并且没有未结束的交付链运行。
4. 记下开始时间 T0。

## 1. 证据入库（账号 A，页面操作）

1. 驾驶舱“录入纪要 / 观察”：按 `M3素材/` 录入 I1～I4 四份访谈纪要（类别访谈，标题、受访者角色、日期照抄）和 O1 现场观察。
2. “上传客户资料”：上传 `D1_值班安排表.txt`，等状态变成“已解析”。
3. 检查：
   - 编号依次是 I-01～I-04、O-01、D-01（MFG-C 原来已有证据时顺延）；
   - KPI 证据数和分类计数正确；
   - 点开能看到正文和解析预览。

## 2. 交付链运行与确认卡闭环（账号 A）

1. 驾驶舱点“运行交付链”。各步状态依次变化：第 3 步整理事实清单 → 第 4 步差距分析 → 第 7 步现状评估报告初稿。
2. **确认卡**：素材里埋了矛盾点（信息安全负责人说“已经 7×24”，SOC 负责人、值班表和现场观察都说只有白班）和证据不足项（工控网监测没人负责）。
   - 预期 Agent 至少发出一张“来源冲突”或“证据不足”卡，运行停在“等你确认”。
   - 在“待你确认”里处理：一张选选项，另一张写意见；只有一张就写意见。
   - 运行应自动继续，后续步骤不再重复问同一个问题。
   - 如果一张卡都没发，如实记录。这不算失败，但要在评论里写明。
3. **取消**：等这次运行结束后，再发起一次，在第 3 步运行中点“取消运行”，状态变成已取消，之后不再写入。D3 的版本号不应在取消之后增加。
4. 记录：第一次运行的开始和结束时间（`GET /api/projects/MFG-C/runs/{id}`）、各步模型和用量、确认卡数量。

## 3. D4 初稿内容检查（账号 A，交付件审阅页）

D3、D4 各抽 2 章检查：

- 有正文，来源标注能核对上（上标颜色正常，没有或很少有红色“核对不上”）；
- 矛盾点有体现：没有直接写成“已 7×24 值守”；
- 没有出现等保测评结论、认证结论之类的用语（资质边界）；
- 没有出现素材以外编造的客户事实。例如：素材里写 SOC 4 人，初稿就不应写成别的人数。

如有问题，记录章节和一句话描述，**不需要改正文**。

## 4. 质量评审、签署、导出（D4）

1. 账号 A 在 D4 审阅页点“发起质量评审”，等结论出来，记录结论和阻断、重要、建议的数量。
2. 有阻断时：
   - 按问题清单在页面上修改相应章节（可以手工改正文）；
   - 重新评审，直到阻断为 0，或者确认无法消除（记录原因后停止本节）。
3. 账号 A 提交签署；账号 B 先退回一次（写理由），状态回到起草；A 再提交，B 签署。
4. **Word 导出**：
   - 用 Word 或 LibreOffice 做一个简单模板 `deliverable.docx`，含占位符 `{{项目代号}} {{交付件编号}} {{交付件名称}} {{状态}}`，另起一段只写 `{{正文}}`。
   - 放到测试机，在 `.env` 设 `EXPORT_TEMPLATE=/srv/templates/deliverable.docx`，挂载这个文件，重启 backend。
   - 导出已签署的 D4：占位符都被替换；没有草稿页眉；页脚有导出编号；来源有 Word 脚注。
   - 再导出一份未签署的交付件（如 D3）：每页页眉标“草稿”。
   - 把 `EXPORT_TEMPLATE` 改成一个不存在的路径，导出应返回 503，不悄悄退回默认模板。测完改回。

## 5. 严格档与隔离

1. 用 add-member 把 qa-ui 加进 GRID-B（#49 测过就跳过这一步）。在驾驶舱确认：证据区和交付链区只显示严格档说明，没有上传、录入、运行按钮。
2. 不是 MFG-C 成员的账号：打开 `/project/MFG-C` 和 `/project/MFG-C/deliverables/D4`，都不显示数据（404）。

## 6. 留痕检查

1. `python -m app.cli verify-audit` 显示审计链完整。
2. 抽查本次的审计记录（`/api/audit` 或审计页）：
   - `project.note`、`project.document`、`run.*`、`confirmation.*`、`deliverable.*`（含 `deliverable.export`）、`quality.*` 记录只有编号、字数、哈希；
   - 不出现纪要正文、章节正文、标题原文。
3. `docker compose logs backend worker | grep -c "都是白班 8:30"` 应为 0（日志里不出现纪要原文）。
4. `python -m app.cli usage-report --days 1` 能看到本次运行的用量。

## 判定

- **通过**：第 1、2、4、5、6 节全部符合预期；第 3 节没有资质用语和编造事实；第一次交付链运行从 T0 起当天完成。
- 第 3 节内容质量的一般问题，例如章节偏短、措辞不够专业，记为“建议”，不阻挡通过。可以交给负责人或资深顾问抽查，再决定是否进入第二阶段提示词调优。
- 回报格式：每一节写通过 / 不通过 / 未覆盖，附关键编号（运行编号、导出编号、卡片编号）和时间。
