# M4 端到端验收清单（S4 ⑦）

对应开发计划第三节 M4 验收标准：**到期提醒、人工确认、删除记录抽检通过；严格档“填卡 → 上传 → 起草 → 回填”闭环跑通。**
通过后打标签 `v0.4`。由测试助手在测试机执行，结果按 `docs/测试交接规范.md` 写成 PR 评论。

## 规矩

- 只用虚拟客户：严格档 **GRID-E**，标准档 **MFG-D**、**MFG-E**，以及本目录 `M4素材/` 里的虚拟材料。不编写、不粘贴任何真实客户信息。素材里的“江北示范供电公司”“天枢调度平台”“李处长”都是编造的。
- **只通过页面、接口和 `app.cli` 操作，不直接改数据库。** 遇到做不下去的地方，记录下来并停下，不要绕过。
- 文号只写编号，例如“同意-E01”“撤回-E01”“删除-D01”，不写客户名称。
- 口令（上传包、工作文件）不写进 PR 评论、截图和日志。
- 模型可以用外部模型，也可以用模拟模型（`--profile mock-llm`）。本次验收的重点是流程闭环和数据处置，不评正文写作质量。

## 0. 前置

1. `git checkout main && git pull && docker compose up -d --build`；`bash scripts/smoke_test.sh` 通过；`alembic` 版本为 0027。
2. 账号：
   - **A**：顾问，即 `.env` 里的测试账号。
   - **B**：项目经理（qa-ui）。
   - **C**：项目负责人。负责确认删除，不是项目成员也可以；不能和发起删除申请的是同一人。没有的话，由系统管理员在“用户与角色”页给一个账号（如 qa-lead）授予“项目负责人”。
3. 立项：
   - `create-project --code GRID-E --tier strict --manager qa-ui --industry 电力`
   - `create-project --code MFG-D --tier standard --manager qa-ui --industry 制造`
   - `create-project --code MFG-E --tier standard --manager qa-ui --industry 制造`
   - 再用 `add-member` 把账号 A 加进三个项目，角色为顾问。
4. 现场工具：把仓库里的 `field-tool/field-tool.html` 拷到测试机桌面，用浏览器直接打开。

## 1. 严格档闭环：填卡 → 上传 → 起草 → 回填（GRID-E）

### 1.1 同意与模板（离场前）

1. B 在驾驶舱“客户同意与摘要卡”面板登记书面同意，文号“同意-E01”，签署日期为今天或更早。状态变为“客户已书面同意”。
2. A 点击“下载空白模板”，得到 json。
3. 没有同意时不能上传：在登记同意之前尝试上传，或者看面板提示，应当被拒。这一步在第 1 步之前做也可以。

### 1.2 现场（断网操作）

1. 断开测试机网络，或者用浏览器开发者工具确认，下面整个过程没有任何网络请求。
2. 现场工具导入模板，项目代号自动填为 GRID-E。
3. 按 `M4素材/对照表.txt` 录入对照表，共 4 行。
4. 按 `M4素材/摘要卡草稿.md` 录入 5 张卡。
   - 第 1～4 张应显示“自检通过”。
   - 第 5 张应标红，类别为机构名称、人员姓名、系统名称、原话。
5. 把第 5 张的现状按草稿里的“改写后”改好，变为自检通过。
6. 保存加密工作文件。刷新页面后重新打开，卡片和对照表都能恢复。
7. 勾选“客户对接人已审阅签字”，导出上传包 `.cpcard`。用文本方式打开，看不到任何真名和占位符明文。

### 1.3 离场后上传

1. 恢复网络。A 在驾驶舱输入口令，选择 `.cpcard` 上传包，在浏览器里解密，核对 5 张卡后上传。清单出现 S-01～S-05。
   - 测试机是 HTTP 访问时，改用粘贴框上传，并在评论里注明。
2. 同一个包再传一次 → 被拒，每张卡下面显示“重复：与 S-xx 内容相同”。

### 1.4 起草

1. A 在驾驶舱运行交付链。
   - 第 3 步读摘要卡写 D3，之后差距分析，再写 D4 初稿。
   - 发了确认卡就处理，处理完运行应自动继续。
   - `GET /api/projects/GRID-E/runs/{id}` 里 `chain` 为 `strict`。
2. 打开 D3、D4，检查以下两点。
   - 正文只用占位符，来源标为 `[S-01]` 这样的格式。全文搜“江北”“天枢”“玄武”“李处长”“QRadar”，结果都应为 0。
   - 手工往 D4 某一章写“由李处长负责 [S-01]”→ 被拒，提示含人员姓名，没有保存。
3. 发起质量评审，处理阻断，可以修改或驳回，规则与 M3 相同。之后 A 提交签署，B 签署 D4。
4. 导出 D4 的 Word。正文是占位符版本，来源有脚注。

### 1.5 回到现场回填

1. 现场工具打开工作文件，在“占位符回填”页选择第 1.4 步导出的 D4 Word，下载“-正式稿.docx”。
2. 用 Word 或 LibreOffice 打开正式稿，检查以下几点。
   - 【客户】【系统A】【人员1】等已换成对照表里的虚拟真名。
   - 页面列出的未替换占位符，与正文实际剩下的一致。被 Word 格式拆开的占位符要手工处理，这种情况如实记录。
   - 文件能正常打开，没有报错或修复提示。
3. 正式稿和工作文件留在测试机本地，测完删除，不上传、不附进评论。

### 1.6 撤回同意

1. 新建 GRID-F（严格档），走一遍简化流程：登记同意 → 上传 2 张卡 → 在 D3 写一章占位符正文。
2. B 登记撤回，文号“撤回-F01”。确认框写明会清空哪些内容。撤回后检查以下几点。
   - 摘要卡内容已清空。
   - D3 正文为空。
   - 再写入正文或运行交付链 → 被拒，提示没有有效同意。
   - 审计里有 `versions_cleared` 等计数，没有文号。

## 2. 到期提醒（MFG-E）

1. A 在 MFG-E 录入一条纪要。
2. B 在“验收与保留期”登记验收：验收日为今天往前 5 个月零 10 天，保留 6 个月。
3. 检查以下几点。
   - 状态为“30 天内到期”（`retention_state=due_soon`），并显示到期日和剩余天数。
   - 剩余天数与日期计算一致（月末顺延到当月最后一天）。
   - 项目列表上也能看到这个状态。
4. `retention-report` 列出 MFG-E。
5. `deletion-scan` 不为 MFG-E 发起删除，因为还没到期。

## 3. 删除：人工确认与删除记录（MFG-D）

### 3.1 准备数据

A 在 MFG-D 做以下准备：

- 录入 1 条纪要（I-01）和 1 条观察（O-01），上传 1 份资料（D-01，可用 M3 素材里的值班表）；
- 给 D4 写大纲和一章正文；
- 运行一次交付链（或者至少发一张确认卡）；
- 在顾问对话里问一句。

B 再签署任意一份交付件，这一步可选，用来验证已签署的交付件也会一起删除。

### 3.2 仅现场使用（M4 ③）

1. B 把 D-01 标为仅现场使用，文号“现场-D01”。之后检查以下几点。
   - 资料详情不再有文件名和预览。
   - 同一文件再次上传 → 被拒。
   - 在交付件正文里写 `[D-01]` → 被拒。

### 3.3 到期删除

1. B 更正验收：验收日为今天往前 7 个月，保留 6 个月。状态变为“已到期”。
2. `deletion-scan`（或等 worker 每小时自动扫描）→ 删除申请出现，发起人为 platform。
3. 先做两项负面检查：
   - B（不是项目负责人）不能确认这个申请；
   - 到期申请没有撤销入口。
4. C 在“删除确认”页确认删除，经验回流选“无可回流”，或者填投料编号。
5. 等后台任务完成，`deletion-report --all` 显示已删除。

### 3.4 删除记录抽检

1. 删除记录是可以交给客户的那份记录。它只应包含：编号、日期、各类计数、确认人、回流情况。检查以下几点。
   - 计数和第 3.1 步准备的数据一致：证据、资料、交付件含已签署的、章节版本、确认卡、对话、运行。
   - 记录里没有正文、文件名和文号。
2. 删除后检查以下几点。
   - MFG-D 的项目页和所有项目接口都返回 404。
   - 项目列表里不再出现 MFG-D。
   - 用 `create-project` 再建 MFG-D → 被拒，因为代号不复用。
3. 对象存储：测试机上有 `mc` 的话，查看项目区桶的 `MFG-D/` 前缀，应为空；没有 `mc` 就注明“未覆盖”。

### 3.5 提前删除（客户书面要求）

1. 在 MFG-E 上，B 发起提前删除，文号“删除-E01”。截止日期应为 10 个工作日后（周一至周五计）。
2. C 写理由撤销这个申请 → 状态为已撤销，项目数据还在。
3. （可选）再发起一次，由 C 确认，这次的经验回流选“客户不同意回流”。

## 4. 留痕与日志

1. `verify-audit` 显示审计链完整。
2. 抽查审计记录：`project.summary_card`、`project.consent*`、`deliverable.*`、`run.*`、`project.local_only`、`project.acceptance`、`project.deletion*`。检查以下几点。
   - 记录里只有编号、日期、计数和类别。
   - 不出现卡片内容、正文、标题、文号，也不出现“江北”“天枢”“李处长”。
3. 分别统计后端和 worker 日志里这几个词出现的次数：`docker compose logs backend worker | grep -c -e 江北 -e 天枢 -e 李处长`，应为 0。

## 判定

- **通过**：第 1～4 节全部符合预期。
  - 严格档闭环（1.1～1.5）一次走通，中途不需要绕过平台。
  - 删除记录抽检（3.4）的计数准确，且不含原文。
- 第 1.5 步里，被 Word 格式拆开、需要手工处理的占位符，只要页面列出了，就不算失败。
- 回报格式：每一节写通过 / 不通过 / 未覆盖，附上关键编号（运行编号、摘要卡编号、删除申请编号、导出编号）和时间。发现的问题写清章节、操作和现象，只摘短句。
