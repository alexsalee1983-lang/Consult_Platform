## 三、核心设计：从 SOC 写死到按服务产品配置

| 配置项 | 产品配置写什么 | 模块能追加什么 |
|---|---|---|
| 交付件清单 | 编号、名称、阶段、是否对客、默认大纲 | 在某个交付件里追加章节 |
| 交付链步骤 | 步骤、负责 Agent、输入和输出的交付件、提示词模板 | 一般不加步骤 |
| 评估基线与维度 | 能力域（事实清单分组）、对标框架、依据集合 | 追加依据和对标项 |
| 质量门禁 | 产品特有的硬规则（如 ISO 27001 的 SoA 覆盖附录 A 全部 93 项） | 追加规则 |
| 知识检索 | 按“服务产品”元数据过滤，先查本产品、再查通用 | 追加标签 |
| 严格档 | 摘要卡评估项、严格档提示规则（第十节修订 ②） | 追加评估项 |

设计原则：

1. **配置放在仓库里**（`products/*.yaml`、`modules/*.yaml`），和 Agent md 一样版本化，改配置走 PR、负责人审批；二期不做网页编辑。
2. **立项即冻结**：项目记下产品和模块的配置版本（内容哈希），之后配置改版不影响进行中的项目。
3. **Agent 不按产品增加**：按交付环节分工；各 Agent md 改为“通用骨架 + 产品模块”，运行时只拼入本项目产品和模块的段落。
4. **SOC 是第一份配置**：先把现有写死的 SOC 搬成配置，现有项目迁移为“产品 = SOC”，M3、M4 验收用例全部重跑通过，再加新产品。

## 十一、公开知识准确应用机制（11-15，负责人同意）

背景：负责人同意把公开资料尽量全部下载到试用机（法律法规、行业监管文件、官方能下载的国家标准、TC260 实践指南、NIST、MITRE ATT&CK 等，按批次写下载清单），并要求“下载后怎么用准”体现在平台机制上。大模型对概念和老法规掌握尚可，但新法规、条款号和原文、版本效力、行业要求都靠不住；知识库的作用是给 Agent 可核对的依据，不是教模型。公共规范第 4 节已规定“依据库里查不到时标【依据待核实】，不得凭记忆补写条款号或原文”，以下机制让平台能检查、能拦住。

**原则**

1. 原文和解读分开。条款号和原文只取官方原件，经机械切分入库、不经模型改写；模型只起草解读、映射、案例和异议应答，而且只能引用已入库的条款。
2. 版权分档。法律法规不适用著作权法（第五条），原文可以逐条入库。美国政府出版物（NIST、CISA）可以原文入库。MITRE ATT&CK 按其使用条款，可以入库，但要保留版权声明。国家标准（GB/T、JR/T、GM/T）即使官方免费下载，知识库也仍只收条款号、条款标题、解读和映射，不收全文（沿用第六节）。原件只放在下载目录，供审改时对照。
3. 宁缺勿错。检索达不到分数门槛的不给，Agent 标“【依据待核实】”或发“证据不足”卡。引用已废止或已被替代的条款，在签署前拦下。

**新增与扩充的任务**：B7、B8、B9 和 B1 / B2 / B5 的补充，已并入第四节 B 线总表。

**内容侧顺序**（开发线 2，配合 B1）：第一，近两年新发布或修订的法规；第二，金融和电力的行业文件；第三，等保、数据安全、密评的条款目录、解读和映射（与 B3 合用）；第四，NIST 和 ATT&CK（ATT&CK 和 Sigma 规则加工成 SOC 检测用例和处置剧本）；第五，监管处罚案例加工成异议应答（只记问题类型、依据和金额，不记当事单位名称）。公开资料的审核按第十二节三级审核（原写“公开资料可以打开 `KB_SINGLE_REVIEWER_PUBLIC`”已被取代，生产保持关闭）。

## 十二、自动化优先原则（11-15，负责人定）

**原则**：平台尽量少用人工，能做成工作流自动完成的都做成自动化；前提是不降低咨询质量。以后每个功能、每个流程设计都先按这条判断。

1. **默认自动，人工要有理由。** 一个环节要人来做，必须属于下面“保留人工”的几类之一；否则设计成“平台程序 + Agent”自动完成。
2. **质量靠多道机器检查，不靠人工兜底。** 能用程序判断的用程序（条款号核对、时效、机密级、结论用语、元数据、引用来源）；要理解语义的交给 Agent，按清单逐项判断并写明理由；再加评测和事后抽检。机器检查不通过就停下，不放行。
3. **人只处理例外。** 自动检查全部通过的直接往下走；存疑的才进人工队列。进队列时由平台和 Agent 先把问题、原文对照和建议列好，人只看那几处、做选择，不从头读。
4. **自动决定可追溯。** 自动通过、自动发布都记下是哪条规则、哪个 Agent 和哪版提示词判的，留审计（不记原文），能抽检、能回滚。
5. **抽检代替逐条审。** 自动发布的内容按比例随机抽检，按问题率调整比例；某类内容问题率超标，就退回逐条人工审，直到修好。
6. **红线和资质边界不因自动化放松。** 数据保护红线、资质边界、两人原则里涉及客户数据和对外交付的部分照旧。

**保留人工的环节**（只有这几类）：

| 类别 | 环节 | 理由 |
|---|---|---|
| 对客户负责的签字 | 项目经理签署交付件、项目负责人确认删除 | 对外交付和不可逆操作，要有人担责 |
| 客户数据 | 非公开来源的去标识确认（知识管理员）、严格档客户书面同意登记、仅现场使用标记 | 数据保护红线 |
| 只有人知道的事 | 上传证据、访谈纪要、方案取舍和范围确认（确认卡）、经验回流内容 | 信息来源在人和客户那里 |
| 公司经验的认可 | 项目沉淀、专家经验（L2、L5）的发布 | 是不是公司认可的做法，只能由人判断；Agent 先查、一人拍板 |
| 规则本身的变更 | Agent md、权限、工具授权、决策记录、产品配置 | 负责人审批 |

- **自动发布不设比例**：符合第一、二级范围的每一条都过机器检查，全部通过才发布，自动发布占多少由检查结果决定，审核页显示实际数字。
- **抽检**：每条自动发布的条目按比例随机决定是否抽中，抽中的进抽检队列，由一位知识专家按七项清单看（不能抽检自己导入或编写的版本）；不通过的退回修改。
- **停止自动发布**：某一类最近 20 次抽检的不通过率超过 10%，这一类全部回到人工两人审核；不通过率回到 10% 以下自动恢复。管理员可用开关 `KB_SRC_AUTO_PUBLISH`、`KB_AGENT_AUTO_PUBLISH` 硬停，恢复由负责人决定。起步阶段抽检次数少，1 次不通过就会停，按从严处理。
- **审核员资格**（决策记录 2026-11-15 第 ⑥ 项）：内容审核为知识专家、所审领域 3 年以上咨询实践；合规审核为知识管理员；人工审核、抽检和 Agent 用同一份七项清单。
- **不变的**：作者不能审自己的版本；去标识确认人不能是上传者；非公开来源不自动发布；数据保护红线和资质边界不变。
