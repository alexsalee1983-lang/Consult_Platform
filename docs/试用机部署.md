# 试用机部署（测试模式、外部模型）

> 2026-11-18 起（决策记录同日）：测试机与试用机互换。专家试用改在原 Ubuntu 测试机上，只跟 main，已有已发布知识，第七节的知识导出导入不再需要；本文档描述的高配电脑改为测试机，按 `docs/测试交接规范.md` 跑两套并行测试环境。本文的安装步骤仍适用于在新电脑上装试用环境。

负责人自用的试用电脑：测试模式运行，对话用外部模型 DeepSeek，重排用硅基流动（决策记录 2026-11-08、2026-11-14）。**只用虚拟客户数据**（BANK-A、GRID-B、MFG-C 等），不放任何真实客户信息；严格档项目在外部模型下拒绝调用模型。这不是生产部署，生产按 `docs/部署手册.md` 执行。

## 一、准备

- Windows 11 + Docker Desktop（WSL2 后端），分给 Docker 的内存 ≥ 12 GB，磁盘 ≥ 40 GB。
- Git。在 Git Bash 里执行下面的命令。
- DeepSeek API 密钥、硅基流动 API 密钥。**只写进 `.env`，不发到聊天、不截图。**

```bash
git clone <仓库地址> consult-platform && cd consult-platform && git checkout main
cp .env.example .env
```

## 二、配置 `.env`

生成随机值（每条运行一次，结果填到对应项）：

```bash
python -c "import secrets; print(secrets.token_urlsafe(24))"     # POSTGRES_PASSWORD、APP_POSTGRES_PASSWORD、KB_POSTGRES_PASSWORD 各一个
python -c "import secrets; print(secrets.token_urlsafe(30))"     # MINIO_SECRET_KEY
python -c "import base64, secrets; print('platform-key:' + base64.b64encode(secrets.token_bytes(32)).decode())"   # MINIO_KMS_SECRET_KEY
python -c "import base64, secrets; print('k1:' + base64.b64encode(secrets.token_bytes(32)).decode())"             # TOTP_KEYS
```

要改的项：

| 项 | 值 |
|---|---|
| `APP_ENV` | `dev`（**不能是 prod**：prod 下外部模型、外部重排都会拒绝启动） |
| `COOKIE_SECURE` | `false`（用 http:// 访问） |
| `WEB_PORT` | `8080`，被占用就换一个；本机还跑别的项目时用 81xx 段：`WEB_PORT=8180`、`BACKEND_DEBUG_PORT=8181`、`WEB_TLS_PORT=8182` |
| `WEB_BIND` | 只自己在本机用就设 `127.0.0.1`，局域网其他电脑访问不到；要给同事用则不设 |
| `POSTGRES_PASSWORD` / `APP_POSTGRES_PASSWORD` / `KB_POSTGRES_PASSWORD` | 上面生成的，三个各不相同 |
| `MINIO_SECRET_KEY` / `MINIO_KMS_SECRET_KEY` / `TOTP_KEYS` | 上面生成的。KMS 密钥另存一份，丢了文件无法解密 |
| `LLM_EXTERNAL` | `true` |
| `LLM_BASE_URL` | `https://api.deepseek.com` |
| `LLM_API_KEY` | DeepSeek 密钥 |
| `LLM_MODEL_REASONING` / `STANDARD` / `LIGHT` | DeepSeek 控制台给的模型 ID |
| `SEED_DEMO_DATA` | `true`（首次启动写入虚拟客户演示数据） |

硅基流动重排，加四行：

```
RERANK_EXTERNAL=true
RERANK_BASE_URL=https://api.siliconflow.cn/v1
RERANK_API_KEY=<硅基流动密钥>
RERANK_MODEL=Qwen/Qwen3-Reranker-8B
```

本地 rerank 容器仍按默认的 int8 模型构建，不受 `RERANK_MODEL` 影响（#87）。国内网络构建慢时，打开 `PIP_INDEX_URL`、`NPM_REGISTRY` 两行的镜像源。

## 三、启动

```bash
docker compose up -d --build        # 首次构建要下载镜像和模型，较慢
docker compose ps                   # 等全部 healthy
```

## 四、首个账号

```bash
docker compose exec backend python -m app.cli create-user --username admin --display-name 管理员   # 口令交互输入
docker compose exec backend python -m app.cli grant-role --username admin --role sys_admin
```

create-user 会在终端显示动态码密钥，用手机认证器（如 Microsoft Authenticator）添加；密钥不要截图外传。浏览器打开 `http://localhost:8080`（改过 WEB_PORT 就用新端口）用 admin 登录。管理员看不到业务数据，所以要在“用户与角色”页另建一个顾问账号（例如 `alex`）来使用。然后立项：

```bash
docker compose exec backend python -m app.cli create-project --code BANK-T --tier standard --manager alex --industry 银行
```

## 五、验证

```bash
docker compose exec backend python -m app.cli selfcheck
curl -s http://localhost:${WEB_PORT:-8080}/api/health
```

`llm`、`rerank`、`embedding` 都应是 ok。之后用顾问账号在对话里提一个问题，能收到回复就说明打通了。

换了重排模型后检索门槛要重新校准：用 `kb-eval` 跑评测集（见 `docs/知识库建设方案.md`），再按结果调 `KB_BASIS_MIN_RERANK`、`KB_SEARCH_MIN_RERANK`。

## 七、升级到二期 main，供专家试用（负责人 2026-11-17 决定）

专家在试用机上审改知识、试用对话和交付链。试用机仍是测试模式、外部模型，**只放公开资料和虚拟客户**（BANK-A、GRID-B、MFG-C 等）：真实客户信息、公司内部制度原文、未公开的专家经验都不录入，等生产环境（公司模型）就绪后再录入。

### 1. 升级

```bash
docker compose ps                     # 先确认现有环境正常
git pull                              # 到 main 最新
docker compose up -d --build          # 后端启动时自动执行数据库迁移（主库和知识区库）
docker compose ps                     # 等全部 healthy
docker compose exec backend python -m app.cli selfcheck
```

`.env` 不用改就能启动：二期新增的项都有默认值。建议加两项：

```
LLM_MODEL_TOOLS=deepseek-v4-pro       # 对话带工具时用 v4-pro（#179 实测，flash 多轮后不稳）；控制台的模型 ID 不同就照填
KB_DOWNLOADS_DIR=./kb-downloads       # 知识资料目录，第 2 步放迁移包
```

改了 `.env` 要再执行一次 `docker compose up -d`。**不要执行 `docker compose down -v`。**

### 2. 导入知识（从测试机迁移已发布的公开知识）

测试机已发布的公开知识（依据原文、解读、映射等）用知识迁移导出导入，平台在试用机上重新自动核验，不用专家重审：

1. 测试机：`kb-export` 导出；把导出目录和清单哈希放进私有资料仓 `Consult_Knowledge` 的 `exports/<日期>/`。清单哈希另经飞书告知。
2. 试用机：把资料仓克隆或拉取到 `KB_DOWNLOADS_DIR`（默认 `./kb-downloads`），然后执行：

```bash
docker compose exec backend python -m app.cli kb-import-export /srv/knowledge/downloads/exports/<日期> --sha256 <清单哈希> --as <知识专家账号>
docker compose exec backend python -m app.cli jobs     # 向量化在后台做，等队列清空
```

导入用的知识专家账号要先建好（第 3 步）。

### 3. 专家账号

系统管理员在网页“用户与角色”页建账号，首次登录要改口令、绑定动态码：

| 专家做什么 | 角色 |
|---|---|
| 审改知识条目、抽检、复审 | 知识专家 `knowledge_expert` |
| 去标识确认、合规审核 | 知识管理员 `knowledge_admin`（两人原则：不能审自己的版本） |
| 试用对话、交付链、驾驶舱 | 顾问 `consultant`，并由项目经理加进虚拟项目 |

一人可以同时持知识专家和顾问角色。系统管理员看不到业务数据，不要给专家。

### 4. 校准检索门槛

试用机的重排用硅基流动，和测试机的本地重排不同，导入后跑一次门槛校准（#184）：

```bash
docker compose exec backend python -m app.cli kb-eval /srv/knowledge/downloads/eval/formal.yaml --as <顾问账号> --sweep
```

推荐值和现值不同时，把报告交负责人定，再改 `.env` 的 `KB_BASIS_MIN_RERANK` / `KB_SEARCH_MIN_RERANK`，然后执行 `up -d`。

### 5. 验证

```bash
docker compose exec backend python -m app.cli selfcheck
curl -s http://localhost:${WEB_PORT:-8080}/api/health
```

用顾问账号在 BANK-A 对话里问一个依据问题，应看到“正在调用工具：知识检索……”，回复带依据引用；在知识专家账号的审批页能看到条目和抽检队列。

## 八、开放给办公室内网的专家（负责人 2026-11-20）

试用期专家都在同一个办公室内网，用自己电脑的浏览器访问试用机，不用 VPN，也不引入新服务。**不要把试用机映射到公网。**

### 1. 一键开放

```bash
bash scripts/trial_lan_setup.sh               # 自动取本机内网 IP；取错时把 IP 作为参数传入
```

脚本做四件事：生成含试用机内网 IP 的自签名证书（90 天，到期重跑）；把 `.env` 改成 `COOKIE_SECURE=true` 并取消只绑本机，原文件先备份；ufw 已启用时只放行网页的 HTTPS 端口和 HTTP 端口（HTTP 只做跳转）；重启前端、后端、worker 并自检。每一步都会打印“通过”或“不通过”。脚本不动数据卷，也不写库。

完成后跑冒烟（自签名证书要用 `CURL_CA_BUNDLE` 指定）：

```bash
CURL_CA_BUNDLE=deploy/tls/server.crt bash scripts/smoke_test.sh https://localhost:${WEB_TLS_PORT:-8443}
```

### 2. 专家怎么连

- 浏览器打开 `https://<试用机内网IP>:<WEB_TLS_PORT>`（默认 8443）。第一次会提示证书不受信任，点“高级 → 继续访问”。
- 账号按第七节第 3 步开，一人一号，初始口令单独发给本人。首次登录改口令、绑定动态码。

### 3. 五位专家的账号与分工（负责人 2026-11-20：按 5 位专家同时使用）

每位专家主责一个产品，负责复核该产品的公开方法版（评估维度、交付件写法、待专家复核的知识条目）。五人都有顾问和知识专家两个角色，其中两人再加知识管理员。这样审核人不是作者、去标识确认人不是上传者，人手足够交叉。系统管理员仍由负责人自己的 admin 担任，不给专家。

| 账号 | 角色 | 主责产品 | 项目 |
|---|---|---|---|
| `zj1` | 顾问、知识专家、知识管理员 | SOC 运营体系设计 | BANK-A 项目经理 |
| `zj2` | 顾问、知识专家、知识管理员 | 网络安全治理规划（NSG） | GRID-B 项目经理 |
| `zj3` | 顾问、知识专家 | 数据安全管理体系建设（DSM） | MFG-C 项目经理 |
| `zj4` | 顾问、知识专家 | ISO 27001 信息安全管理体系建设 | 三个项目的成员 |
| `zj5` | 顾问、知识专家 | 事件后 E2E 评估与整改（IRE） | 三个项目的成员 |

账号名可以换成专家的拼音，但不用工号、手机号。下面的命令每人执行一次，口令交互输入，动态码密钥当面绑定：

```bash
docker compose exec backend python -m app.cli create-user --username zj1 --display-name 专家一
docker compose exec backend python -m app.cli grant-role --username zj1 --role consultant
docker compose exec backend python -m app.cli grant-role --username zj1 --role knowledge_expert
docker compose exec backend python -m app.cli grant-role --username zj1 --role knowledge_admin   # 只给 zj1、zj2
docker compose exec backend python -m app.cli create-project --code BANK-A --tier standard --manager zj1 --industry 银行
```

GRID-B、MFG-C 照此立项，项目经理分别是 zj2、zj3。立项后，项目经理在网页上把其余四人都加为成员，五个人就能在三个虚拟项目里各自试自己主责的产品，也能互相评审。已有同名虚拟项目的，用 `add-member --role manager` 指定经理，不要重复立项。

五人同时使用时，交付链是后台任务排队执行，试用机压力不大。外部模型限流导致变慢时，可以错开时间跑交付链。

### 4. 开放前跟专家讲清楚

1. 只用虚拟客户（BANK-A、GRID-B、MFG-C 等），不输入任何真实客户信息：试用机对话走外部模型。
2. 平台只给差距分析、符合性初判、整改建议，不出具测评或认证结论。
3. 意见直接在平台上改、在确认卡上点：试用机开了判断数据埋点，修改会自动记录，用来改进平台。

### 5. 日常

- 试用机保持开机、不休眠；每天跑 `scripts/backup.sh`。
- `backup.sh` 必须给出备份口令文件：`BACKUP_PASSPHRASE_FILE=/etc/consult-platform/backup.pass bash scripts/backup.sh /srv/backups/consult-platform`（口令文件只放试用机、权限 600，不进仓库，不写进 `.env`；不设会直接报错退出）。
- 更新到新版本按第七节第 1 步执行，`.env` 和证书都保留，不用重跑本节。
