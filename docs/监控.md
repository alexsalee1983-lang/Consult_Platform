# 监控（M5 ⑤）

依据：开发计划 S5 ⑤（自建 Prometheus / Grafana，内网、不映射公网、不联网）；等保三级技术控制自查 8.1.4.3 d、8.1.4.4 f、8.1.5.4。

## 1. 组成

| 部分 | 位置 | 说明 |
|---|---|---|
| 指标 | `backend/app/core/metrics.py` | backend、worker 各开一个指标端口 9100（`METRICS_PORT`），只在 docker 内部网络，**不映射到宿主机**；业务端口上没有 `/metrics` |
| Prometheus | `deploy/monitoring/prometheus/`（`prometheus.yml`、`alerts.yml`） | 每 15 秒抓 backend、worker（多个 worker 按 DNS 逐个抓），数据保留 `PROMETHEUS_RETENTION`（默认 30 天）；9090 **不映射端口**，只有 Grafana 在内部网络访问，排查时 `docker compose --profile monitoring exec prometheus wget -qO- localhost:9090/api/v1/targets` |
| Grafana | `deploy/monitoring/grafana/` | 数据源和“平台运行”看板随启动自动导入（只读）；只绑定宿主机 `127.0.0.1:${GRAFANA_PORT:-3000}`（其他主机连不上，经 SSH 隧道访问）；关闭使用统计、更新检查、新闻、头像等一切外联 |

指标只有计数、耗时和状态。标签只用路由模板（`/api/projects/{code}`，不是实际路径；没匹配到路由的记 `unmatched`）、方法、状态码、任务种类、上游服务种类（llm / embed / rerank）、机密级规则编号和登录结果，**不含项目代号、用户名、文件名和任何客户内容**（`tests/test_metrics.py` 核对）。

| 指标 | 含义 |
|---|---|
| `cp_http_requests_total` / `cp_http_request_duration_seconds` | 接口请求数和耗时（流式接口含整个输出过程） |
| `cp_upstream_requests_total` / `cp_upstream_request_duration_seconds` | 经网关的模型、向量、重排调用（重试后的最终结果）和耗时 |
| `cp_jobs_total` / `cp_job_duration_seconds` | 后台任务执行结果和耗时（worker） |
| `cp_jobs_by_status`、`cp_workers_online`、`cp_state_up` | 抓取时查询：各状态任务数、在线 worker 数、数据库和 Redis 查询是否成功（backend） |
| `cp_auth_logins_total` | 登录结果：allowed / blocked / locked |
| `cp_guard_blocks_total` | 机密级检测命中（按规则编号） |
| `cp_audit_write_failures_total` | 写审计失败（业务改动已生效、审计没写上） |
| `cp_audit_chain_ok`、`cp_audit_chain_verified_timestamp_seconds` | worker 启动时和之后每小时校验一次审计哈希链的结果和时间（只进指标，不写审计）。backend 也导出这两个量但不校验、恒为 0，查询和告警都要带 `job="worker"`；同理 `cp_workers_online`、`cp_state_up`、`cp_jobs_by_status` 只有 backend 有意义 |

## 2. 启动

```bash
# .env 里设 GRAFANA_ADMIN_PASSWORD（至少 12 位，不设 Grafana 拒绝启动），口令按公司要求保管，不进聊天和文档
docker compose --profile monitoring up -d
# 访问：从堡垒机建 SSH 隧道 ssh -L 3000:127.0.0.1:3000 <运维账号>@<部署机>，浏览器打开 http://127.0.0.1:3000
```

Grafana 用户：管理员账号只给运维；其他人需要看时由管理员在 Grafana 里建 Viewer 账号。改了 `alerts.yml` 或 `prometheus.yml` 后 `docker compose --profile monitoring restart prometheus`；改看板改仓库里的 `platform.json`，界面上不能保存。

检查配置：`docker compose --profile monitoring run --rm --entrypoint /bin/promtool prometheus check config /etc/prometheus/prometheus.yml`（同时检查告警规则，CI 每次跑）。

## 3. 告警

规则在 `alerts.yml`，阈值与压测方案一致。一期不接外部通知渠道：“平台运行”看板顶部“正在告警”面板列出正在触发的告警，运维每天看一次；接入公司告警平台时再加 Alertmanager（新增外部对接要负责人同意）。

| 告警 | 条件 | 级别 |
|---|---|---|
| 后端不可用 | backend 指标端口 2 分钟抓不到 | 严重 |
| 没有在线 worker | 5 分钟 | 严重 |
| 状态查询失败 | 后端查数据库或 Redis 失败 5 分钟 | 严重 |
| 写审计失败 | 15 分钟内有一次 | 严重 |
| 审计链校验未通过 | worker 每小时校验 | 严重，按安全事件处理 |
| 审计链校验停了 | 2 小时没完成 | 警告 |
| 接口 5xx 比例高 | 超过 5% 持续 10 分钟 | 警告 |
| 接口变慢 | 普通接口 p95 > 1 秒持续 15 分钟（不含大模型对话） | 警告 |
| 上游调用失败多 | 某个上游失败超过 20% 持续 10 分钟 | 警告 |
| 后台任务失败 | 1 小时内有任务最终失败 | 警告 |
| 任务积压 | 排队超过 50 条持续 30 分钟 | 警告 |
| 登录失败激增 | 10 分钟超过 20 次 | 警告 |
| 机密级拦截激增 | 1 小时超过 30 次 | 警告 |

处理：严重告警当天处理并记运维记录；审计链校验未通过、登录失败激增当作安全事件，立即报告负责人。

## 4. 不在本项范围

- 主机和容器资源（CPU、磁盘、网络）：用公司已有的主机监控；需要时可另加 node-exporter / cAdvisor。
- 日志集中采集：容器日志已按 ②c 轮转，接公司日志审计系统（部署侧）。
