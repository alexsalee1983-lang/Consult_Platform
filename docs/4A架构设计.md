## 零、一句话定位

**平台不是“用 AI 写报告的工具”，而是公司安全咨询能力的操作系统：把专家的判断变成可复用、可度量、可进化的资产，让每一个项目都比上一个做得更快、更准、更有公司味道。**

公司的竞争力可以写成一个乘式：

> 咨询核心竞争力 = **方法资产**（公司做法、模板、黄金样例） × **依据可信度**（条款准确、时效正确、证据链完整） × **交付效率**（自动化程度） × **客户信任**（数据保护、资质边界）

任何一项为零，整体为零。平台的四个架构分别对这四项负责，所以四项都要建，而不是只做效率。

**三个高度上的判断**

1. **护城河在数据飞轮，不在模型。** 模型会商品化，谁都能接；别人拿不到的是公司历年项目沉淀下来的“这类客户通常卡在哪、哪种整改建议能落地、客户会怎么挑战”。平台每交付一个项目，就要把这类判断自动回流成知识，形成飞轮。
2. **可信是咨询行业 AI 的生死线。** 咨询报告里一个编造的条款号就能毁掉专家形象。所以依据原文只取官方原件、机械切分，模型只写解读，每个引用都机器核对——这是我们和“通用大模型 + 文档”方案的根本区别，要一直守住并做深。
3. **自动化优先，人做只有人能做的事。** 人的时间只花在签字担责、客户沟通、方案取舍、公司经验认可上（决策记录 2026-11-15）。顾问从“写手”变成“判断者和客户关系的经营者”。

**北极星指标**（每个季度在管理看板上看）

| 维度 | 指标 | 2026-12 现状 / 目标 | 2027 年底目标 |
|---|---|---|---|
| 效率 | 一个 D1～D8 交付包从证据齐到初稿齐的人工时 | SOC 跑通 / 5 个产品跑通 | 比纯人工减少 60% |
| 质量 | 首次提交签署的质量门禁通过率；客户评审轮次 | 开始记录 | 门禁一次通过 ≥80%，评审轮次 ≤2 |
| 可信 | 交付件引用核对率；编造条款号次数 | 评测 91.4%、编造 0 | 核对率 ≥98%，编造持续为 0 |
| 资产 | 公司实践条目（L2、L5）数；被交付件引用次数 | 公开知识为主 | 每个核心产品 ≥100 条公司实践，月引用 ≥1000 次 |
| 人才 | 新顾问独立交付所需时间 | 约 2 年 | 1 年 |

## 一、设计原则（在现行七条之上升级为十条）

| # | 原则 | 含义 | 落在哪 |
|---|---|---|---|
| 1 | 客户决定给什么 | 不取客户不给的，客户要删的照办 | 数据架构、删除 |
| 2 | 两档管理 | 标准档便利、严格档不出场 | 业务、数据 |
| 3 | 机密级两档都不收 | 口令、密钥、漏洞细节、拓扑、业务数据和个人信息样本 | guard |
| 4 | 项目与知识分离 | 项目内容只经去标识和审核回流 | 数据分区、工具硬规则 |
| 5 | 依据可核对 | 原文只取官方原件，模型只写解读，引用逐条机器核对 | 知识服务 |
| 6 | 平台编排、Agent 出文字 | 能用确定流程的不用自主 Agent；Agent 读写只经工具层，模型只经网关 | 应用、技术 |
| 7 | 自动化优先、人只处理例外 | 机器多道检查 + 抽检代替逐条人审 | 全部流程 |
| 8 | 生成与评审分离 | 写的 Agent 不评自己；质量评审模拟客户挑战 | Agent 体系 |
| 9 | 一切可度量、可回放 | 每个自动决定记规则、Agent、提示词版本、模型；评测先于上线 | 评测与运营中心 |
| 10 | 资质边界 | 只做差距分析、符合性初判、整改建议，不出具测评、密评、认证结论 | 门禁、提示词 |

### 2.5 能力飞轮：竞争力从哪里长出来

```
   交付项目 ──产出──▶ 交付件 + 顾问手改记录 + 客户挑战 + 评审意见
      ▲                              │
      │                              ▼ 自动萃取（Agent）+ 去标识 + 一人拍板
   更好的初稿 ◀── 知识库 L2/L5（公司做法、异议应答、踩坑、黄金样例、行业基准）
      │                              ▲
      └──── 评测集变严 ──▶ Agent 迭代 ─┘
```

飞轮的五个“自动转动”机制（已有的标 ✓）：

1. ✓ **使用反馈**：顾问删掉 Agent 引用的条目 → 条目进复查（B13）。
2. ✓ **依据变更传导**：依据换版 → 引用它的条目和交付件被提醒（B4、B5、B9）。
3. **手改即信号**【待定】：顾问对 Agent 初稿的改动（版本差异）按章节类型聚类，反复出现的改法由知识库建设 Agent 起草成“公司做法”候选条目，进第三级审核。这是把隐性经验变成显性资产成本最低的方式。
4. **客户挑战沉淀**【待定】：确认卡和评审意见里出现的客户异议，项目结项时自动汇总成异议应答候选（OBJ）。
5. **结项回流预填**（P16）：结项时 Agent 按回流单模板预填“通用做法、判断规则、异议应答、踩坑”，顾问只确认和删改。

### 3.2 Agent 体系：三层结构

现行 13 个 Agent 按交付环节分工（不按领域），这条是对的、要坚持：领域差异放进产品配置和知识标签，Agent 数量不随产品膨胀。目标态把它们明确分成三层：

| 层 | Agent | 职责 | 自主度 |
|---|---|---|---|
| **入口与协调** | 咨询师（顾问对话主入口）、项目交付管理 | 理解顾问意图、转交专业 Agent、管项目节奏 | 对话内可自主调读取类工具（A7） |
| **专业生产** | 调研访谈、依据与差距分析、方案设计、制度起草、报告与汇报；储备：售前方案、新人带教 | 按交付链步骤产出交付件章节 | 平台编排，步骤内只出文字 |
| **守门** | 质量评审与异议应答、知识审核、脱敏审查、知识库建设 | 评审、审核、去标识、起草知识 | 只出意见，决定由平台规则重算 |

**每个 Agent = 公共规范 + 角色骨架 + 产品模块段落 + 模块追加 + 项目卡**，运行时按项目配置快照拼装（C1 已做）。这让“一个 Agent 服务 17 个产品”成立。

**Agent 的生命周期管理（目标态，向软件发布看齐）**

```
改 md / 改产品配置 → 跑 Agent 评测集（黄金样例 + 红线用例）→ 不低于上一版才能合并
 → 生产按提示词版本记每次运行 → 质量门禁通过率、手改幅度按版本统计 → 退化即回滚
```

现在缺的是第二步和第四步：C4 各产品评测集、按提示词版本统计的“手改幅度”。

### 3.3 关键应用流程

1. **交付主流程**：证据齐 → 自动发起交付链 → 各步 Agent 起草（取证据、查依据、写章节）→ 遇到取舍发确认卡、停下 → 顾问处理后继续 → 自动质量评审 → 门禁通过自动提交签署 → 项目经理签署 → 导出。
2. **知识主流程**：官方原件 → 切条核验 → 自动发布（抽检 5%）→ 解读起草（只引用已入库条款）→ 引用核对 → Agent 审核 → 自动发布（抽检 20%）/ 人工队列 → 对比评测门禁。
3. **飞轮流程**：结项 → 回流预填 → 去标识 → 第三级审核 → 发布 → 下一个项目检索时本产品、本行业条目优先。

## 四、数据架构（DA）

### 4.1 数据域

| 数据域 | 内容 | 存放 | 生命周期 |
|---|---|---|---|
| 客户项目域 | 项目卡、证据（D/I/O/S）、交付件章节版本、确认卡、评审、签署、运行记录 | 主库 + 对象存储项目区 | 验收后保留期（默认 6 个月）→ 删除、留删除记录 |
| 知识资产域 | 条目与版本（L1～L5、14 种 doc_type）、依据原文、映射、审核记录、抽检 | 知识区库（分库、独立账号）+ 对象存储知识区 | 复审周期（L4/ENF/BMK 6 个月，其余 12 个月）→ 新版本或下线，历史保留 |
| 配置资产域 | 产品、模块、Agent md、公共规范 | 代码仓（版本化）+ 立项快照 | 随版本发布 |
| 运行与度量域 | 用量、指标、提示词版本、评测结果 | 主库 + Prometheus | 1 年以上 |
| 治理审计域 | 审计哈希链、删除记录、同意记录 | 主库（只追加） | 至少 1 年，删除记录长期 |

### 4.2 两个核心数据模型（深度：竞争力的数据底座）

**① 证据链模型：发现—证据—依据—风险—建议**

咨询报告最常被挑战的是“你凭什么这么说”。目标态把证据链从“正文里的标注”提升为结构化数据：

```
发现(F) ──证据──▶ D-xx / I-xx / O-xx / S-xx（项目区证据，编号不复用）
   │──依据──▶ SRC 条款（文件 + 条款号 + 版本 + 时效）
   │──风险──▶ 影响 × 可能性
   └──建议──▶ 优先级、责任部门、周期、验收标准（四要素）
```

现在 `sources` 已记下每章引用的证据和条目、A10 已从差距分析表解析出能力域和初判；下一步【待定】是把差距分析表的每一行存成“发现”记录，这样可以：每条发现单独追溯、整改跟踪按条推进、结项时按发现聚合成行业基准。

**② 统一控制框架（UCF）：把所有标准接到同一张网上**

```
法规/标准条款（SRC） ──映射(MAP)──▶ 公司控制项（能力域 × 控制目标）◀──映射── 其他标准条款
                                         │
                       ┌─────────────────┼──────────────────┐
                    访谈问题           评估方法           整改建议模板 / 制度条款
```

现在 ISO 27001 ↔ 等保 2.0 管理要求映射 v0 已入库（B3）。目标态以“公司控制项”为中枢，所有标准都映射到它，一次调研就能同时回答多个标准的差距——这是合规类咨询最大的效率来源，也是很难被复制的资产。

### 4.3 数据分级与分区（不变，再强调）

| 级别 | 标准档 | 严格档 |
|---|---|---|
| 机密 | 不收（guard 拦截） | 不收 |
| 敏感（客户制度、纪要、现状问题） | 项目区，按项目隔离 | 不出场；同意后只收摘要卡 |
| 一般、公开 | 直接用 | 直接用 |

项目区与知识区之间只有一条路：去标识（规则 → 脱敏审查 Agent → 知识管理员确认）→ 第三级审核。

### 4.4 数据资产化：行业基准【待定】

公司做过的银行、电力、制造项目越多，“同类客户的成熟度分布、最常见的十个差距”就越有价值，这是售前最有说服力的材料。做法建议：

- 只用结项时去标识的成熟度分数和差距类别（不带客户名、不带原文），按行业和规模区间聚合；
- 一个分组少于 5 家客户不出数（防止反推）；
- 合同告知模板加一句“去标识统计数据用于行业基准”，客户不同意的项目不进；
- 以 BMK 条目入知识库，走第三级审核（决策记录 2026-11-16 已为 BMK 定了类型）。

这件事涉及客户承诺，须负责人和法务确认。

## 五、技术架构（TA）

### 5.1 分层（现行，已在代码里落地）

入口（网页、命令行、worker）→ 编排（runs、autoflow、quality、agent_review、deid_flow、conversations）→ Agent 调用（call.py）→ 工具层（invoke：授权 + 区域硬规则 + 成员检查 + 审计）→ 领域规则（project/*、kb/*）→ 基础设施（网关、guard、存储、任务、审计）。详见 `docs/架构设计.md` 第五节和工具架构图。

### 5.2 模型策略

| 层次 | 现状 | 目标态 |
|---|---|---|
| 路由 | 推理 / 标准 / 轻量三级，按 md 的 model_tier | 加“按任务实测选模型”：每个等级用评测集选当期最好的白名单模型，模型升级先过评测 |
| 工具调用 | 对话内 function calling（A7），交付链平台编排 | 交付链保持平台编排；只在“步骤内多次查依据”处开放受限的 Agent 自主检索 |
| 检索 | 全文 + 向量 + RRF + 重排，依据精确通道，产品/模块加权 | 加 UCF 映射扩展检索（查一个标准时带出映射到的其他标准条款） |
| 模型定制 | 不训练（知识库不是教模型） | 【待定】长期可考虑只用公开知识和已去标识、已发布的公司做法做轻量微调，客户资料永不用于训练；先以评测证明收益再决定 |
| 外部模型 | 只限开发测试 + 虚拟数据，强制假名化，生产拒绝启动 | 保持 |

### 5.3 质量与可信工程（深度：防编造的四道闸）

1. **入库闸**：依据原文只取官方原件，sha256、条号连续、白名单域名，机械切分。
2. **生成闸**：Agent 只能引用库里的条款，查不到写【依据待核实】。
3. **核对闸**：每个引用按“文件 + 条款号”机器核对；时效（已废止、即将实施）进门禁。
4. **评测闸**：有无知识库对比评测，准确率 ≥90%、编造 0，未达标暂停自动发布；模型、md、门槛变化都要先过评测。

目标态加第五道：**客户挑战模拟闸**——质量评审 Agent 按高管、业务、审计、技术四类角色出挑战，挑战答不上的章节标“重要”。

### 5.4 安全架构

- 等保第三级建设与测评、密评（公司安全部门办理）；
- 三权分立（系统管理员、审计员、业务角色互斥），项目非成员 404；
- OWASP 大模型应用十大风险：资料一律作为数据传入（防提示注入）、工具按 Agent 白名单授权、写入类工具只由平台运行时调用、输出过机密级和资质边界检查；
- 审计哈希链只追加、不记原文；
- 供应链：依赖固定版本，CI 做代码、依赖、镜像扫描；不引入联网的 AI 库。

### 5.5 部署与扩展演进

| 阶段 | 规模 | 架构 |
|---|---|---|
| 二期（现在） | 10 人在线、知识几千条 | 2 台服务器、无 GPU、单机 compose，主库与知识区分库 |
| 2027 | 30～50 人、知识数万条 | 应用层双机 + 负载均衡；PostgreSQL 主备；worker 按任务类型分池；知识区检索若超出 pgvector 能力再引入 OpenSearch |
| 2028【待定】 | 多团队、多地区 | 出海项目若有数据本地化要求，按地区部署知识只读副本，项目区留在当地 |
