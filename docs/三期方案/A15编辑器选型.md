关键推论：正文的“真相”是一段带方括号标记的 Markdown 文本，后端解析、导出、门禁都依赖它。任何编辑器必须做到读入文本与写出文本逐字节一致（往返无损）。这一条使所有“富文本模型再序列化回 Markdown”的方案先天吃亏。

## 2. 评判维度

D1 正文保持 Markdown 且往返无损（硬）；D2 来源标注显示为不可误删的标签；D3 选区 API（选中即改、diff 回退）；D4 `@`、`[` 自动补全；D5 在原文锚定批注；D6 中文输入法稳定；D7 离线、无联网无遥测无 CDN（红线 2，硬）；D8 许可证；D9 包体积；D10 维护活跃度；D11 React 18 + Vite 集成；D12 版本可固定（硬）。

## 3. 候选对比

### 3.1 CodeMirror 6（`@codemirror/*`，MIT）

- D1：文档模型就是纯文本（`EditorState.doc`），读写即 Markdown 原文，无序列化环节，往返无损天然成立。
- D2：`Decoration.replace` + `WidgetType` 把 `[I-01]` 渲染成标签，`EditorView.atomicRanges` 让光标和退格把它当整体。底层文本不变，复制出去仍是 `[I-01]`。
- D3：`state.selection.main`、`sliceDoc(from,to)`、`coordsAtPos` 一手 API；选中后浮层、`dispatch({changes})` 替换区间，事务可撤销，适合选中即改和回退。官方 `@codemirror/merge` 提供统一或并排 diff。
- D4：官方 `@codemirror/autocomplete`，`@` 与 `[` 各写一个补全源，数据来自证据与知识库接口。
- D5：`RangeSet`/`Decoration.mark` 随编辑自动映射位置，`ChangeSet.mapPos` 可把旧版本偏移映射到新版本；批注存后端，存“章节版本 + 起止偏移 + 原文摘录哈希”。
- D6：contenteditable，自带 IME 组合处理，6.x 对中文输入法长期稳定；个别平台（旧 Safari、部分 Linux IBus）曾有组合边界问题，需测试机验证（待核实）。
- D7：纯本地库，无网络请求、无遥测、无字体或 CDN 依赖。
- D8：MIT。D9：核心加 markdown、autocomplete 约 gzip 100 至 140 KB（待核实）。D10：活跃，发布稳（待核实最新版本）。
- D11：不必用 React 封装，约 40 行 `useEffect` 挂载 `EditorView` 即可（不用 `@uiw/react-codemirror`，少一层依赖）。D12：精确版本可固定，但多个包互相约束，需整组锁，`@codemirror/state` 全仓只能有一份。
- 缺点：不是所见即所得，用户看到 Markdown 源码（可用装饰弱化 `#`、`**`），见第 7 节问题 1。

### 3.2 Milkdown（MIT，ProseMirror + remark）

- 所见即所得 Markdown 编辑器，文档树经 remark 序列化。D1 风险：序列化会规范化列表符号、强调符号、转义、空行、表格；`[I-01]` 可能被当链接引用或转义成 `\[I-01\]`，必须写自定义 remark 插件与节点保护，长期有回归风险。
- D2：原子内联节点可做，体验好。D3、D5：ProseMirror 选区与 `Mapping` 成熟。D4：官方有 slash 插件，`[` 触发需自写。D6：ProseMirror IME 总体成熟，自定义节点交界处有已知问题（待核实）。D7：本地无遥测。D8：MIT。D9：gzip 约 150 至 250 KB（待核实）。D10：活跃。D11：官方 React 封装。D12：可固定，但插件多、版本耦合多。

### 3.3 TipTap（开源核心 MIT，不用 Cloud 与 Pro 扩展）

- 同为 ProseMirror。注意评论、AI、协作云等 Pro/Cloud 扩展为付费或闭源，npm 需私有令牌，**不得使用**。
- D1：Markdown 支持历史上非一等公民（较新版本有官方 Markdown 扩展，待核实），同样存在规范化与方括号转义问题。D2、D3、D5：能力同 ProseMirror，文档最丰富。D4：`@tiptap/suggestion` 支持 `@`，`[` 可配。D6：同 ProseMirror。D7：核心无遥测，但须审计依赖树不拉入云相关包。D8：核心 MIT。D9：gzip 约 120 至 220 KB（待核实）。D11、D12：官方 React 封装，可固定。
- 额外风险：开源与商业边界随产品线变化，合规审查成本高于 CodeMirror。

### 3.4 Lexical（Meta，MIT）

- D1：自有状态树，Markdown 经 `@lexical/markdown` 转换，不逐字节往返，对表格、嵌套列表、方括号覆盖不如 remark，需自写 transformer。
- D2：`DecoratorNode` 可做标签。D3：选区 API 完整但底层。D4：有 typeahead 范例，需自写。D5：无现成区间锚点映射机制，需自维护。D6：有专门 IME 实现，部分输入法仍有问题报告（待核实）。D7：无遥测。D8：MIT。D9：gzip 约 80 至 120 KB（待核实）。D10：Meta 维护，仍 0.x，API 变动风险高。D11：React 优先。D12：可固定，但 0.x 破坏性变更多。

### 3.5 BlockNote

- 块编辑器（类 Notion），基于 TipTap 与 ProseMirror。许可证：核心 MPL-2.0，XL 包为 GPL-3.0 或商业（待核实），非 MIT/Apache。数据模型是块 JSON，Markdown 为有损导入导出，D1 不满足，且块结构与“章节整体 Markdown”冲突。自带 Mantine 样式，与 `theme.css` 令牌体系冲突。gzip 约 300 KB 以上（待核实）。
- 结论：淘汰。

### 3.6 对照：保留 textarea + 增强

- D1 完美、D6 最稳、D7 无依赖、体积 0。D2 做不到（textarea 内无法渲染标签，只能旁置预览，防误删只能保存时校验提示）。D3 `selectionStart/End` 可用，但浮层定位需镜像 div，脆弱。D4 需自造镜像层与弹层。D5 不可行。
- 结论：作兜底和对照，不满足 A15 的“来源标注显示为标签”，撑不住 A16、A22。

## 5. 推荐方案

推荐 **CodeMirror 6**（Markdown 源码模式 + 来源标签装饰），textarea 保留为兜底。

理由：
1. D1 是硬要求，后端正则解析、核对、导出脚注、质量门禁都依赖正文文本。CodeMirror 文档模型即文本，往返无损天然成立；ProseMirror 与 Lexical 系都要为方括号标记和 Markdown 规范化写保护逻辑并长期承担回归风险。
2. A16、A22 需求（选中即改、diff 与回退、`@` `[` 补全、原文锚定批注）都有官方或一手能力：选区 API、`@codemirror/merge`、`@codemirror/autocomplete`、可映射的 `RangeSet`。
3. MIT、无遥测、纯本地、可固定、体积小，合规审查最简单。
4. 与现 textarea 数据契约相同（字符串进、字符串出），新旧并存与回退成本最低。

代价：界面是“Markdown 源码 + 标签与弱化装饰”，不是所见即所得。缓解：审阅页保留只读渲染预览；若负责人要求所见即所得，退而选 TipTap 开源核心并自写往返测试（见第 7 节问题 1）。

### 5.1 功能落点（按期）

- 三期 A15：CodeMirror 编辑器组件（Markdown 高亮、令牌主题、来源标签装饰与原子删除）；写稿侧栏“插入保留来源”即在光标处 `dispatch` 含标注的文本。
- 四期 A16：选中浮层（选中即改，Agent 返回后用 `merge` 视图展示前后、接受或回退）；`@` 引用证据与知识库条目，`[` 补全来源编号。
- 五期 A22：评审意见锚点（装饰 + 位置映射；后端存版本号、起止偏移、原文摘录哈希；版本变化后用 `ChangeSet` 或哈希重定位，失败降级为章节级批注）；“应用修改建议”即对锚点区间发 `changes`。

## 6. 迁移步骤（新旧并存一个关口，正文格式不变）

1. A15 第 1 天：核实各包最新稳定版、体积（`vite build` 前后对比）、已知 IME 问题，确定固定版本。
2. 新增 `frontend/src/components/DocEditor.jsx`，接口与 textarea 同形（`value`、`onChange(text)`、`placeholder`），内部挂载 `EditorView`；外部值与文档不同才 `dispatch`，避免光标跳动。
3. 来源标签前端正则与后端 `_EVIDENCE_REF`、`_KB_REF`、`_INFERRED` 保持一致，新增一致性测试（同一批样例，前后端匹配结果相同）。标签颜色用令牌（证据 `--cyan`、知识库 `--vio`、推断 `--amber`，核对不上 `--crim`）。
4. `Deliverable.jsx` 加“新编辑器”开关（默认关），编辑区按开关渲染 `DocEditor` 或原 textarea；两者读写同一字符串、同一保存接口，**后端不改**。
5. 并存期（一个关口）：内部试用默认开启，保留一键切回；出问题立即回退，不涉及数据迁移。
6. 往返测试：用存量交付件虚拟样例（BANK-A、GRID-B、MFG-C 的章节）做“载入、不编辑、取出”逐字节相等断言；再测插入、删除标注、粘贴、撤销重做后的文本。
7. 中文输入法专项（测试机）：微软拼音、搜狗、五笔，覆盖标签前后输入、组合输入中点击、选词时退格；Windows 与 macOS 浏览器各过一遍。
8. 关口结束：稳定后移除旧 textarea 分支（单独小 PR，可回退）。

## 7. 风险与需负责人拍板的问题

风险：
- R1 IME：contenteditable 个别输入法可能有组合异常；并存期保留回退并做专项测试。
- R2 标签与光标：原子范围内删除、选择、复制行为要明确（复制得到原文标注）；写专门测试。
- R3 包间版本约束：`@codemirror/state`、`view` 重复安装会使扩展失效；精确版本并在构建后检查依赖树只有一份。
- R4 体积：约新增 100 至 140 KB gzip（待核实）；仅交付件审阅页 `React.lazy` 按需加载。
- R5 可访问性：contenteditable 读屏支持弱于原生 textarea；保留 textarea 兜底缓解。
- R6 红线 2：不得引入带联网能力的包（TipTap Cloud、Pro 扩展、BlockNote XL 等）；CI 构建后检查产物无外链，字体图标全部本地。
- R7 锚点漂移（五期）：多版本间批注重定位不可能 100% 准确，需明确“降级为章节级批注”的产品行为。

需负责人拍板：
1. 是否接受“Markdown 源码模式 + 标签装饰”而非所见即所得？若必须所见即所得，走 TipTap 开源核心路线，并追加方括号保护与往返测试工作量（A15 约增加 3 至 5 个工作日，待评估）。
2. 并存期新编辑器默认开启（内部试用）还是默认关闭、手动开启？
3. 标签误删保护强度：原子整体删除（推荐）还是再加“删除来源标注需确认”？
4. A15 是否只换交付件编辑区，对话输入框保持 textarea（建议保持）？
