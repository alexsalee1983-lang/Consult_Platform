## 0. 结论先行

1. 新增知识区表 `kb_item_labels`（条目 × 维度 × 取值），用来存产品、行业、控制项、能力域、一级目录和检索标签。不用数组列，因为 PostgreSQL 和 SQLite 的数组/JSON 查询写法不一样，标签表两边写法相同。
2. 新增 `kb_item_aliases`（别名 → 条目，永久保留）。新 doc_id 是不带分类含义的稳定序号（建议 `KB-000123`），旧编号 `L2-OPS-SOC-TPL-007` 全部登记成别名。
3. 主库里的旧引用一律不改写，包括已签署交付件的 `section_versions.sources`、正文，以及对话消息的 `kb_refs`。所有读取点都改走同一个解析函数 `kb.refs.resolve()`，靠它保证不改也能用。
4. 知识区迁移链 k0010～k0012 分三步走，每步都有 downgrade。过渡期 `layer / domain / product / doc_type` 四列保留，用作“主分类”，回滚靠它们重新算出旧编号。
5. 拆 3 个 PR：①解析层和引用校验基线（不改数据）→ ②多值标签 → ③换 doc_id。第③个 PR 合并前必须做到：`kb-ref-check` 迁移前后对比零差异，已签署交付件的引用全部可解析。

## 2. 目标表结构

### 2.1 标签表还是数组列

| 方案 | PostgreSQL | SQLite 测试 | 原生 SQL 检索过滤 | 回滚 | 结论 |
|---|---|---|---|---|---|
| JSON 列（现状） | `jsonb ?` / `@>` | `json_each` | 两边要写两套 | 简单 | 不选 |
| PG `ARRAY` | `&&`、GIN | 不支持 | 测试跑不了 | — | 不选 |
| **标签表 `kb_item_labels`** | 普通 B-tree 索引 | 同 | `EXISTS (SELECT 1 FROM kb_item_labels …)` 两边写法相同 | drop 表、回写列 | **选** |

### 2.2 `kb_item_labels`（k0011）

| 列 | 类型 | 说明 |
|---|---|---|
| `item_id` | FK `kb_items.id` ON DELETE CASCADE | |
| `kind` | String(16) | `product` / `industry` / `control` / `capability` / `domain` / `tag` |
| `value` | String(64) | 规范化后的取值（产品缩写、行业名、控制项编号大写、标签原样） |
| `source` | String(16) default `manual` | `manual`（条目文件 / 界面）/ `legacy`（迁移回填）/ `derived`（B19 由控制项推出） |
| 主键 | (`item_id`, `kind`, `value`) | 去重 |
| 索引 | (`kind`, `value`, `item_id`) | 按标签找条目 |

规则（写在 `app/kb/labels.py`，由 `items.py` 统一写入，其他模块只读）：
- 产品：取值必须在 `meta.PRODUCTS` 里，可以填多个。**`GEN` 保留为显式取值**，表示通用，不用“空集合”表示通用（检索的 `scope` 逻辑和覆盖矩阵都依赖它）。`GEN` 不能和具体产品同时出现。
- 行业：沿用 `industries` 的中文取值，新增 `meta.INDUSTRIES` 取值表校验（现在是自由文本，需要先统计现有取值，见 4.3），“通用”同样不和具体行业同时出现。
- 控制项：沿用 `items.check_control_ids` 的规则。B19 落地前只校验格式，落地后校验必须在控制项中枢里存在（见第 8 节）。
- 能力域、一级目录：从“分类字段”改成“视图维度”，见 2.4。
- 标签是条目级的，同 tags 和 control_ids 一样不进版本内容、不走审核。**例外：产品和行业改动要记审计**（只记 kind、取值和条目编号）。理由：这两项决定检索范围和 A12 装配结果。

### 2.3 `kb_items` 列的去留

| 列 | 过渡期（三期） | 四期以后 |
|---|---|---|
| `doc_id` | 改为新序号 `KB-000123` | 不变 |
| `layer`、`doc_type`、`stage` | 保留单值，不进标签（层级和类型决定审核流程和复审周期，本来就是单值） | 保留 |
| `product`、`domain` | 保留，改名语义为“主产品”“主目录”，写入时取标签里的第一个，**只给回滚和旧报表用，新代码不再读** | 视情况删除（单独迁移，须负责人同意） |
| `industries`、`capabilities`、`tags`、`control_ids`（JSON） | 保留并双写，**读取以标签表为准** | 同上 |

### 2.4 一级目录、能力域改为视图（k0012）

- 建数据库视图 `kb_v_item_facets`（`op.execute("CREATE VIEW …")`，PG 和 SQLite 都支持）：每个条目一行，输出 `item_id, doc_id, layer, doc_type, products, industries, domains, capabilities, controls`。
- 多值列用 `string_agg`（PG）或 `group_concat`（SQLite）拼接。两边函数名不同，迁移里按 `op.get_bind().dialect.name` 分支，**只有这一处分支**。
- `domains` 和 `capabilities` 的来源：B19 落地前取 `kind='domain' / 'capability'` 的 legacy 标签；B19 落地后改成 legacy 标签与“控制项 → 目录 / 能力域”推导结果的并集（推导结果写成 `source='derived'` 的标签，由 B19 的程序维护，视图定义不用改）。
- 条目文件里的 `domain`、`capabilities` 仍然接受（兼容），但不再是必填，也不再参与编号。界面“知识地图 / 按目录看”改为读视图。

### 2.5 `kb_item_aliases`（k0010）

| 列 | 类型 | 说明 |
|---|---|---|
| `alias` | String(40) 主键 | 旧编号或其他历史编号 |
| `item_id` | FK `kb_items.id` | |
| `kind` | String(16) | `legacy`（B15 换号）/ `transfer`（跨环境迁移时对方的编号）/ `merge`（以后合并重复条目） |
| `created_at` | DateTime | |

约束：
- 别名**永不删除**，条目下线后别名照样能解析，解析结果是“已下线”。
- `alias` 与 `kb_items.doc_id` 在代码层互斥（`labels.py` / `refs.py` 写入时检查）。新格式 `KB-\d{6}` 和旧格式的正则不相交，所以按格式不可能冲突，只需要防 transfer / merge 别名的重复。

## 3. 解析路径：旧编号不改也能用

### 3.1 统一入口 `app/kb/refs.py`（PR①新增）

- `REF_PATTERN`：一个正则同时认新旧两种格式：`L[1-5](?:-[A-Z0-9]{2,8}){3,4}-\d{3,5}` 或 `KB-\d{6}`。4 处写死的正则（1.2 A）全部改为引用它。前端 `DocBody.jsx` 只能复制一份，另加一条测试，校验前后端正则的源码字符串一致。
- `resolve(db, refs) -> dict[str, Resolved]`：`Resolved = {item_id, doc_id（现行编号）, via: "doc_id" | "alias", retired, current_version_id, layer}`。先按 `kb_items.doc_id IN (...)` 查，没命中的再按 `kb_item_aliases.alias IN (...)` 查。两次查询都在知识区库里完成，**不跨库 JOIN**（分库约定）。
- `canonical(db, refs) -> dict[str, str]`：ref → 现行 doc_id，用来聚合计数。
- 可见性不在这里判断，调用方照旧按 `visible_roles` 过滤。

### 3.2 各使用点改法（全部在 PR①，行为不变，因为 PR①时还没有别名数据）

| 使用点 | 改法 |
|---|---|
| `deliverables.parse_sources` | 用 `refs.resolve` 核对。`sources.knowledge` 仍存**正文里写的原样 ref**，另加一个可选字段 `doc_id`（现行编号）。旧记录没有这个字段，读的时候现场解析 |
| `export.py` 脚注 | 用 `refs.resolve` 取标题。正文里的编号原样输出，不替换（已签署文本不能变） |
| `cards.py` 严格档剔除 | 改用 `REF_PATTERN` |
| `kb_impact._kb_state` / `usage_counts` | 先 `canonical` 再比较。`usage_counts(doc_id)` 改成按条目的“现行编号 + 全部别名”去匹配 |
| `quality.cited_kb_refs` / `kb_ref_states` | 用 `resolve`；签署门禁判 gone 的条件改为“解析不到，或者解析到的条目已下线 / 没有现行版本”，和现状语义一致 |
| `recheck.usage` | 按 `canonical` 聚合，cutoffs 的键用现行编号 |
| `api/kb_items._item` | 路径参数先 `resolve`。**按别名访问时直接返回结果，不做重定向**，响应里带 `doc_id`（现行编号）和 `aliases`。可见性判断和 404 / 403 的语义不变 |
| `api/kb_items` 列表的模糊搜 | 同时匹配别名 |
| `transfer.py` | manifest 增加 `aliases`。生产导入时：原 doc_id 如果是旧格式，就登记为别名（`legacy`）；如果是新格式且没被占用，就沿用；被占用的登记为 `transfer` 别名 |
| `search.Hit` / `chat_tools` / `knowledge.py` | 给 Agent 的一律是现行编号。`conversation.kb_refs` 的旧数据只用于展示，前端点击时走 `_item` 的别名解析 |

### 3.3 Agent 侧

- 检索结果只给新编号，Agent 照抄就行。万一 Agent 写出旧编号（比如来自历史项目卡或顾问粘贴），也能通过别名解析成功，不会算成编造。
- 新编号不带含义，Agent 不会再按格式“猜”一个像样的编号。但如果编造的 `KB-xxxxxx` 恰好碰上一个真实条目，仍会被核对成 found。这个风险现状就有，B15 不加剧。缓解办法写在第 7 节。

## 4. 迁移步骤（知识区链，k0010 起；编号先占位，动手前告知开发线 2）

### 4.1 `k0010_kb_aliases`（PR①）

- upgrade：建 `kb_item_aliases` 表，不回填。
- downgrade：drop 表（PR①阶段表一定是空的）。

### 4.2 `k0011_kb_labels`（PR②）

- upgrade：
  1. 建 `kb_item_labels`。
  2. 回填，`source='legacy'`，逐行用 Python 处理，不写方言 SQL：
     - `product` → `kind=product`（单值变成一个元素）；

     - `tags` → `kind=tag`。
  3. 回填后自检：每个条目至少有 1 个 product、1 个 industry 标签，否则迁移失败、整体回滚。PG 的 DDL 有事务；SQLite 测试库失败就重建。

### 4.3 `k0012_kb_doc_id`（PR③）

- 迁移前：跑 `kb-ref-check --snapshot before.json`（第 5 节）。
- upgrade：
  1. 给 `kb_items` 加 `seq Integer unique`，按 `id` 升序回填 `seq = id`。这样编号稳定，不依赖排序规则，同一库里重跑结果一致。
  2. 每行插入别名 `(alias=原 doc_id, item_id, kind='legacy')`。
  3. `doc_id = 'KB-' || 6 位补零的 seq`。补零在 Python 里拼字符串，避免 PG 的 `lpad` 和 SQLite 写法不同。
  4. 建视图 `kb_v_item_facets`（2.4）。

### 4.4 主库

主库**没有迁移**。`sources.knowledge[].doc_id` 是 JSON 里的可选字段，不改表结构。旧记录不回填，保证 `body_sha` 和已签署快照不动。

### 4.5 环境顺序

1. 测试机环境 A：先跑 PR③全流程，包括 upgrade、校验、downgrade、再 upgrade、再校验。
2. 环境 B：在 A 跑完的基础上验证 transfer 的别名。
3. 生产：按 `docs/部署手册.md` 先备份知识区库（`docs/备份与恢复.md`），后端启动时自动升级，然后人工跑 `kb-ref-check --compare`。

## 5. 引用校验脚本 `kb-ref-check`

`python -m app.cli kb-ref-check [--snapshot <out.json>] [--compare <before.json>] [--signed-only]`，只经 `app/kb/refcheck.py`。只读，不调模型，不联网。

### 5.1 扫描范围（主库读、知识区库解析，分两次查询，不跨库 JOIN）

| 来源 | 取法 | 是否必须全部通过 |
|---|---|---|
| 已签署交付件 | `sign_offs.action='sign'` 的最新一次，用 `versions` 快照取章节版本：① `sources.knowledge` 存的 ref；② 用 `REF_PATTERN` 重扫 `body` 得到的 ref | **必须** |
| 其他交付件章节版本 | 全部 `section_versions` 的 ①② | 必须（但未签署的允许“迁移前就解析不到”） |
| 对话消息 | `conversation_messages.kb_refs[].doc_id` | 报告，不阻断 |
| 运行记录 | A12 合并后的 `agent_run_steps.refs.knowledge` | A12 之后变为必须 |
| 导出脚注 | 对已签署交付件调用 `export` 的标签生成函数（不生成 Word），取 `{ref: 标签}` 的哈希 | **必须**前后一致 |

### 5.2 每个 ref 的输出（只记编号，不记正文，红线第 4 条）

`{ref, source_kind, project_id, deliverable_id, section_seq, version, signed: bool, item_id, current_doc_id, via, retired, current_version}`。快照文件里有项目 id，所以**只能放在测试机或部署机本地**，不提交、不贴原文进 PR 评论；PR 评论只贴计数。

### 5.3 对比规则（`--compare`）

对每个 `(source, ref)`：
- 迁移前 found → 迁移后必须 found，且 `item_id` 相同（`item_id` 主键不会变）；
- `retired` 和 `current_version` 必须相同（迁移不改版本）；
- 已签署交付件的 ①② 两个集合在迁移前后都必须相等（证明新正则对旧正文抽取结果完全一样）；
- 导出标签哈希必须相同。

输出分 4 类计数：一致、迁移前后都解析不到（列编号，留给人工）、**退化**（之前 found、之后不 found，或者 item 变了）、新增 found。**退化 > 0 时退出码非零**，这就是“全部通过才合并”的判定。

### 5.4 测试和演练数据

- pytest：用虚拟项目 BANK-A、GRID-B 造一个已签署交付件，引用 3 个旧编号的条目（其中 1 个已下线、1 个依据已废止）。依次跑 upgrade → check → downgrade → check，断言零退化。
- 测试机：在现有虚拟项目数据上跑真实快照对比。结果按 `docs/测试交接规范.md` 写进 PR 评论，只写计数。

## 8. 与 B19、A12 的接口约定

### 8.1 B19 控制项中枢 v0

- 中枢表放在知识区库（知识侧数据，交付侧只读）。建议表名 `kb_controls`（`control_id` 主键、名称、目录、能力域、状态）和 `kb_control_maps`（控制项 ↔ 等保 2.0 / ISO 27001 附录 A / CSF 2.0 / SOC-CMM / SP 800-61 / 行业条款，关系类型和置信度跟 C12 对齐）。迁移编号由 B19 自己从 k0013 起申请。
- B15 和 B19 的边界：条目挂控制项的数据就是 `kb_item_labels(kind='control')`，B19 **不另建**条目与控制项的关联表。B19 落地后，`labels.check_control` 从“只校验格式”改成“必须在 `kb_controls` 里、状态有效”；k0008 留下的 JSON 列 `control_ids` 只双写，不再读取。
- 视图维度：B19 按 `kb_controls.domain / capability` 给条目写 `source='derived'` 的 domain 和 capability 标签（条目控制项变更时重算），`kb_v_item_facets` 自动带上，不用改视图。
- 控制项编号改名时，B19 给控制项另做别名，**不复用** `kb_item_aliases`（那张表只管条目）。

### 8.2 A12 按知识清单装配

- B15 提供只读查询 `labels.match(db, user, *, products, industries=(), controls=(), layers=(), doc_types=(), stage="") -> list[MatchedItem]`。只返回已发布、未下线、调用人看得到的现行版本，口径同 `search.py`。`products` 自动带上 GEN，`industries` 自动带上“通用”。`MatchedItem = {doc_id（现行编号）, version, layer, doc_type, matched: {kind: [values]}}`。
- 槽位声明（产品配置里，A12 定格式）引用的是标签取值（产品缩写、行业名、控制项编号），**不引用 doc_id**；需要指定某个条目时用 `import_key`。这样换编号、合并条目都不影响配置。
- 运行记录：A12 在 `agent_run_steps.refs["knowledge"]` 记录 `[{doc_id, version, slot}]`，一律用现行编号。`kb-ref-check` 从 A12 合并起把这一项纳入必须通过的范围。
- 就绪度和缺口：`labels.coverage(products, industries, controls) -> {slot: count}` 给 A12 立项提示和“知识不足”卡使用，也给知识地图（B6）共用同一个统计口径。
- 权限边界不变：`labels.match` 由平台程序在交付链里调用，或者作为工具开放给交付侧 Agent，只读知识区；知识侧 Agent 不经它读项目区。
