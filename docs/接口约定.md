# 二期接口约定

> 二期开工关口（`docs/二期开发计划.md` 第五节）的共同输入：开发线 1 按它写校验和平台代码，开发线 2 按它写配置草稿、知识和 Agent md。**由开发线 1 起草、负责人确认后生效**；改动走 PR，两条线都要知会。状态：草案（2026-11-14）。

本文件约定五件事：产品与模块配置格式（A1）、立项快照（A3）、`kb.search` 的产品参数（B2）、`kb.mapping` 工具（B3）、Agent md 的产品段与模块段（C1）。

## 一、术语

| 词 | 含义 |
|---|---|
| 产品 | 服务目录里的核心产品，如 SOC 运营体系设计。一个项目只属于一个产品 |
| 模块 | 挂在产品上的专项，如等保 2.0 整改。一个项目可以勾 0 个或多个模块；模块不单独建交付链 |
| 产品代号 | 2～6 位大写字母，与知识元数据“服务产品”取值（`app/kb/meta.py` 的 `PRODUCTS`）同一套 |
| 模块代号 | 2～8 位大写字母、数字和连字符 |
| 配置版本 | 配置文件规范化后内容的 sha256 前 12 位，平台计算，不手写 |

产品和模块代号（二期）：

| 代号 | 名称 | 类别 |
|---|---|---|
| SOC | SOC 运营体系设计 | 产品（已有） |
| ISO | ISO 27001 认证咨询 | 产品 |
| DSM | 数据安全管理体系 | 产品 |
| IRE | 事件后 E2E 评估与整改 | 产品 |
| NSG | 网络安全治理规划 | 产品（不用 GOV，避免与一级目录代号 GOV 混淆） |
| DJBH | 等保 2.0 整改与体系建设 | 模块 |
| REG-FIN / REG-PWR | 行业监管专项（金融 / 电力） | 模块 |
| REDTEAM | 实战攻防演练支撑 | 模块 |

`GEN`（通用知识）只用于知识元数据，不是产品配置。知识元数据扩充上表的产品代号要同步公共规范第 7 节，经负责人同意（二期计划第十节修订 ③）。

## 二、产品配置 `products/<代号>.yaml`

文件名小写，如 `products/soc.yaml`。UTF-8，不写客户信息，不写标准全文（只写条款号）。

```yaml
code: SOC                        # 必填，与文件名一致
name: SOC 运营体系设计             # 必填
domain: OPS                      # 必填，知识库一级目录代号（meta.py DOMAINS：GOV / CMP / DAT / OPS / RES / ARC）
status: ready                    # ready 可立项 / draft 草稿（不能立项，CI 只校验格式）
modules: [DJBH, REG-FIN, REG-PWR, REDTEAM]   # 可勾选的模块

deliverables:                    # 必填，编号 D1 起连续，至少 1 个
  - code: D1
    title: 启动包
    stage: 启动                   # 启动 / 调研 / 评估 / 设计 / 汇报 / 验收
    client_facing: true          # 是否交给客户（影响质量规则“对客用语”）
    outline: [项目范围, 工作计划, 沟通机制]   # 默认大纲，可空；立项后顾问可改
  # …… D2～D8

baseline:                        # 评估基线与维度
  domains: [组织与人员, 流程, 技术平台与数据源, 度量与改进]   # 事实清单分章、差距分析的能力项
  frameworks: [SOC 能力框架, 等保 2.0, 行业要求]             # 对标框架（写进提示词）
  basis: ["GB/T 22239-2019"]     # 依据集合：标准号或法规名，basis.lookup 优先查这些

chain:                           # 交付链步骤，按顺序执行
  - key: facts                   # 步骤键，本文件内唯一，小写字母和下划线
    number: 3                    # 交付链第几步（界面显示）
    name: 整理事实清单
    agent: research-interview    # 必须是已登记的交付侧 Agent，且有 doc.generate 授权（写交付件时）
    inputs: [evidence]           # evidence = 本项目证据（严格档为摘要卡）；D3 = 交付件当前版本；run:gap = 本次运行某步产出
    output: D3                   # 写入的交付件；空 = 产出存运行记录
    query: "{product_name} 现状 事实 调研"     # 知识检索词模板
    instruction: |               # 提示词模板，变量见下
      任务：交付链第 {number} 步。根据下面的本项目证据，整理 D3 事实清单：按 {product_name} 能力域（{domains}）分章列出……
  # gap（第 4 步）、draft（第 7 步）、二期补 D5～D8 的步骤

gates:                           # 产品质量门禁规则（通用规则在平台代码里，不写在这里）
  - id: soa-annex-a              # 规则编号，产品内唯一
    kind: coverage               # 规则类型，见下
    deliverable: D5
    items_file: rules/iso27001-annex-a.txt     # 或 items: [...]
    level: blocking              # blocking 阻断 / major 重要
    message: SoA 未覆盖附录 A 的全部控制项

strict:                          # 严格档（二期计划 A8）
  card_items: [安全组织, 监测能力, 事件响应, 度量与改进]   # 摘要卡“评估项”可选值；空 = 不限
```

**提示词模板变量**：`{product_name}` `{domains}` `{frameworks}` `{basis}` `{number}` `{modules}`（勾选模块的名称），以及 `{module_instructions}`（勾选模块对本步追加的说明，拼在末尾）。只允许这些变量，未知变量 CI 报错。平台固定的 `OUTPUT_RULES`、`STRICT_RULES` 和资质边界说明不进配置，由平台拼接。

**门禁规则类型**（配置只能选类型、填参数，不能写代码）：

| kind | 参数 | 判定 |
|---|---|---|
| `coverage` | `deliverable`、`items` 或 `items_file` | 交付件正文必须出现清单里的每一项（如附录 A 控制号） |
| `required_sections` | `deliverable`、`sections` | 大纲必须含这些章节标题 |
| `forbidden_terms` | `deliverable`（空 = 全部）、`terms` | 正文不得出现这些说法 |
| `min_sources` | `deliverable`、`min` | 每章来源标注不少于 min 个 |

**校验（CI 测试，开发线 1 写）**：字段齐全、代号格式、D 编号连续、`chain` 引用的 Agent 和交付件存在、`inputs` 只引用前面的步骤、模板变量合法、`modules` 里的模块存在且模块声明可挂本产品、`items_file` 存在、`status: ready` 的产品每个交付件有 `stage`。

## 三、模块配置 `modules/<代号>.yaml`

```yaml
code: DJBH
name: 等保 2.0 整改与体系建设
status: ready
products: [SOC, ISO, DSM, NSG]   # 可挂的产品（与产品的 modules 两边都写，CI 核对一致）
adds:
  sections:                      # 往交付件默认大纲追加章节（按产品写）
    SOC: {D5: [等保 2.0 整改专项]}
  frameworks: [等保 2.0 第三级]   # 追加对标框架
  basis: ["GB/T 22239-2019", "GB/T 25070-2019"]
  instructions:                  # 对某个步骤追加说明（按步骤键）
    gap: 对照第三级安全管理要求逐项列差距……
  gates: []                      # 同产品 gates 的格式
  card_items: [等保整改]
  kb_tags: [等保]                # 检索加权标签（B2）
```

## 四、立项快照（A3）

- 立项（网页或命令行）选一个 `status: ready` 的产品，勾 0 个或多个它允许的模块；严格档、标准档照旧必选。
- 平台把**合并后的完整配置**（产品 + 所选模块的追加项）存进项目快照表 `project_configs`（开发线 1 写迁移）：`project_id`、`product`、`modules`、`product_version`、`module_versions`、`snapshot`（JSON）。交付链、门禁、检索、提示词都只读快照，不读当前文件。
- 快照立项后不变；二期不提供“升级到新配置”。配置改版只影响之后立项的项目。
- 一期已有项目由迁移补成产品 = SOC、无模块，快照取 A2 搬出的 `products/soc.yaml`。`projects.service` 保留为显示名。
- 项目接口返回体加 `product`、`modules`、`product_version`；交付件清单按快照返回，界面不再假定 D1～D8 固定。

## 五、`kb.search` 的产品参数（B2）

现有参数不变：`query`、`layer`、`product`、`stage`、`doc_type`、`limit`。二期改两点：

1. **`product` 默认取项目快照**：Agent 在项目上下文里调用且没传 `product` 时，平台用项目的产品代号；显式传入的以传入为准。
2. **排序**：先查本产品，再查通用（`GEN`），本产品条目优先；项目勾了模块时，带模块 `kb_tags` 标签的条目加权（知识条目现在没有标签字段，B2 在知识区迁移链里加 `tags`，条目文件格式同步加可选字段）。返回体每条加 `scope` 字段：`product` / `general`。

`basis.lookup` 同样默认取项目产品，并优先查快照里 `basis` 列出的标准。评测题（`kb-eval`）加可选字段 `product`，报告按产品分组统计。

## 六、`kb.mapping` 工具（B3）

新工具，区域 `knowledge`、只读，经 `tools.invoke` 调用、进审计（只记参数里的标准号和条数）。

请求：

```json
{"source": "ISO/IEC 27001:2022", "target": "GB/T 22239-2019", "control": "A.5.15", "query": "", "limit": 20}
```

`source` 必填；`target`、`control`、`query` 可选（`control` 精确匹配条款号，`query` 在映射说明里全文检索）。

返回：

```json
{"items": [{"source_ref": "A.5.15", "target_ref": "8.1.4.2", "relation": "partial", "note": "访问控制策略……",
            "doc_id": "L4-CMP-ISO-MAP-001", "version": 1}], "total": 1}
```

`relation` 取值：`equivalent` 等同 / `partial` 部分覆盖 / `related` 相关。映射矩阵作为知识条目（L4、类型 MAP，已有取值）走正常的投料、审核、发布，只返回已发布的现行版本。授权（开发线 1 的迁移写入、同步 `tests/test_tools.py`）：`compliance-basis`、`solution-designer`、`policy-drafter`、`consultant-lead`；知识侧 Agent 不需要。

## 七、Agent md 的产品段与模块段（C1）

为与上面的“模块”区分，md 里按产品写的部分叫**产品段**、按模块写的部分叫**模块段**。

- md 正文末尾保留一级标题 `# 服务产品模块`，下面每个二级标题是一段：`## 产品 SOC：SOC 运营体系设计`、`## 模块 DJBH：等保 2.0 整改与体系建设`（`产品` / `模块` + 空格 + 代号 + 全角冒号）。
- 运行时拼系统提示时，`# 服务产品模块` 之前的通用部分全部保留，之后只保留与项目快照的产品和所选模块代号匹配的段；没有匹配的产品段时，按该 md 写的“模块未就绪”规则处理。对话不在项目里时只保留通用部分。
- frontmatter `service_modules` 改为列代号（`[SOC, NSG]`），仍只作说明；提示词版本照旧按 md 全文哈希。
- 先改 `solution-designer.md` 做样板（它已是这个结构，只改标题格式），负责人确认后其余 Agent 一次性改（二期计划八-9）。
