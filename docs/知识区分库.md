# 知识区与项目区分库（M5 ③）

依据：架构设计“知识区与项目区分库”，决策记录 2026-11-09（一期同库分表，S5 拆库，隔离落到数据库账号层面）。

## 结构

| | 主库 `consult` | 知识区库 `consult_kb` |
|---|---|---|
| 账号 | `consult`（数据库容器初始账号） | `consult_kb`（非超级用户，不能建库建角色；两个库都收回了 PUBLIC 的连接权限，它连不上主库） |
| 表 | 用户、角色、项目区（证据、交付件、确认卡、运行……）、对话、后台任务、审计、用量 | `kb_items` `kb_versions` `kb_chunks` `kb_reviews` `kb_uploads` `kb_deid_reports` |
| 迁移链 | `backend/alembic`（版本表 `alembic_version`） | `backend/alembic_kb`（版本表 `alembic_version_kb`） |
| 扩展 | pgvector、zhparser（历史迁移装的，分库后不再使用） | pgvector、zhparser、检索配置 `zh`（由 `kb-init.sh` 以管理员身份安装） |

后端同时持两个连接（`DATABASE_URL`、`KB_DATABASE_URL`）。会话按模型基类 `KbBase` 把知识区读写发往知识区库；两库之间没有外键，`kb_uploads.job_id` 只作记录（主迁移 0030 去掉了外键）。一次提交同时写两库时分别提交，不是两阶段提交：唯一同时写两库的是投料（知识区写上传记录、主库写后台任务和审计），后台任务可重复执行，只成功一半时重新上传即可。

不配 `KB_DATABASE_URL` 时两区同库（本地开发、单元测试），知识区迁移链跑在同一个库上。生产（`APP_ENV=prod`）不分库、或两库账号相同、库名相同，后端拒绝启动。

## 新部署

1. `.env` 设置 `KB_POSTGRES_PASSWORD`（不要用 `@ : / ? # %`，至少 20 位）。
2. `docker compose up -d --build`：postgres 首次初始化数据卷时自动执行 `kb-init.sh` 建库、建账号、装扩展；后端启动时两条迁移链各自升级到最新。

## 已有数据的旧部署（测试机）

```bash
git pull && echo "KB_POSTGRES_PASSWORD=<自己生成>" >> .env   # 口令不要贴到聊天和 PR 里
docker compose build postgres backend && docker compose up -d postgres
docker compose exec postgres kb-init.sh                          # 建库、建账号、装扩展（可重复执行）
docker compose run --rm backend python -m app.cli kb-split      # 复制知识区数据并逐表核对行数
docker compose up -d --build                                     # 后端能启动；日志里会提示主库还有旧副本
# 检索、审批队列、知识地图核对无误后（删数据，先经负责人同意）：
docker compose exec backend python -m app.cli kb-split --drop-source
```

后端启动时的检查：

- 主库的知识区表是空的（新部署时旧迁移建出来的）→ 自动删除。
- 主库有知识区数据、知识区库是空的 → 拒绝启动，提示执行 `kb-split`。
- 两边都有数据 → 正常启动，日志告警，等 `--drop-source`。

`kb-split` 只在知识区库为空时复制；复制后（以及每次执行时）逐表核对行数，不一致就不删任何数据。向量列按文本原样搬，不重新向量化；全文检索列是生成列，自动重算。对象存储的知识区本来就是单独的桶，不动。执行记审计 `kb.split`（只记各表行数）。

## 备份与恢复

`scripts/backup.sh` 另导出知识区库为 `kb.dump.gpg`，清单记 `alembic_kb` 版本；`scripts/restore.sh` 删库重建后还原，并重跑 `kb-init.sh` 补回库级权限（`pg_dump` 不带库级授权）。分库前做的备份没有 `kb.dump.gpg`，知识区数据在 `db.dump.gpg` 里，恢复后按上一节重新搬迁。

## 以后改知识区表

```bash
cd backend
alembic -n kb revision --autogenerate --rev-id k0002_xxx -m "M?：说明"   # 生成后人工检查
```

主迁移链（`alembic revision ...`）的自动生成已排除 `kb_` 表。分库后不支持把主迁移链降级到 0030 以前。
