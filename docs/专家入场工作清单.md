# 专家入场工作清单与执行指导书

版本 1.0（2026-11-18）。依据：决策记录 2026-11-18“无专家先行”（负责人同意）、`docs/4A架构设计.md` v4.0 第七、八节、《人工环节复查》《人工职责清单》。

二期在没有人工专家的情况下先把平台框架跑通，几个产品都按“公开方法版 v0、待专家复核”就绪。只有专家能做的事先排着队，本文列出这些积压事项，并说明专家入场后按什么顺序做、怎么做、做到什么算完。具体页面怎么点，看《平台操作指导书》《知识管理指导书》；产品评审的示范，看《专家交付指导书》。

## 一、先记住的五条

1. **专家只做五类事**：签字担责、客户数据、只有人知道的事、公司经验的认可、规则变更。程序和 Agent 能判断的已经自动化了，专家处理的是例外，不要重做一遍自动核验。
2. **资质边界**：意见和样例里不出具、不暗示等保测评结论、密评结论、认证结论，统一写“差距分析、符合性初判、整改建议”。
3. **只用虚拟客户**：评审样例、写意见、截图，都只用 BANK-A、LOGI-B、FIN-C、HLTH-D、MFG-E 等虚拟客户。真实项目经验要先投料、经去标识确认，才能进知识库。
4. **两人原则**：自己写的、自己导入的版本，自己不能审、不能抽检；内容审核由知识专家做，合规审核由知识管理员做。
5. **改配置、改 Agent md 都走 PR**：专家把意见写清楚，由开发线 2 改文件、开 PR，负责人合并。`agents/*.md` 的修改要负责人同意。

## 二、入场准备（第 0 天，约半天）

| 步骤 | 谁做 | 怎么做 |
|---|---|---|
| 开账号 | 系统管理员 | 在“用户与角色”页建账号，按分工授角色：知识专家、知识管理员、顾问、项目负责人。首次登录要改口令、绑动态码 |
| 读材料 | 专家 | 本文，《专家指导书》第一、四节，《专家交付指导书》前两节，自己负责的产品的配置文件 `products/<产品>.yaml` |
| 看现状 | 专家 | 工作台（我的待办）、知识审批队列（待审、存疑、待抽检、待复查、复审到期）、知识地图与健康（覆盖矩阵、缺口 TOP） |
| 定分工 | 知识库负责人 | 按第三节填好每项的负责专家和完成日期，发到群里 |

## 四、怎么执行

### 1. 审定产品和模块配置（E1、E10、E11）

1. 开发线 2 把 yaml 整理成一张表，列出交付件、评估域、每步任务说明、门禁规则、禁用词和依据，专家不必直接读 yaml。
2. 专家逐项在表上批注：对不对、缺什么、哪里在客户面前站不住。照《专家指导书》第五节的五个方面看：交付件清单、评估基线、任务说明、质量门禁、黄金样例。
3. 开发线 2 按批注改配置，PR 描述写明“专家 X 审定”。配置里把 `expert_review` 改为 `done` 的那一行必须附专家意见，经负责人合并。
4. 改配置只影响之后立项的项目，已立项的项目沿用立项时的配置快照。

### 2. 评审虚拟客户整套交付件（E2）

1. 在测试机上打开对应产品的虚拟项目，逐份看 D1～D8，同时对照项目驾驶舱里的确认卡和证据。
2. 按下表填写，每个产品写一份评审表，交给开发线 2：

| 问题 | 怎么答 |
|---|---|
| 公司的做法和样例不同的地方有哪些？ | 至少列 3 处；如果没有，说明原因 |
| 缺了什么公司一定会做的内容？ | 逐条列出 |
| 哪里写错了，或在客户面前站不住？ | 写清章节和原因 |
| 换成其他行业要改哪些地方？ | 逐条列出（作为三期行业包的输入） |
| 结论 | 采纳 / 修改后采纳 / 推倒重写 |

3. 改进项分两类：
   - 属于配置或知识的，进 E1 或 E12；
   - 属于 Agent 写法的，由开发线 2 起草 md 修改，经负责人同意后改。

### 3. 处理知识队列（E3～E6、E8、E13）

- 顺序：存疑 → 待抽检 → 待审 → 复审到期和待复查。抽检和存疑影响自动发布会不会停摆，排在最前面。
- 看存疑条目时，先看 Agent 列出的问题清单，再看并排的依据原文，结论只能是通过、退回或下线，不要在审核时改正文：内容要变就退回作者，由作者出新版本。
- 抽检不通过时写清原因。最近 20 次不通过率超过 10%，这一类自动发布会整批转人工，这是从严设计，不是故障。
- 依据原文（SRC）只核对来源、文号、条号和标题。国家标准、行业标准不收正文，不要补正文。
- 每天的量：一位知识专家加一位知识管理员，每天 2 小时左右，一周能清掉一个产品的存疑和抽检。

### 4. 审定评测题（E7）

1. Agent 评测集：看每道题的提问、要点（points）和不应出现的内容（must_not）是否符合公司做法；红线题（资质边界、编造条款号）不能删，只能加。
2. 知识评测题：确认期望依据（文件加条款号）正确；改动在资料仓直接提交，代码仓的回归题经 PR。
3. 审定后由开发线 2 重跑评测，结果作为三期“评测门接入 CI”的基线。

### 5. 公司实践补充（E12）

- 投料时写清来源说明和授权编号，要填来源项目时只填虚拟代号或本项目代号。
- 去标识确认由知识管理员做，不能是上传者本人；确认后平台删除原件。
- 第三级审核：知识审核 Agent 先出意见，一位知识专家（不能是作者）做内容审核即发布。

## 六、记录与回报

- 每天下班前在群里报三个数：清了多少存疑、抽检了多少条、退回了多少条。不贴条目原文，只写编号。
- 配置和 md 的意见写进 PR 评论，或交给开发线 2 代写进 PR，不要只停留在聊天里。
- 发现红线问题立即停下，报负责人：真实客户信息、机密级内容、资质结论用语都算。
