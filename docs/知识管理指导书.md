# 知识管理指导书

版本 1.1（2026-11-16，原《知识库开发与维护指导书》v1.0 改名并补充）。本文讲知识库从零建起来、再长期维护，**按什么顺序做、每一步谁做、怎么做、做到什么算完**，以及资料放在哪里、怎么从测试环境搬到生产。

依据：

- 《知识库建设方案》《知识库建设总体计划》（为什么这样建）
- 《二期开发计划》第十一节（公开知识准确应用）、第十二节（三级审核）
- 决策记录 2026-11-13、2026-11-15、2026-11-16

角色职责汇总见《人工职责清单》，平台页面怎么用见《平台操作指导书》。

## 谁做什么

| 角色 | 职责 |
|---|---|
| 知识库负责人（专人） | 定每批内容和先后、维护下载清单、每周看知识地图、季度依据核对出清单 |
| 知识专家（每个产品至少 2 人） | 起草和改条目、内容审核、抽检、复查、第三级拍板 |
| 知识管理员（至少 2 人） | 去标识确认、合规审核、季度依据变更登记 |
| 平台（自动） | 切条、核验、引用校验、知识审核 Agent 审核、自动发布、抽检排队、复审到期复查、使用反馈标记、对比评测门禁 |
| 开发线 2（Claude Code） | 收集公开资料、写下载清单、起草解读和映射、写评测题、跑入库和评测 |

## 先记住五条

1. **原文和解读分开。** 条款号和原文只取官方原件，机械切分入库，不经模型改写。模型只起草解读、映射、方法、案例，而且只能引用已入库的条款。
2. **国家标准不收全文。** GB/T、JR/T、GM/T 等只收条款号、条款标题、解读和映射。原件只放在下载目录，供审改时对照。
3. **宁缺勿错。** 查不到的依据，Agent 标“【依据待核实】”，不靠记忆补写条款号。
4. **知识区不收客户信息。** 项目沉淀先去标识，由知识管理员确认（不能是上传者），确认后原件删除。
5. **机器先审，人看例外。** 依据原文由程序核验，公开解读由知识审核 Agent 审，全部通过的自动发布、按比例抽检。项目沉淀和专家经验必须由一位非作者知识专家拍板。

## 分类速查

| 层 | 内容 | 典型交付物类型 |
|---|---|---|
| L1 | 方法论、交付框架 | MTD |
| L2 | 公司实践、项目沉淀 | CAS、TPL |
| L3 | 行业知识 | REF |
| L4 | 法规标准依据 | SRC（原文或条款目录）、REF（解读）、MAP（映射） |

其他类型：TPL 模板、GLD 黄金样例、POL 制度母版、PIT 踩坑记录；二期新增 ENF 执法案例、RAR 参考架构、BMK 基准数据、GLS 术语对照。复审周期：L4 依据和 ENF、BMK 6 个月，其他 12 个月。

元数据取值以 `backend/app/kb/meta.py` 为准，包括服务产品 SOC / ISO / DSM / IRE / NSG / GEN。改取值要同步公共规范第 7 节，并经负责人同意。

# 第一部分 建库：按顺序做

整体顺序：

1. 准备
2. 下载清单
3. 依据原文切条、核验、自动发布
4. 起草解读和映射
5. 引用校验
6. 知识审核 Agent 审核与自动发布
7. 抽检
8. 对比评测
9. 映射矩阵
10. 产品交付包与萃取
11. 项目沉淀（第三级）
12. 测试环境的知识搬到生产

每一批都走完第 2～8 步，再开下一批。内容上的先后顺序见第二步末尾。

## 第 1 步 准备（一次性）

| 事 | 谁 | 怎么做 | 完成标准 |
|---|---|---|---|
| 账号和角色 | 系统管理员 | 在“用户与角色”页建知识专家（每个产品至少 2 人，作者和审核人要分开）和知识管理员（至少 2 人，上传者和确认人要分开） | 两人原则能成立 |
| 审核员资格 | 知识库负责人 | 内容审核由知识专家担任，须有所审领域 3 年以上咨询实践；合规审核由知识管理员担任 | 名单报负责人 |
| 法务三问 | 法务 | 书面答复客户资料能否沉淀、合同是否限制 AI、内部制度能否改作母版 | 答复前不入公司实践（L2） |
| 自动发布开关 | 系统管理员 | 确认 `.env` 里 `KB_SRC_AUTO_PUBLISH`、`KB_AGENT_AUTO_PUBLISH` 按负责人决定设置；`KB_SINGLE_REVIEWER_PUBLIC` 生产保持关闭 | 在“模型配置状态”页和自检里看到 |
| 资料仓与下载目录 | 知识库负责人 | 原件和清单按批次放进私有资料仓 Consult_Knowledge；部署机把资料仓拉到 `.env` 的 `KB_DOWNLOADS_DIR`，后端看到的是 `/srv/knowledge/downloads/<批次>/`；不提交代码仓（决策记录 2026-11-16） | 目录只读挂给后端 |

## 第 2 步 写下载清单

谁做：知识库负责人，测试助手或开发线 2 可以协助下载。

清单为 CSV，UTF-8 编码，每行一个文件。列如下：

| 列 | 说明 |
|---|---|
| 文件名 | 下载目录里的文件名 |
| 名称 | 如《数据安全法》 |
| 文号/标准号 | 必填，核验时要用 |
| 发布机关 | |
| 发布日期 | |
| 施行日期 | |
| 现行状态 | 现行 / 即将实施 / 已废止 / 已被替代 |
| 版本 | |
| 替代文件 | |
| 原网址 | 必须是官方网站：gov.cn、nist.gov 和境外政府域名（白名单在 `sources.OFFICIAL_HOSTS`，可用 `KB_SOURCE_HOSTS` 扩充）；出海地区先做非洲 7 国和港澳、泰国、印尼、越南、新加坡、马来西亚 |
| 原件 sha256 | |
| 切分方式 | 按条 / 按章节 / 条款目录；不填时按文号判断，GB、JR/T 等标准自动按目录切 |
| 一级目录 | |
| 适用行业 | |
| 获取方式 | 写“已下载”；不是“已下载”的行跳过 |

sha256 在下载机上算：`sha256sum 文件`。原网址和 sha256 缺一项，这一行就不能自动发布，只能转人工审核。

**内容先后**（《二期开发计划》第十一节）：

1. 近两年新发布或修订的法规。
2. 金融、电力行业文件。
3. 等保、数据安全、密评的条款目录、解读和映射（与控制映射矩阵合用）。
4. NIST、MITRE ATT&CK（要保留版权声明）。其中 ATT&CK 和 Sigma 规则加工成 SOC 检测用例和处置剧本。
5. 监管处罚案例，加工成异议应答。只记问题类型、依据和金额，不记当事单位名称。

## 第 3 步 依据原文切条、核验、自动发布（第一级审核）

谁做：知识专家或知识管理员执行命令，平台自动发布。

```bash
# 先只切不入库，抽看几条
docker compose exec backend python -m app.cli kb-source-split /srv/knowledge/downloads/b1/清单.csv \
    --dir /srv/knowledge/downloads/b1 --out /tmp/src-b1
# 核验并自动发布
docker compose exec backend python -m app.cli kb-source-publish /srv/knowledge/downloads/b1/清单.csv \
    --dir /srv/knowledge/downloads/b1 --as <知识专家> --report /tmp/src-b1.json
```

平台做的事：

- **切分**：法规按“第 X 条”切，条号要连续；NIST 按控制号或章节切；国家标准只切条款目录。每条一个 SRC 条目，带文号、版本、施行日期、现行状态和替代关系。
- **检测**：每条先过机密级检测。
- **核验**：五项全部通过才由平台自动发布，审核记录写“平台核验”：
  1. 原网址在官方网站白名单里；
  2. sha256 一致；
  3. 写了文号；
  4. 切出了条款且没有被退回；
  5. 条号连续。
- **转人工**：没有通过的转人工审核。
- **抽检**：随机抽 5% 进抽检队列。

人做的事：

- 打开 `--report` 看没有通过的行。常见原因有原件是扫描件、条号跳号、文号缺失。改清单或换原件后重新跑。同一文件重跑时条目 key 不变，平台建新版本，不会重复。
- 转人工的条目按两人原则审：内容审核和合规审核各一人，作者不审自己的。
- 抽检：知识专家在审批页“抽检”里对照原件看，不能抽检自己导入的版本。

完成标准：这一批 SRC 全部是“已发布”或“已退回”，没有长期挂在队列里的条目。

## 第 4 步 起草解读、映射、方法

谁做：开发线 2 或知识专家起草，Agent 经网关协助。

```bash
docker compose exec backend python -m app.cli kb-draft --source <公开资料> --source-detail "<来源>" \
    --out /tmp/drafts --as <知识专家>
```

- 起草的内容包括：
  - REF：解读；
  - MAP：A 标准某条对应 B 标准某条；
  - MTD：方法；
  - 只含公开资料的 CAS、OBJ；
  - ENF 执法案例（只记问题类型、依据和金额，不记当事单位）、RAR 参考架构、GLS 术语对照、BMK 基准数据。
- 引用写成“文件 + 条款号”，只引用第 3 步已入库的条款。
- 条目文件格式见 `backend/app/kb/files.py`，示范见 `knowledge/samples`；正式条目文件放资料仓。
- 文件里的 `key` 是固定标识，重复导入按它建新版本；doc_id（如 ENF-003）由平台入库时分配，文件名或正文里写的编号不算数。
- 人工核对后导入：`kb-import /tmp/drafts --as <作者> --submit`。

## 第 5 步 引用校验（导入时自动）

平台自动做：REF、MAP、CAS、OBJ 里每个“文件 + 条款号”都必须能在库里找到原文或条款目录。找不到的列为“待核”，**不能提交审核**。审核页会并排显示原文。

人做：处理“待核”。有两种办法：

- 补下载这份依据，回到第 2、3 步；
- 改成库里已有的正确条号。

不允许删掉条号来绕过校验。

## 第 6 步 知识审核 Agent 审核与自动发布（第二级审核）

适用范围：公开来源、无需去标识的 REF、MAP、MTD、ENF、RAR、GLS，以及只含公开资料的 CAS、OBJ。TPL、GLD、POL、PIT、BMK 走人工两人审核；SRC 走第 3 步。

平台自动做：

1. **程序规则**：检查引用都已核对、没有测评或认证结论用语、没有机密级内容、元数据齐全。
2. **知识审核 Agent**（`kb-reviewer`，经网关，不授权工具）按七项清单逐项判断，写明理由：
   - 忠于原文
   - 不添加要求
   - 引用对得上
   - 资质边界
   - 无客户与机密信息
   - 不重复不冲突
   - 适用条件清楚
3. 全部通过的自动发布，标“Agent 审核”。审计记规则、Agent 和提示词版本，不记原文。
4. 任何一项存疑的进人工队列，问题和原文对照已经列好。

人做（我的任务“知识审核”）：

- 内容审核由知识专家做，合规审核由知识管理员做。
- 只看 Agent 标出的那几处，用同一份七项清单判断，通过或退回。退回要写明改什么。
- 作者不能审自己写的版本。一人同时持有两个角色的，可以审两项。

## 第 7 步 抽检与自动停止

| 类别 | 抽检比例 | 停止条件 |
|---|---|---|
| SRC 依据原文 | 随机 5% | 最近 20 次抽检不通过率超过 10%，这一类回到人工两人审核 |
| Agent 审核 | 随机 20%；最近 20 次不通过率超过 5% 时升到 40% | 同上 |

- 抽检人是知识专家，不能抽检自己写的或自己导入的版本。不通过的退回修改。
- 问题率回到 10% 以下，平台自动恢复。如果是管理员手动硬停的，恢复要由负责人决定。
- 起步阶段抽检次数少，1 次不通过就可能触发停止。这是按从严处理设计的，不是故障。
- 知识库负责人每周在“知识地图与健康”页看问题率和自动发布占比。

## 第 8 步 对比评测（每批必做）

谁做：平台在入库后自动跑；知识专家评审题目。

```bash
docker compose exec backend python -m app.cli kb-eval /srv/knowledge/eval/<批次>.yaml --as <用户> --compare --out /tmp/eval.json
```

- 题目分三类：按条号查询、跨依据映射、行业要求。每批至少覆盖本批新增的依据。
- 同一批题目分两次作答：一次不用知识库，一次用知识库。平台自动核对文件名和条款号，报告两种方式的准确率和编造条号的次数。
- **不达标的这一批暂不发布。** 先查是缺条目、元数据错了，还是检索门槛（`KB_BASIS_MIN_RERANK`）要校准。
- 评测只用虚拟数据。外部模型只限开发测试环境。

## 第 9 步 控制映射矩阵

谁做：开发线 2 起草，知识专家审核。

- 第一份是 ISO 27001 与等保 2.0 管理要求的映射 v0，以后按产品需要扩充，例如数据安全法与 DSM 评估项的映射。
- 导入后，依据与差距分析、方案设计、制度起草、咨询师这 4 个 Agent 可以用 `kb.mapping`（只读）查询。
- 每条映射两端的条款都必须已入库（第 5 步规则同样适用）。

## 第 10 步 产品交付包与萃取

谁做：产品专家负责人（知识专家角色）给出结构和公司做法；开发线 2 起草。

- 每个产品约 50 条，包括 MTD 方法、TPL 模板、OBJ 异议应答和评估基线。
- 交付包结构、产品配置 `products/*.yaml` 里的交付件、评估域和提示词，要由产品专家核对。之后经负责人同意，把配置从 draft 改为 ready。
- 治理规划（NSG）萃取工作坊约 5 人天。专家时间不够时，降级为“平台已配置、公司实践待补”的版本。
- 公司做法属于 L2 / L5，**走第三级审核**（第 11 步），不自动发布。

## 第 11 步 项目沉淀与专家经验（第三级审核）

来源包括项目回流、专家经验、内部制度改造。

1. **投料**：顾问或专家在“知识投料”页上传。文件名不进审计。
2. **去标识**：
   - 平台按规则词库自动替换；
   - 脱敏审查 Agent 复查漏网的名称；
   - 知识管理员（不能是上传者）对照报告确认，报告只有类别、占位符和次数。确认后，平台删除原件和未去标识的解析结果。
3. **起草条目**：作者按条目格式写成 CAS、TPL、OBJ 或 MTD，标服务产品和行业。
4. **Agent 先审**：知识审核 Agent 按七项清单列出问题和建议。
5. **人拍板**：一位知识专家（不能是作者）判断“是不是公司认可的做法”，然后发布或退回。**不自动发布，不抽检，逐条人审。**
6. **记回流**：投料编号记下来，项目删除确认时要填。

## 第 12 步 测试环境的知识搬到生产（决策记录 2026-11-16）

公开知识在测试机上建好、评测达标后，整体搬到生产，生产上不重做。

```bash
# 测试机：导出已发布的公开知识，打印清单哈希
docker compose exec backend python -m app.cli kb-export /tmp/kb-export --as <知识专家>
# 把目录拷到生产部署机后：哈希全对才导入
docker compose exec backend python -m app.cli kb-import-export /srv/kb-export --sha256 <清单哈希> --as <知识专家>
```

- 导出的是条目文件和 manifest.json（文件哈希、原 doc_id、作者、审核记录），不带审核意见原文。
- 生产导入时平台重新自动核验：审核记录完整、机密级、资质边界、引用、元数据。通过的保留原作者和原审核人发布，另记一条“平台迁移”审核；没通过的转人工审核。
- 只搬公开知识。项目沉淀、专家经验在生产上直接走第 11 步。

# 第二部分 维护：周期性做

| 频率 | 事 | 谁 | 怎么做 |
|---|---|---|---|
| 每天（自动） | 使用反馈 | 平台 | worker 扫描交付件引用。顾问常改掉、推翻的条目会被标“待复查”，进抽检队列。应急时可执行 `kb-recheck-scan` |
| 每周 | 处理存疑项、抽检、待复查 | 知识专家、知识管理员 | 看我的任务。目标是队列不积压超过一周 |
| 每周 | 看运营 | 知识库负责人 | 在“知识地图与健康”页看覆盖缺口 TOP、问题率、自动发布占比、贡献统计 |
| 每季度首月 | 依据时效核对 | 知识库负责人出清单，知识管理员登记 | 对照官网整理核对清单，表头同下载清单。平台不自动抓官网（联网，决策 11-15 不做）。<br>`kb-basis-check 核对清单.csv --as <知识管理员>` 先比对，核对后加 `--apply`：平台把新发布、修订、废止的依据建新版本、标替代或下线 |
| 依据换版后（自动） | 影响提醒和门禁 | 平台 | 引用旧条款的交付件会通知相关顾问复核。引用已废止或已被替代的条款，签署前会被拦下；即将实施的判“重要” |
| 每批入库 | 对比评测 | 平台 / 知识专家 | 同第 8 步 |
| 条目到期复审 | 复审 | 平台 + 知识专家 | 公开来源的条目先交给知识审核 Agent 复查，通过的顺延复审日期，存疑的转人；项目沉淀和专家经验仍由人复审 |
| 有需要时 | 下线 | 知识专家、知识管理员 | 不再认可的做法下线，历史版本保留。已废止的依据不下线，标状态，平台会自动拦截引用 |
| 换模型时 | 重新向量化 | 运维 | 换向量维度要先有新迁移，再执行 `kb-reembed`；换完跑一次对比评测 |

## 修改条目的规矩

- doc_id 由平台分配，永远不变。内容有变化一律建新版本，历史版本保留。
- 只经 `kb-import`、知识投料页或审批页修改，不直接改数据库（测试助手也不行）。
- 元数据取值、审核规则、七项清单的修改都属于规则变更，要经负责人同意。

## 出问题怎么办

| 现象 | 先查 |
|---|---|
| 自动发布突然全停 | 抽检问题率是否超过 10%，开关是否被关 |
| Agent 老标“【依据待核实】” | 是否缺依据（看知识地图缺口），是否检索门槛过高（跑对比评测） |
| 引用校验一直“待核” | 依据没有入库，或条号写法和条款目录不一致 |
| 去标识确认点不了 | 你是上传者，需要另一位知识管理员确认 |
| 审核项置灰 | 你是作者，需要另一位同角色的人处理 |
