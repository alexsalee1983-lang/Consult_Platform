## 一、设计原则

1. **按交付环节分工，不按知识领域分工。**
   6 个一级目录、几十个服务产品的差异放在知识库标签里，不靠增加 Agent 的数量来区分。如果按领域建 Agent（"数据安全 Agent""SOC Agent"……），数量会膨胀，规范也会分叉。
   同一个"制度起草 Agent"，挂载 SOC 交付包时起草运营制度，挂载治理规划交付包时起草治理制度。

2. **生成与评审分离。**
   写东西的 Agent 不评审自己的产出。质量评审 Agent 独立存在，并且模拟客户的挑战。

3. **规范只写一次。**
   写作规范、保密规则、资质边界和引用格式统一放在《01_公共规范.md》中，每个 Agent 引用这份文件，不在各自的 md 里复制。

4. **知识侧和交付侧隔离。**
   交付侧 Agent 只能读取知识库的"已发布区"。内容要写入知识库，只能经过"知识库建设 Agent → 脱敏审查 Agent → 专家审批"这一条路径。

5. **顾问在环。**
   所有对客交付物都是"草稿"。顾问审核并署名后才能交给客户，Agent 不直接面对客户。

| 9 | 项目交付管理 | delivery-pm.md | ⑦ 不管理预期 | 项目经理 | 读 L1 | 一期以"模式"运行，二期独立 |
| 12 | 方案设计 | solution-designer.md | ③ 只对标准不对业务；④ 建议泛化 | 交付顾问、项目经理 | 读 L1–L5 已发布区；读项目区 | 一期（2026-11-07 新增） |
| 10 | 售前方案 | presales.md | 售前复用交付经验 | 售前 | 只读"售前可见"字段 | 预留 |
| 11 | 新人带教 | coach.md | 新人需要约 2 年才能独立交付 | 新顾问 | 读 L1–L5 | 预留 |

> **为什么一期是 6 个独立 Agent，再加 3 个"模式"？**
> 方案第 5～6 周要配置的 3 个高频场景是制度起草、条款与依据查询、异议应答，分别对应 #5、#4、#6，需要先做好。
> 调研、报告和项目管理所依赖的模板（访谈提纲、报告模板、客户管理工具）要到第 3～5 周才会随交付包成型。因此一期先把它们作为咨询师 Agent 的工作模式来运行，等模板稳定以后再拆成独立 Agent。
> 本次已经把这 3 个 Agent 的 md 写完整，拆分时可以直接使用。

## 四、一个典型项目里 Agent 的协作方式

| 项目阶段 | 主要 Agent | 产出 | 质量门禁（质量评审 Agent） |
|---|---|---|---|
| 启动 | 项目交付管理 | 启动会材料、范围确认单、WBS、项目卡 | 范围边界和资质边界写清楚了吗？ |
| 调研 | 调研访谈 | 调研计划、资料清单、按角色的访谈提纲、访谈纪要 | 每个问题都能追溯到控制项或报告章节吗？ |
| 分析 | 依据与差距分析 | 差距分析表、监管要求清单 | 每条差距都有证据和依据吗？是否关联了业务？ |
| 设计 | 方案设计 → 制度起草、报告与汇报 | SOC 目标运营模型、实施路线图、制度文件、规划报告 | 方案与客户人力和工具匹配吗？关键取舍是否由顾问确认？制度能落地吗？建议是否带齐四要素？ |
| 汇报与评审 | 质量评审与异议应答 | 评审意见、预判的挑战及应答 | 模拟客户的高管、业务、审计、技术四类角色进行挑战 |
| 结项 | 知识库建设 → 脱敏审查 | 结项沉淀单 | 脱敏通过，专家审批后入库 |

**交接靠"项目卡"。** 每个项目建一份项目卡（模板见《01_公共规范》第 6 节）。所有交付侧 Agent 开始工作前都要读项目卡，确认客户画像、服务产品、阶段和范围，避免顾问反复交代背景。

## 五、Agent md 统一模板

每个 Agent 的 md 都按下面的结构来写。

```markdown
---
name: 英文标识（小写-连字符）
display_name: 中文名
version: 0.1
phase: 一期 / 二期 / 预留
primary_users: 主要使用者
knowledge_access:            # 对应 RAG 知识集合
  read: [...]
  write: [...]
tools: [...]                 # 平台上实际开放的工具
depends_on: [01_公共规范.md]
handoff_to: [...]            # 产出交给谁
---

# 角色            一句话说明它是谁、不是谁
# 目标            对应哪些根源问题，要做到什么程度
# 适用 / 不适用   遇到不适用的请求时，转交给哪个 Agent
# 输入            开工前必须拿到什么；缺少时先问什么
# 工作模式与流程  按模式分别写步骤
# 输出规范        固定的输出结构和模板
# 自检清单        输出前逐条检查
# 边界与禁止      红线
# 交接            产出交给谁、以什么格式交
# 示例            1～2 个典型的输入和输出
```

**写作要点**

- 流程写成编号步骤。判断规则用"当……时，……，因为……"的形式写清楚，少写形容词。
- 输出必须给出模板或表头。一个 Agent 的输出能不能稳定，主要靠模板。
- 红线单独成节，写成可以检查的句子。例如写"不得出现'测评结论'字样"，而不是写"注意资质边界"。
- 示例只举本公司的真实服务场景，例如 SOC 和治理规划。

## 六、与两个月计划的衔接

| 周 | Agent 相关动作 |
|---|---|
| 第 1 周 | 定稿《01_公共规范》，包括元数据字段、命名规范、密级和角色；在平台上建好 RAG 知识集合（L1–L5、待入库区） |
| 第 2～3 周 | 启用**知识库建设 Agent**（模式 A：盘点筛选），帮专家从 10G 资料中挑出最好的 20% |
| 第 3～5 周 | 启用**知识库建设 Agent**（模式 B：加工入库；模式 C：萃取工作坊支持）和**脱敏审查 Agent** |
| 第 5～6 周 | 上线**制度起草**、**依据与差距分析**、**质量评审与异议应答**三个 Agent，加上**咨询师主入口** |
| 第 7 周 | 在试点项目中使用；顾问反馈统一记到"Agent 问题清单"，区分是 md 的问题还是语料的问题 |
| 第 8 周 | 发布 v1；把"结项沉淀"（知识库建设 Agent 的模式 D）写进项目流程 |

## 七、平台落地说明

1. **一个 Agent 对应平台上的一个智能体。** md 正文就是系统提示词，frontmatter 用来配置知识集合和工具权限。
2. **《01_公共规范》的放置方式**：如果平台支持公共提示词或全局指令，就放在那里；如果不支持，就拼接在每个 Agent 系统提示词的最前面，但源文件只维护这一份。
3. **如果平台不支持 Agent 之间互相调用**：咨询师 Agent 在识别出任务类型后，不直接调用其他 Agent，而是输出"建议转到 ××Agent，并附上这段交接信息"，由顾问复制过去。等平台具备编排能力以后再改成自动路由。
4. **知识集合按层级切分**（L1、L2-SOC、L2-治理、L3、L4、L5、待入库区），每个 Agent 只挂载自己需要的集合。这样既能控制检索噪声，也能控制权限。
5. **版本管理**：md 文件放进版本库。每次修改都在 frontmatter 里更新 version，并写一行变更说明。改动先在试点中验证，再发布。

## 八、衡量 Agent 是否有用

| 指标 | 怎么采集 |
|---|---|
| 交付物一次通过率 | 质量评审 Agent 给出"通过"的比例 |
| 报告和制度编写耗时 | 试点项目前后对比 |
| 依据"待核实"比例 | 依据与差距分析 Agent 的输出中，标注"待核实"的条目占比，用来反映依据库的缺口 |
| 新异议入库数 | 质量评审 Agent 标出的"新异议"中，最终入库的数量 |
| 顾问满意度 | 每次对话后的点赞或点踩，按月统计 |
